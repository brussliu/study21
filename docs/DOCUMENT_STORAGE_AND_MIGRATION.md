# 資料ファイル保存・2.0 移行設計

## 2.1 の所有権と公開方式

資料とフォルダは `家族学生ID` で所有する。生徒は自分のアカウント ID、保護者は紐づく有効な生徒のアカウント ID に解決されるため、同一家族だけが同じ資料を参照できる。API の全検索・更新・削除はこの ID を条件に含める。

新規ファイルは次の非公開構造で保存する。

```text
{STUDY21_DOCUMENT_STORAGE_ROOT}/
  families/{家族学生ID}/{yyyyMM}/{資料番号}/{枝番号}-{UUID}.{拡張子}
```

Web サーバーの静的公開ディレクトリには置かない。プレビューとダウンロードは `/api/user/documents/{資料番号}/files/{枝番号}/content` を経由し、HTTP セッションと家族所有権を確認してから返す。元ファイル名は DB に保持し、新規アップロードの物理名には UUID を使う。2.0 から移行したファイルは照合可能性を優先し、2.0 の物理名を保持する。

## study2.0 との比較

2.0 は `${catalina.base}/webapps/file/doc` をルートに、概ね `/doc/{yyyyMM}/{資料番号}/{資料番号}_{枝番号}.{拡張子}` へ保存し、`/doc/**` と `/file/**` を静的公開していた。この方式は URL を知る別ユーザーが認可チェックを迂回できる。

2.1 は家族 ID を物理パスと DB の双方に持ち、バイナリ応答も必ず認証 API を通す。また、保存規則・パス検証・旧ファイル解決は `DocumentFileStorage` に閉じ込めている。

## 2.0 からの段階移行

1. `TBL_DOC_フォルダ情報.sql`、`TBL_DOC_資料情報.sql`、`TBL_DOC_資料詳細情報.sql` の順で 2.1 に作成する。
2. 2.0 の DOC テーブルには所有者がないため、対象資料と `家族学生ID` の対応表を事前に確定する。全資料が一家庭分の場合のみ、`MIG_DOC_資料管理_20260831.sql -v family_student_id=...` をそのまま使える。
3. 移行 SQL でメタデータと明細を投入する。別家族と資料番号が衝突した場合は処理を停止する。
4. 移行期間は `STUDY2_DOCUMENT_STORAGE_ROOT` に 2.0 の `webapps/file/doc` を読み取り専用でマウントする。DB に残る `/doc/...` パスを 2.1 API が読めるので、サービスを止めずに段階移行できる。
5. 旧ファイルを新しい家族別構造へコピーして SHA-256 を照合後、`MIG_DOC_物理ファイル切替_20260910.sql` で `パス` と2.0実ファイル名を同一トランザクションで更新する。
6. 全件照合後に旧ルート設定を外す。一定の保留期間が終わるまで 2.0 の原本は削除しない。

注意: 複数家庭の資料が 2.0 に混在する場合、推測で割り当ててはならない。CSV 等の明示的な `資料番号,家族学生ID` 対応表を作り、移行 SQL を対応表 JOIN 方式へ切り替える。
