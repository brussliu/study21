# 架构决策记录

## 为什么一个 PC 前端

- 管理员、学生、家长在 PC 端共享同一套系统外壳、Design Token 与组件。
- 通过路由区域（`/admin`、`/student`、`/parent`）与 Menu Registry 区分，避免维护多个 PC 应用。

## 为什么一个 Mobile 前端

- 移动端是独立的 Mobile Web / PWA（非 Android 原生 App）。
- 学生与家长主要在移动端使用，共享同一移动外壳与组件。
- 不修改旧 Android 项目（`study2apk`）。

## 为什么两个后端

- 管理员与普通用户（学生/家长）的安全边界、访问频率、发布节奏不同。
- `admin-api` 与 `user-api` 独立运行、独立部署，互不调用。

## 为什么本阶段不做数据库

- 需求明确要求数据库与 DDL 由用户后续独立完成。
- 避免在未确认业务与权限前过早设计表结构。

## 为什么不迁移业务

- 本阶段目标是搭建可构建、可测试的系统骨架。
- 避免在角色权限、DDL 未定的情况下带入业务耦合。

## 为什么 AI 调用用 LangChain4j

- 原先把 OpenAI 兼容的 `chat/completions` 直接用 `java.net.http.HttpClient` 拼；用户要求 AI 调用改用 LangChain4j 框架。
- 接缝不变，仍是 `admin-api` 的 `GeometryAiClient`。实现有两个，由 `study21.geometry-ai.client`（部署时用环境变量 `STUDY21_GEOMETRY_AI_CLIENT`）选择：`langchain4j`（默认，`GeometryAiLangChain4jClient`）与 `http`（旧实现，回退用）。Bean 由 `GeometryAiClientConfiguration` 只建一个；`study21.geometry-ai.stub=true` 时两个都不建，只用固定应答的 `GeometryAiStubClient`（保证 E2E 不出网）。
- 只加 `dev.langchain4j:langchain4j-open-ai` 一个依赖（版本由父 pom 的 `langchain4j-bom` 统一），其 HTTP 实体是 `langchain4j-http-client-jdk`，底层仍是 JDK 自带的 `java.net.http.HttpClient`。
- 返回值仍拼回 OpenAI 兼容的正文（`choices[0].message.content` / `usage`），也仍支持图片（`content` 数组的 data URL）与 `response_format`，因此既有解析器、`BAT_AI呼出履歴情報` 与画面都不变。
- 本次只配到 batC52（AI 画図助手）并验证；课堂笔记（classroom-ai）等其它功能仍用各自的原实现。

## 为什么 AI 设定统一成同一套 TAB

- 用户要求：设定页面上**所有调用 AI 的处理**用同一套 TAB 表现，项目名与位置统一，数字项一律用滑块。
- 规则集中在 `frontend/pc-web/src/features/system-settings/aiSettingsLayout.ts`（唯一来源）。三类画面共用它：runtime 渲染的 AI 批次区块（`study2SettingRuntime.ts`）、图形管理的 `GeometryAiSettingsSection.vue`（batC51/C52）、授课录音的 `ClassroomAiSettingsSection.vue`（STT/batC61/batC62）。
- TAB 固定为 **基本設定**（AI 相关：使用モデル → リクエストタイムアウト → Temperature → 最大出力Token数 → 出力形式）、**System Prompt**、**User Prompt**、**その他**（AI 无关：最大再実行回数 → スレッド数 → 图像条件 → 1回の最大処理数 → コマンド数の上限 → 日次の上限 等）。没有项目的 TAB 不显示。コマンド数の上限（`*_MAX_COMMANDS`）是「一次运行接受多少条」的执行条件，不算 AI 设定，因此放在 その他。
- 「使用モデル」的选择一律占整行，其余项目两列。这条规则也在同一个模块里（`aiIsFullWidth`），runtime 与两个组件共用，避免各自画各自的。
- 本次只统一现有设定项，不新增设定（例如缺 Temperature/最大出力Token数的批次，等后端实现时再补）；不删 User Prompt TAB（已实现的批次都真的在读它）。
- 不调 AI 的区块（图像前处理、命令验证、录音上限、触发器、前置词预设）保持原样。
- 数字项全部渲染成滑块（`input[type=range]` + 右侧值显示），step 与单位由模块决定（s / MB / px / 回 / 枚 / 語 / 文 / 問 等）。

## 为什么【接続テスト】只给 4 个 AI

- 「AIモデル」页面上能测的是 **OpenAI 兼容的 `chat/completions` 4 个**（千問 / 豆包 / DeepSeek / OpenAI）。四者形状相同，所以用同一个后端接缝（`AiConnectionTester` → `GeometryAiClient`＝LangChain4j 实现）发一次极小的 chat 请求即可（输出上限 16 token、超时 30 秒）。
- 端点：`POST /api/admin/setting/testAi`，body 是**保存前的输入值** `{provider, model, apiKey, url}`（这样未保存也能试）。200 的正文用 `ok` 表示成败：`ok=true` →「接続できました（…ms）」；`ok=false` → 错误理由（HTTP 401 等）。设定缺失/未支持的 provider → 400，画面把消息原样显示成红色。
- **BigModel / 智譜 OCR 不给按钮**：它的端点是 `layout_parsing`（要发图片的另一种形式），用聊天请求测不出来，所以画面本来就没有这个按钮（这次也确认过没有）。
- 画面侧：按钮在 URL 项目旁（`data-provider`），点的时候禁用直至返回；`ok=false` 也按失败（红色）显示。

## 为什么 AI 输出用 DTO（@Schema）当唯一来源

- 用户要求：batC51/batC52 的 AI 返回数据不再在提示词里手写 JSON 结构，统一用 DTO 接收与管理；DTO 是唯一来源，不在提示词/DB 里重复维护一份 JSON Schema。
- DTO 在 `admin-api` 的 `geometryai/dto`：`BatC51ResultDto`（分類/図形種/図形名/タグ/メモ/認識/コマンド/説明）、`BatC52ResultDto`（コマンド/説明），枚举 `FigureKind` / `FigureSubKind`。每个字段都有 `@Schema(description=...)`，必填用 `requiredMode = REQUIRED`。JSON 键沿用现有的日文键（与 DB 的 `提案JSON` 一致），英文键用 `@JsonAlias` 兼容。
- 用 `victools jsonschema-generator`（4.x，Jackson 2 系；5.x 是 Jackson 3 所以不用）+ `swagger-annotations-jakarta` 从 DTO 自动生成 JSON Schema。同一份生成结果用于三处：①运行时注入提示词（`AiResponseFormatPrompt`）②设定页 Data TAB 的 API（`GET /api/admin/setting/ai-response-schema?task=...`）③解析时用 Jackson 读进 DTO（`AiResponseDtoParser`，保留命令行回退）。
- 设定页新增 **Data TAB**（`AiDataSchemaPanel.vue`，batC51/C52 共用）：显示从 JSON Schema 生成的「项目结构」（字段名/类型/说明/必填，可展开嵌套）与格式化后的 JSON Schema。只读，不能编辑。TAB 顺序＝基本設定 | System Prompt | User Prompt | Data | その他。
- 设计文档里手写的 JSON 例子已删除，改为指向 DTO；seed 的系统提示词也不再写死输出格式。

## 为什么 AI 画図助手は「押さずに反映・失敗には戻さない」

- 用户要求：AI 给出命令后**不要再点按钮**（原来要按【反映】），并且**失败时不要显示【戻す】**（出错了还显示回退按钮很奇怪）。
- 反映は自動：状態が `READY` になったら `applyAssistStep()` がそのまま作図へ流し込む。画面から【反映】【破棄】を外した（判断を挟まない）。適用の記録（`POST /assist/{id}/applied`）はこれまでどおり残す。
- 反映を待たされる場合の扱い：AI の結果がアプレットの準備より先に返ることがある（開いた直後の指示）ので、`waitAppletReadyForApply()`（最大 15 秒・250ms 間隔）で待ってから反映する。押させない以上、ここで待たないと案が無駄になる。
- 【戻す】は**反映済みのステップだけ**に出す（`canRestoreStep`）。失敗したステップは作図を変えていないので、戻す先が無い（押しても何も起きない＝混乱のもと）。ただし DB には「この案は使わなかった」と `POST /assist/{id}/discarded` で記録する（依頼が実行中のまま残らないように）。
- 【戻す】の意味も変えた：**その指示を出す前の作図へ戻す**（＝その指示と、そのあとの変更が作図から消える）。反映が自動になると、押しても何も変わらない「戻す」は取り消しとして使えないため（スナップショットは指示を出した時点の作図のまま残し、反映後に上書きしない）。
- 失敗の理由はそのステップに残し、**どの行で失敗したか**を出す（`applyCommands()` が理由を返す。失敗した行は最大 3 件まで表示し、残りは件数で示す）。従来は 1 行目だけをトーストに出して終わっていた。
- 旧版の履歴に残る「未反映（pending）」は、依頼が残っていれば実行中として状態を取り直し（READY なら自動反映）、依頼が無ければ「反映されませんでした」と案内する（押しても何も起きない行を残さない）。

## 为什么 AI 画図助手の履歴をサーバーに置く

- 用户要求：助手の履歴が `localStorage`（端末ごと）だけだと、**別の PC・別のブラウザで開くと履歴が見えない**。サーバー側の履歴にして、端末をまたいで見えるようにする。
- 新しい入口は `GET /api/user/geometry/ai/assist?figureId=…`（図形ごと・**古い順**・自分が作った行だけ・既定 20 件・上限 50 件）。返すのは指示 / 反映方法 / 生成状態 / 適用区分 / コマンド / 説明 / エラー / 作成・更新日時と、**`指示前XML` を持っているか**だけ。
- `指示前XML` は 1 行が大きくなり得る（上限 2,000,000 文字）ので**一覧では運ばない**。【戻す】を押したときに `GET /assist/{id}` で 1 件だけ取る（`beforeXmlAvailable` が false の行は【戻す】を出さない。端末のスナップショットが無く、サーバーの上限を超える作図は切られているため戻せない）。端末にスナップショット（`localStorage`）があればそちらを優先する。
- 画面は「サーバーが表示の正・端末はスナップショット置き場」: 同じ `assistId` で突き合わせて、指示・コマンド・状態はサーバーの値にし、【戻す】用の作図データと「詳細」の開閉だけローカルから引き継ぐ。サーバーが知らない行（依頼の作成に失敗した等）は捨てずに後ろへ残す。取得に失敗したときはローカルの履歴のままで動く（画面を止めない）。
- 反映できなかった理由（どの行で失敗したか）は `POST /assist/{id}/discarded` の任意 `reason` で `エラーメッセージ` に残す。`適用区分=REJECTED` は「作図に反映しなかった」の意味に広げた（利用者の【破棄】＋反映できなかったとき）。理由つきの REJECTED は履歴で「失敗＋理由」として出す。
- 新規作成中（図形になっていない）とコピーして開いた直後は `figureId` が無いので履歴も無い（助手は空白）。保存して図形になった時点でその図形の履歴になる。
- 索引 `idx_geo_ai_assist_figure_owner`（図形 × 登録者 × 画図指示ID）を追加。既存環境向けに `database/移行/MIG_GEO_AI画図指示_履歴インデックス_20260917.sql`（何度流しても同じ）。

## 为什么【入力欄を隠す】の白い領域は「1px ずらして戻す」で直す（作り直さない）

- 症状：左の入力欄を隠して作図エリアが広がると、右側だけ座標軸・グリッドが描かれず白いまま残る（利用者の報告）。
- 実測で分かったこと（配備版でも再現。真の原因は 3 つ重なっていた）:
  1. **注入先の容器が作ったときの大きさのまま** … `#geometryGgbElement` に GeoGebra が書いた `inline width`（作成時の値）が残る。→ 毎回の同期で容器そのものの幅・高さも枠に合わせる。
  2. **渡す高さが枠の外側の高さ**だった（枠線の分 2px 大きい）。→ `clientHeight`（中身）を渡す。アプレット作成時の `params.height` も同じ。
  3. **GeoGebra は「大きさが変わっていない」と描き直さない**。枠が広がったあと `setSize(1884, 1034)` を何度呼んでも
     絵は古い幅（実測 1953）で止まったままだった。`setWidth` / `setHeight` / `refreshViews` / `setCoordSystem` /
     再描画の停止→再開 / レイヤー（`display`・`visibility`・`transform`・`opacity`）の作り直しは**すべて効かなかった**。
- 決め手（実測・候補を 1 つずつ独立に試した結果）: **`setSize(w+1, h)` のあと `setSize(w, h)` とすると全域が描き直される**
  （枠 1884 で絵が 2544 まで届いた。40ms ほど）。同じ大きさの `setSize` を何度送っても効かないので、
  原因は「大きさが変わっていないので GeoGebra が描き直しを省略している」ことだった。
- 対策：大きさを伝えるときは必ず**1px ずらして戻す**（`nudgeAppletSize`）。`applyAppletSize` と、
  再描画を再開したあと（`scheduleRepaintResume`）に入れる＝落ち着いてからももう何度か回す
  （1 回目は GWT の再レイアウトと重なって無視されることがあるため）。
  **アプレットは作り直さない**ので、待ち時間もちらつきも無く、作図も取り消し履歴（Ctrl+Z）もそのまま残る。
- あわせて「右端まで描けているか」の判定を直した。以前は「白でなければ描いてある」で見ていたが、
  GeoGebra は**描いていない所を透明のまま**残す（実測: canvas は 1498 まで広がったのに、不透明だったのは
  古い幅 903 の所までで、右側は alpha 0。ページの白が透けて白く見えていた）ので、透明（RGB 0）を
  「描いてある」と誤判定して**壊れた状態を見つけられなかった**。今は右端の帯に不透明な画素があるかで見る
  （読み戻せない環境では `null`＝判断しない）。この判定が効くようになったので、
  「送り直しても届かなければアプレットを作り直す」（`retryAppletSizeIfNeeded` → `rebuildAppletForSize`）が
  本当の保険として働く。
- 実測（真の GeoGebra・実アプリ・chrome-headless-shell）: 【入力欄を隠す】180ms、【表示】に戻す 184ms、
  ウィンドウを 2005→2600px に広げる 226ms で右端まで到達。いずれもアプレットの注入は 1 回のまま・
  同じインスタンス・作図（A, B, 線分）も残っていた。
- 内部ビュー幅（`getViewProperties().width`）は壊れた状態でも新しい幅（1498）を返すので、
  この症状の判定材料にはならない（`viewWidthOf` は他バージョン向けの補助として残す）。

## 为什么 STT 可以用「ブラウザ音声認識」（キー不要）

- 用户要求：参照 `work/inputdemo` 的做法（Web Speech API，无需 API Key），设定页加上这个选项，并**默认选它**，先自己跑跑看效果。
- 実装の形: STT プロバイダーに **`browser`** を追加（設定画面の先頭＝既定）。`browser` のときは
  **画面（Chrome / Edge）が Web Speech API で認識**し、final になった発話を
  `POST /api/user/classroom/{id}/transcripts` で送る。サーバーはその分塊で **STT を呼ばない**
  （`ClassroomAiSettings.browserStt`。音声は今までどおり保存するので回放はできる）。
- `GET /classroom/options` が `sttMode`（`BROWSER` / `SERVER`）と言語モード→ BCP-47 の表
  (`sttLanguageCodes`) を返す。**言語コードの定義はサーバー 1 か所**（`sttLanguageCode`）で、
  画面はその表を引くだけ。ブラウザ認識に言語の自動判別は無いので、混在モード（ja-en / zh-en）は
  主言語（ja-JP / zh-CN）で書き起こす（API に `alternativeLanguageCodes` 相当が無い）。
- 認識の言語は `recognition.lang` に 1 つだけ設定する（`continuous=true`、`interimResults=true`、
  `maxAlternatives=1`）。Chrome は無音や一定時間で `end` になるので、録音中なら自動で聞き直す。
  非対応ブラウザ（Firefox / Safari）・マイク不許可・認識サービスに繋がらない場合は日本語で案内を出す
  （音声の保存は続く）。途中経過（interim）は画面に出すだけで保存しない（保存は final だけ）。
- 連番は**サーバーが振る**（ブラウザの切句は分塊と一致しないため）。時間は「録音開始からの経過秒」を受け、
  始まりは前のセグメントの終わりにして単調に増やす。トリガー（フェーズノート）の評価は分塊のときと同じ。
- `browser` のときは モデル・URL・API Key を使わない（画面ではサーバー側の項目を出さない）。
  サーバー側の STT（google / alibaba / whisper / azure / other / stub）はそのまま残るので、混在言語の授業や
  Firefox しか使えない環境では切り替えて使える。
- 副次的な効果: サーバーが分塊ごとに STT を呼ぶ実装には「2 塊目以降が単体で再生できないファイル」という
  不具合がある（実測）。`browser` はサーバー STT を通らないので、その影響を受けない。
  （この不具合は後に**分塊ごとの 16kHz PCM を一緒に送る**ことで直した。上の
  「STT の設定を『AIモデル』ページのタブへ移し…」を参照）

## 为什么 AI 解析（batC61 / batC62）有一个总开关

- 用户要求：**先只试 STT（書き起こし）の精度**，AI 解析（フェーズノート・最終まとめ）**先临时关掉**，之后再说解析的事。
- **バッチ管理画面では batC\* を無効にできない**（`BatchService.updateActive` は batS / batL / batR だけを許可し、C 系は「実行のきっかけを持たない」ため）。しかも授業ノートの起動は `rerunStep` 経由で、**有効／無効に関係なく実行される**。→ バッチのフラグでは止められない。
- そこで **`CLASSROOM_AI_NOTE_ENABLED`**（設定画面「授業録音」→ フェーズ分析のトリガー）を追加。**未設定なら有効**（既定 true）。
  false のとき user-api は **PENDING のノート行を作らない**（＝ batC61 / batC62 を呼ぶ入口が無くなる）:
  ・録音中のトリガー評価（`evaluateTrigger`）は何も作らない
  ・終了時（`end`）も最終まとめの行を作らず、`notice` に理由を返す
  ・`GET /classroom/options` が `noteEnabled` を返し、録音中画面は「AI 解析は現在オフ。書き起こしだけを行います」と案内する
- 一時的に切る／戻すは設定画面のセレクト（使う／使わない）で行う。**AI 解析を止めている間は、詳細画面の最終まとめは空のまま**（「（整理結果はまだありません）」）。
- サーバー側のテストは「AI 解析が無効ならトリガーが成立してもノートを作らない」「終了しても最終まとめを作らず理由を返す」を固定している。
- **2026-09-22 追記**: 種別 C もバッチ一覧から有効／無効を切り替えられるようになり、**無効にすると
  呼出（`rerunStep`）が拒否される**（下の「なぜ種別 C の有効を目印にしたか」の追記 2）。
  ただし**止めたいだけならこの `CLASSROOM_AI_NOTE_ENABLED` を使う**（PENDING のノートを作らないので
  流水線がエラーにならない）。バッチの無効は処理そのものを禁じる強いスイッチで、呼ぶと 400 で失敗する。
  両方を残す理由: 設定画面は「AI 解析をやめる（授業は続けられる）」、バッチは「その処理を止める（呼ぶと失敗する）」。

## 为什么 STT の設定を「AIモデル」ページのタブへ移し、分塊は 16kHz PCM で送る

- 利用者の指示: ①ブラウザ音声認識を選んだときは**設定が要らない項目を隠す** ②STT は
  **ブラウザ音声認識／Google Speech-to-Text／Alibaba Paraformer-Realtime-V2 の 3 つだけ**
  ③Google と Alibaba は **AI モデルと同じ扱い**にして「AIモデル」ページに専用のタブを作る
  ④阿里巴巴も設定できるようにし、**何を設定するかを画面に書く**。
- 設定の置き場（ページ区分 `AI_MODEL`）: `AI_GOOGLE_STT_{MODEL,API_KEY,URL}` /
  `AI_ALIBABA_STT_{MODEL,API_KEY,URL}`。モデルと URL は seed し（`latest_long` /
  `https://speech.googleapis.com/v1/speech:recognize` / `paraformer-realtime-v2` /
  `wss://dashscope.aliyuncs.com/api-ws/v1/inference`）、**API Key は seed しない**
  （各自で入れて【接続テスト】で確かめる）。阿里巴巴は**千問と同じ DashScope のキー**を使える。
- 旧 `CLASSROOM_AI_STT_{MODEL,ENDPOINT,API_KEY}` は provider=whisper/azure/other の互換用に残し、
  値は `database/移行/MIG_AI_STT設定_20260918.sql` が Google の設定へ引き継ぐ（何度流しても同じ）。
- 【授業録音】の STT は**プロバイダーの選択だけ**になった。browser のときはサーバー側でだけ要る項目
  （タイムアウト・話者分離・接続情報）を**出さない**。google / alibaba のときは
  「どのタブで設定するか・いまの値・API Key が設定済みか」を案内として出す（置き場が 1 か所で分かる）。
- 音声認識の【接続テスト】も足した（`POST /api/admin/setting/testStt`）。**無音を 1 回送る**だけ
  （チャットの【接続テスト】と同じ作法）。Google は `speech:recognize` へ LINEAR16、阿里巴巴は
  WebSocket へ pcm を送る（本番と同じ経路）ので、キー・モデル・URL の誤りがそこで分かる。
- 阿里巴巴は **HTTP ではなく WebSocket**（run-task → 音声フレーム → finish-task）。プロトコルは
  `common-core` の `DashScopeAsrClient` に置き、**授業録音の認識と設定ページの【接続テスト】で共用**する。
  言語は BCP-47（ja-JP）→ `language_hints`（ja）、音声は pcm 16kHz。
- 分塊の「**2 つ目以降が認識できない**」問題を直した（実測: `MediaRecorder` の `timeslice` で切った分塊は
  1 塊目だけがコンテナのヘッダを持ち、2 塊目以降は認識エンジンがデコードできない）。画面は分塊ごとに
  **ヘッダ無しの 16bit PCM（`audio/L16`）**を並行して作り（`AudioWorklet`。ブラウザ認識のときは作らない）、
  `POST /classroom/{id}/chunks` の **`stt` パート**で送る。サーバーは `file`（webm）を**再生用に保存**し、
  認識には `stt` を使う（無ければ今までどおり `file` で認識する＝互換）。
  Google へは LINEAR16 + `sampleRateHertz=16000`、阿里巴巴へは `format=pcm` として渡す。
- 実測（実機・偽のマイク・ローカルスタブ）: 分塊 seq=2 が `mime=audio/l16 bytes=161332`（≒5.04 秒 =
  5 秒ぶんの 16kHz 16bit）で届き、**2 塊とも書き起こされた**。アプレット／音声の保存形式は変えていない。

## 为什么 AI のコマンドが実行時に失敗したら「1 回だけ直させる」

- 利用者の報告: 「再画一个正三角形，三个顶点，落在这个圆上。」で
  `Polygon(A, B, C, 3)` が返り、GeoGebra が引数の数の間違いで拒否した（円の指示は成功していた）。
- 実測でわかった原因は 3 つ:
  1. **引数の数の間違い**（`Polygon` は「3 点以上」「点のリスト」「2 点＋頂点数」の 3 形。混ぜると存在しない形）。
     従来のプロンプトには**引数の数の規則が無かった**（サーバーの前段フィルタは長さ・禁止語・危険文字だけを見る）。
  2. **条件を満たしていない**（`A/B/C = Point(c)` は円上の任意の点で、正三角形にならない）。
  3. **失敗が AI に伝わらない**（失敗したらその場で終わり。同じ種類の指示が別の日には成功していた＝当たり外れ）。
- 対策（コード側）:
  - `GeometryCommandSignatureCard` … 紛らわしいコマンドの形と 3 つの規則（使用前定義・条件をコマンドで成り立たせる・
    一覧にある形だけ使う）を system プロンプトへ足す（batC51 / batC52 の両方）。
  - 画面は `getDefinitionString` / `getObjectType` から**「名前 = 定義（型）」の一覧**を作って依頼に載せる
    （列 `作図オブジェクト`。XML には円の中心・半径が残らないため）。実測例:
    `c = 中心 (0, 0), 半径 3 の円（円）`。
  - 実行に失敗したら、**実行できなかった行と理由**（列 `失敗の内容`）を付けて同じ指示をもう一度だけ送る
    （＝自動修正。新しいステップとして「AI が修正」と出す。無限に呼ばないよう 1 指示 1 回）。
  - 失敗の理由には「作図に無い名前」も足す（GeoGebra のエラーだけでは名前の作り話に気づけない）。

## 为什么 AI 画図助手の窓は「大きさだけ覚える」（位置は毎回左の入力欄の位置）

- 利用者の指示: 窓を動かして閉じても、**次に開くときは必ず左の入力欄（図形名）の位置**に出してほしい。
- 前は位置と大きさの両方を localStorage（`study21.geometry.aiAssist.window.v2`）に覚えていたため、
  動かした場所のまま開いていた。→ **位置は覚えない**（開くたびに既定＝左の入力欄の左上へ）。
  保存するのは大きさだけにした（右下の把手で変えた大きさは今までどおり次も同じ）。
- 既定の位置は「左の入力欄の矩形」に合わせる（`defaultAssistWindow`）。入力欄を隠しているときは
  作図エリアの左端に寄せる。窓が画面からはみ出さないよう、位置と大きさは必ず画面内へ収める
  （大きくしたまま開くと上端が図形名より上へ寄るのはこのため）。
- 開いている間は今までどおりつまんで動かせる（覚えないだけ）。
- 実測（実機）: 既定で窓 (293,160) ＝ 左の入力欄 (293,160) に一致。420px 動かして閉じ、開き直すと
  **(293, 66)** ＝左の列に戻る（大きさを 1002 に広げていたため、上端だけ画面内へ寄る）。
  localStorage の値は `{"width":480,"height":1002}` で位置を含まない。

## 为什么【終了】のあとに届いた分塊を受け入れ、画面は送り終わるまで待つ

- 利用者の報告: 授業録音で `POST /classroom/{id}/chunks?seq=N` が **409（Conflict）** になった。
- 実測（DB）: 19 秒の録音・8 秒の録音は**音声が 1 バイトも残っていなかった**（24 秒の録音も最初の分塊だけ）。
  `MediaRecorder` の最後の分塊は `stop()` の**あと**に `ondataavailable` で届くので、画面が
  「停止 → すぐ【終了】」と送ると、サーバーは先に録音を終わらせ（状態 STOPPED）、
  あとから届いた分塊を「録音中ではありません」で弾いていた。
- 対策は 2 つ（両方入れた）:
  1. **画面**: 【終了】の前に**最後の分塊を送り終わるまで待つ**（`stopRecorderAndFlush`。
     `stop` イベント → 送信チェーンの完了まで待ってから `POST /end`）。
  2. **サーバー**: 停止直後（既定 10 分以内）に届いた分塊は**音声だけ保存して受け入れる**
     （`isLateChunkAllowed`。書き起こしはしない＝録音は終わっていて最終まとめも作られている）。
     古い記録への誤った追記は 10 分の猶予で防ぐ。
- 併せて、STT の接続情報の解決を「終了後の分塊を返す」より後ろへ移した（設定が不完全でも音声は残せる）。

## 为什么書き起こしを「実際の経過秒」にし、阿里をストリーミングにした

- 利用者の報告: ①文字が出るのが遅すぎて「話しながら出る」になっていない ②一覧の時刻が
  `00:00 / 00:20 / 00:40 / 00:15 / 00:20 …` と**時系列が壊れている**。
- ②の原因は**時刻の計算**だった: サーバーが `開始 = (連番-1) × そのときの 分塊の長さ設定` で計算しており、
  録音中に設定（20→5 秒）を変えると 2 本の時間軸が混ざる。→ 画面が**実際に測った経過秒**
  （`startSeconds` / `endSeconds`）を `/chunks` に載せ、サーバーはその値を使う（無ければ従来の計算＝互換）。
- ①の原因は**方式**だった: 1 分塊（5 秒）ごとに 1 往復する作りのため、話してから出るまで
  分塊の長さ＋往復ぶん待たされた。→ **録音 1 回 = WebSocket 1 本**の常連セッション
  （`DashScopeAsrClient.Stream`）にし、画面は 500ms ごとに 16kHz PCM を送り、
  `interim`（未確定の文）を 1 行で出し、確定した文だけをセグメントとして保存する
  （`POST /classroom/{id}/stt/stream` と `/finish`。使えるのは阿里巴巴のときだけ＝`options.streamStt`）。
- 併せて **空の認識結果はセグメントにしない**（`（聞き取れませんでした）` の埋め草をやめた。
  文字数と AI まとめを汚していた）。`language_hints` は**その授業の言語モード**から決める。
- 実測: 実サービスへ 500ms ずつ 8 フレーム送って `task-finished` を確認
  （`tmp/e2e/check-alibaba-stt-stream.mjs`）。実音声での文言確認は利用者のマイクで行う（この検証環境に TTS が無い）。

## 为什么オンライン授業は「マイク＋PC の音」を混ぜて録る

- 利用者の要望: 対面は今までどおりマイクだけ。腾讯会议・ブラウザの網課では**PC が再生している先生の声**も
  録って、書き起こしと AI ノートに使いたい（ヘッドホンだとマイクには先生の声が入らない）。
- 方式: 純ウェブ（Chrome / Edge on Windows）。録音の音源を 3 つから選ぶ:
  `mic`（対面）／`mic-screen`（会議）／`mic-tab`（ブラウザの網課）。
  二音源のときは `getDisplayMedia` で**タブの音声**（画面全体ならシステム音声）をもらう。
- **本当に混ぜる**（`src/features/classroom/audio-graph.ts`）: マイクと共有音声をそれぞれ `GainNode` で
  調整し、`DynamicsCompressorNode` で軽く抑えてから `MediaStreamAudioDestinationNode` へ。
  録音（`MediaRecorder`）と書き起こし用 PCM（AudioWorklet）は**混ぜた後**から取る。
  単に 2 本のトラックを 1 つの `MediaStream` に入れるだけでは混ざらない（片方しか聞こえない）。
- **戻さない**: 混ぜた音を `context.destination`（スピーカー）へつながない＝会議相手へのハウリング防止。
  共有の音も `suppressLocalAudioPlayback: true` でマイクへ回さない。映像トラックは共有を続けるために
  保持するだけで、**保存も送信もしない**（混ぜるのは音声トラックだけ）。
- **黙って片側に落とさない**: 共有で音声トラックが来ない（「タブの音声を共有」のチェック忘れ）／
  共有をキャンセルしたときは、**録音を始めない**（「録音中」にしない）。理由を日本語で出し、
  【共有を選び直す】で録音を止めずに遠隔音だけ入れ替えられる（`replaceRemote`）。共有が終了したときも
  知らせる（`track.onended`）。
- 音量はマイク／網課で**別々のレベル表示**を出す（どちらが入っていないか目で分かるように）。
- 書き起こし: 二音源では**サーバー書き起こし**を使う（ブラウザの Web Speech API は混ぜた音を取れない）。
  阿里巴巴なら J-2 のストリーミングで「話しながら文字が出る」。
- 実装: `audio-graph.ts`（7 テスト）＋ `ClassroomLiveView.vue`（モード選択・レベル・共有の取り直し）。
  画面テストで「音声付きの共有→録音開始」「音声なしの共有→開始しない」「共有キャンセル→開始しない」を固定。

## 为什么取込みは「名前」だけでなく「中身」も見る

- 起こったこと: 文字のテキストを `.mp3` に変えたファイルを【音声ファイル】で送ると、
  画面の事前チェック（拡張子と `audio/mpeg`）もサーバーの検査も通り、**書き起こしも再生もできない
  音声**として保存された（実測）。利用者からは「取り込めたのに何も出ない」としか見えない。
- 直し方:
  - 画面: `Audio` で長さが読めないファイルは**音声ではない**として断る
    （「この音声ファイルを読み取れませんでした（mp3 か確かめてください）」）。
  - サーバー: 先頭が ID3 タグか MPEG のフレーム同期（`0xFF`＋上位 3 ビット）でなければ断る
    （`ClassroomServiceImpl.looksLikeMp3`。厳密なデコードではないが、名前だけ mp3 のファイルを防ぐ）。
- 90 分の上限は画面（`Audio.duration`）とサーバー（`durationSeconds`）の両方で見る。

## 为什么「授業録音」の読み出し列を書き忘れると画面が黙って空になる

- 起こったこと: 科目（`CR_授業記録情報.科目`）を足したとき、`INSERT` と `resultMap` は直したが
  **`ListColumns`（一覧・詳細の SELECT 列）に足し忘れた**。DB には入っているのに API は常に
  `subject = null` を返し、画面の科目バッジが出なかった（実機 E2E で発覚）。
- 学び: MyBatis の「列を並べる SQL」は**書き忘れても例外にならない**（`null` になるだけ）。
  列を足すときは ① `INSERT` ② `resultMap` ③ `ListColumns` ④ `AllColumns` ⑤ init SQL の 5 箇所を
  一度に直す。画面テストは API をモックするので**この種の欠落は実機 E2E でしか出ない**
  （`tmp/e2e/check-classroom-new-lesson-e2e.mjs` が科目を確認する）。

## 为什么録音の音源（マイクのみ／マイク＋PC の音）を覚えておく

- オンライン授業が続く週は、毎回「マイク＋タブの音声」を選び直すのは手間（選び忘れると
  先生の声が録れない）。選んだ音源を `localStorage`（`study21.classroom.audioMode`）に覚え、
  次に開いたときは同じ音源で始める。知らない値・読めない環境では今までどおりマイクのみ。

## 为什么授業を始める設定（音源・前置詞）は【新しい授業】でまとめて選ぶ

- 利用者の指示（3 点）:
  1. 【録音する音源】の選択を**録音中の画面から【新しい授業】へ移す**
  2. 【新しい授業】に**前置詞（シナリオプリセット）の選択**を足す
  3. 録音中の画面へ入ったら**共有の選択を出し、選んだらそのまま録音を始める**。
     【15 秒だけ試し録り】は**やめる**
- 理由: 録音中の画面で音源を選ぶと、**録音を始めたあとでは変えられない**（`disabled`）のに
  目の前に選択がある＝「変えたつもり」を招く。授業を始める前に決める設定（授業名・科目・
  言語モード・前置詞・音源）は**1 か所（一覧の dialog）にまとめる**ほうが迷わない。
  前置詞は AI ノートの整理方針を決めるので、これも録音前に選ぶ。
- 実装:
  - dialog: 前置詞（`GET /classroom/presets`。読めなければ画面の初期値＋理由）と、
    **録音するときだけ**音源（`AUDIO_MODE_LABELS` の 2 択＝下の「音源を 2 つに統合」）を出す。音源の記憶
    （`study21.classroom.audioMode`）の読み書きは dialog が行う
    （`features/classroom/audio-graph.ts` の `loadAudioMode` / `saveAudioMode` に共通化）。
  - 録音中: 音源は `?audioMode=` で受け取り（知らない値は前回の選択→マイクのみ）、
    `autostart=1` で**入ると録音を始める**。二音源なら `getDisplayMedia` →
    音声が取れたら録音開始、取れなければ**始めない**（理由を日本語で出し、やり直せる）。
  - 試し録りは UI・コード・テストとも削除（同じ確認は**録音中の音量表示**＝マイク／網課の
    レベルで行う）。選択の欄は録音中の画面に置かず、音量表示と【共有を選び直す】だけ残す。
- 併せて、入口が dialog になって到達できなくなっていた**新しい授業の専用ページ**
  （`/classroom/new`・`ClassroomNewView.vue`）と、そのルート・テストを削除した
  （同じ設定が二重に育つと、どちらが本当か分からなくなる）。
- 検証: 画面テスト（`tests/classroom-ai.spec.ts`「授業一覧」「録音中」）＋
  実機は `tmp/e2e/check-classroom-new-lesson-e2e.mjs` と `tmp/e2e/check-dual-source-e2e.mjs`
  （後者は「共有を選ぶと自動で始まる」「保存された音声に両方の音が入っている」を見る）。

## 为什么二音源は「音が消えない」「マイクだけ書き起こさない」ようにしたか

- 利用者の報告（実機・3 点）:
  1. 音源＝マイク＋ブラウザ TAB で録音を始めると、**それまで聞こえていたブラウザの音が聞こえなくなる**
  2. 書き起こしが**マイクの音しか拾わない**（ブラウザ側で再生している先生の声が文字にならない）
  3. 【マイク＋タブの音】と【マイク＋画面共有の音】は利用者から見て**操作が同じ**（共有の選択で選ぶ）
     → 1 つにまとめて【マイク＋スピーカー（オンライン授業）】にする
- ①の原因は `getDisplayMedia` の **`suppressLocalAudioPlayback: true`**（共有した音のローカル再生を止める指定）。
  ハウリング防止のつもりだったが、この機能は**授業を聞きながら録る**使い方なので、聞こえなくなると成立しない。
  → **`false` に変更**（共有した音は今までどおり聞こえる。混ぜた音を `context.destination` へつながない
  方針は変えない＝アプリから音を戻さない）。スピーカーで聞くとその音がマイクにも入るため、
  画面では**ヘッドホン**を勧める。
- ②の原因は**2 つ**あった。
  1. **認識の方式**: ブラウザ認識（Web Speech API）はマイクからしか音を取れない
     （ストリームを渡す口が無い）。二音源＋ブラウザ認識では、スピーカーの音は**原理的に**文字にならない。
  2. **書き起こし用 PCM が二音源のときだけ取れていなかった**（コードの不具合）。
     `startPcmCapture` が**別の `AudioContext`** を作って、混ぜているコンテキストの節点へ
     `connect` していたため `InvalidAccessError` になり、例外を握りつぶしていた
     （実測: サーバー認識でも `POST /stt/stream` が 0 回・分塊 STT は保存した webm で代用）。
     → `tap.context`（混ぜているコンテキスト）を使い、PCM の取り出しとミキサーを同じ
     コンテキストに載せた。併せて、用意できなかったときは**黙って続けず**画面で知らせる
     （`data-cr-pcm-notice`）。さらに混ぜる仕組みの `AudioContext` を閉じ忘れていたのも直した。
     **テストで固定**: 「PCM の取り出しはミキサーと同じコンテキストで作る」を画面テストで見張る
     （別コンテキストに戻すと落ちる）。実測は `check-dual-source-e2e.mjs` が
     `/stt/stream` の回数（14 秒で 12 回）と、サーバーの
     `classroom stream stt opened ... provider=alibaba` で確かめる。
  - 対処 1（設定）: STT プロバイダーを**サーバー認識（阿里巴巴）**にした（`CLASSROOM_AI_STT_PROVIDER`）。
    画面は混ぜた音から 16kHz PCM を作って送るので、両方の音が書き起こされる
    （`startPcmCapture` の `tap`＝ミキサー。ストリーミング＝`/stt/stream` は録音 1 回に 1 本）。
  - 対処 2（画面）: それでも二音源＋ブラウザ認識の組み合わせは起こり得るので、**黙って半分を見せない**。
    【新しい授業】で二音源を選んだ時点で案内を出し、録音中は「ブラウザ認識（マイクのみ）」と表示、
    警告バー＋転写の【マイクのみ】バッジを出す（マイクの書き起こし自体は続ける）。
  - テストで固定: 「PCM の取り出し（AudioWorklet）は**ミキサー**につながっている（マイクの流れから
    取り直していない）」を画面テストで見張る（マイクから取る実装に戻すと落ちる）。
- ③: タブの音・画面共有の音はどちらも `getDisplayMedia` の共有で選ぶので、画面の選択を
  `mic` / **`mic-pc`（マイク＋スピーカー（オンライン授業））**の 2 つに統合した。統合前に選んだ値
  （`mic-screen` / `mic-tab`）は**「マイク＋スピーカー」として読み替える**（`localStorage` の記憶と
  その頃の URL が残っていても選び直させない。`toClassroomAudioMode`）。
- 実測（実機・ローカルスタック）: 共有の指定が `suppressLocalAudioPlayback: false` で取れること、
  自動開始で共有が 1 回だけ出ること、保存された音声に共有の音（1500Hz）が入っていること、
  終了後にマイクも共有も解放されることを `tmp/e2e/check-dual-source-e2e.mjs` で確認する。

## なぜ取り込んだ mp3 に「ファイル自身のサンプリング周波数」を宣言するか

- STT をサーバー認識（阿里巴巴）にした直後、**音声ファイル（mp3）の取り込みが 409 で失敗**した:
  `音声認識が失敗しました（FLOW:AUDIO_DECODE_ERROR）: Failed to decode audio: sample rate 16000
  not equals with real 44100`。
- 原因: `ClassroomSttAlibabaClient` が**画面の PCM と同じ 16kHz を常に宣言**していた。画面が送る
  ヘッダ無し PCM は 16kHz で正しいが、取り込む mp3 は 44.1kHz・wav は 48kHz など**ファイルごとに違う**。
  DashScope（Paraformer-Realtime-V2）は宣言した周波数と実際の音声が違うと**デコードを拒否する**
  （実測: `sample_rate=44100` なら成功、16kHz／未指定なら失敗。未指定は 16000 とみなされる）。
- 直し方:
  - **mp3 / wav はヘッダから読む**（`AudioFileSampleRate`。ID3v2 を飛ばしてフレーム同期を探し、
    MPEG のバージョンと周波数の番号から決める。wav は `fmt ` チャンク）。読めないときは
    `sample_rate` を**送らない**（分からない値を宣言しない）。
  - `DashScopeAsrClient` は `sampleRate <= 0` のとき `sample_rate` を付けない（今までは 16000 を入れていた）。
  - 画面が作る PCM（`audio/L16`）は今までどおり 16kHz を宣言する。
- 検証: `AudioFileSampleRateTest`（mp3 の ID3 有無・MPEG2、wav、読めない中身）＋
  `ClassroomSttAlibabaClientTest`（mp3 は 44100 を宣言／読めなければ付けない）＋
  実機は `tmp/e2e/probe-mp3-import.mjs`（409 → 200・音声は保存される）。

## 作図画面の「GeoGebra コマンド」欄を「いまの作図そのもの」にする理由と限界

- 症状: 図形管理【図形作成】の「GeoGebra コマンド」欄が**いつも空**。2.0 では貼り付けて実行する
  入力欄だったので、作図の状態を表す仕組みが無かった（実行後に作図から読み直すこともしていなかった）。
- 実機で確かめたこと（GeoGebra **5.4.920.0**・`https://www.geogebra.org/apps/deployggb.js`・
  `language: 'ja'`。調べ方は `tmp/e2e/probe-ggb-*.mjs`）:
  - `getDefinitionString()` は**日本語の説明文**（例「中心 A で, 点 B を通る円」）でコマンドに使えない。
    `getCommandString()` が返す `Circle(A, B)` / `Point(c)` / `Midpoint(A, B)` を使う。
  - `getAlgorithmXML()` は `<command name="…"><input …/><output …/></command>` を返す。
    **どのコマンドが何を作るか**が正確に分かる（多角形の辺は `output` に並ぶので行にしない。
    `getSiblingObjectNames()` も同じ組を返す）。
  - `getAllObjectNames()` は**作図した順**（依存の順）で返る。
  - **ドラッグした自由点は `getCommandString()` が空になる**（座標だけが残る）。道具で置いた点も同じ。
  - グラフの関数（`f(x) = x^2`）もコマンド文字列を持たない（値の文字列が定義になる）。
  - **スライダ・チェックボックスはコマンド文字列を持たない**（XML にも増分が無い）ので再現できない。
  - 【元に戻す】【やり直し】は `client:undo` / `client:redo` の通知を出す（取り消しにも追随できる）。
- 決め方:
  - 書き出しは `frontend/pc-web/src/features/geometry/construction-commands.ts` の**純関数**
    （`exportConstructionCommands(api)`）に置く。画面は読むだけなので同期のループにならない。
  - 欄は**いまの作図**を出す（AI が返した行や打ち込んだ行を並べない）。同期は 300ms まとめて
    （ドラッグ中は更新通知が連続するため。読むだけなので作図 120 個で 3ms 程度）。
  - 利用者が**編集中の内容は自動同期で上書きしない**。欄の下に「現在の作図：N コマンド」を常に出し、
    【作図の内容に戻す】で戻せる（編集中の入力と作図の状態を混ぜない）。
  - **コマンドにできない作図は黙って落とさず**、欄の下に件数と理由を出す（完全に同期したようには見せない）。
- 再現できない（＝欄に出さない）もの: スライダ・チェックボックス、それらに依存する作図、
  `x = 1` のような**定義そのものを書く作図に依存する**作図（名前が GeoGebra 任せになるため）、
  画像などコマンドを持たない作図。多重出力（交点 2 点）は `Intersect(c, f, 1)` のように
  添字つきで書き出す（実機で往復を確認）。多角形が作る辺は `Polygon(A, B, C)` の 1 行に含まれる。
  ドラッグした自由点の座標は小数 6 桁で丸める（見やすさのため。作図そのものは変えない）。
- 検証: 単体（`tests/geometry-construction-commands.spec.ts`・実機で取った値を使う）＋
  画面（`tests/geometry-draw.spec.ts`）＋実機（`tmp/e2e/check-command-sync-e2e.mjs`。
  書き出したコマンドを**空白の作図で組み直し**、名前・種類・定義コマンド（＝関係）が一致すること、
  「点は円の上」の関係が生きたままであることを確かめる）。

## なぜ分塊の書き起こしが失敗しても音声を捨てないか

## なぜ書き起こしの接続が切れたら自動でつなぎ直すか

- 利用者の報告（実機）: 「一出错，屏幕上原有识别出的内容就消失了」。
- 何が起きていたか: ストリーミング書き起こしが（認識側の失敗で）一度止まると、**その録音の残りは
  一切書き起こされなかった**（サーバーのセッションは切れたまま）。加えて、画面に出ていた
  **未確定の文（interim）は停止時に消える**ので、利用者からは「認識した内容が消えた」ように見えた。
  さらに案内を `syncError` に書いていたため、**ポーリングが成功するたびに案内が消えていた**（実測）。
- 直し方:
  - 認識側の失敗では**すぐ諦めない**。セッションを閉じて 2 秒後に**つなぎ直す**（最大 3 回）。
    成功したら回数を戻す。3 回失敗したら理由を出して停止する（**録音した音声は保存されている**旨も書く）。
  - 案内は `syncError` と**別の枠**（`data-cr-live-stt-notice`）に出す（ポーリングの成功で消えない）。
  - 録音の開始・停止で回数を 0 に戻す（`stopSttStream` では戻さない＝戻すと「何回失敗しても 1/3」になり
    永遠に諦められない。実装中に踏んだ罠）。
- 検証: 画面テスト 2 件（つなぎ直して続ける／数回で諦めて理由を出す）。

## なぜ書き起こしの音声を 100ms ずつ送り、画面側にも上限を置くか

- 利用者の報告（実機）:
  1. **先に録音を始めて、あとからブラウザの別タブを再生すると、何も書き起こされない**
     （先に再生してから録音すると書き起こされる）
  2. 別タブの音は書き起こされるが、マイクの声が書き起こされない
- 実測（本物の日本語音声＋本物の阿里巴巴で再現）: サーバーのログに
  `classroom stream stt failed ... 音声認識との接続が切れました（1009: Max frame length of 262144
  has been exceeded.）`。**1 回の送信（WebSocket の 1 フレーム）が DashScope の上限 256KB を超えると
  セッションが切られ、以降は何も書き起こされない**（256KB ＝ 16kHz 16bit で約 8 秒）。
  - 画面は 500ms ごとに送るが、**前の送信が終わるまで次の送信をしない**（`streamSending`）。
    往復が遅い／音が長く続くと、貯まった音が 1 回でどっと送られ、8 秒を超えたところで切断。
  - 「先に再生してから録音」だと最初から音があるので貯まりにくく、
    「先に録音して後から再生」だと**無音の間に貯まって**最初の送信で切れる、という差になっていた。
  - 授業の途中で切れる（＝途中まで文字が出て、あとは出ない）のも同じ原因。
- 直し方:
  - サーバー（`DashScopeAsrClient.Stream.send`）: **1 フレーム 3200 バイト（100ms）ずつ**に分けて送る
    （batch 側と同じ。`java.net.http` の WebSocket は同時に 1 送信しか許さないので、1 枚ずつ待つ）。
  - 画面（`ClassroomLiveView.takeSttFrame`）: 送る前に**直近 2 秒だけ残して古い音を捨てる**
    （`PcmChunkBuffer.trim`）。遅れが溜まっても 1 回の送信が膨らまず、書き起こしが遅れ続けない
    （そのときは画面に「古い音を飛ばして続けます（録音には全部入っています）」と出す）。
  - 文字が消えない工夫（前の項のつなぎ直し・案内の分離）はそのまま。
- 検証: `tmp/e2e/check-two-source-stt-order.mjs`（**本物の日本語音声**を偽マイクと共有の音に流し、
  本物の阿里巴巴で書き起こす）。①先に録音して後から再生 → 音が始まった後で書き起こされる、
  ②最初から両方鳴っている → マイクの声も共有の音も書き起こされる、を確認。
  時間計測は `node /tmp/timing-probe.mjs` 相当（送信間隔が 500ms に戻ったこと）。

  - 送信は 250ms 周期・1 回最大 2 秒（小分け）。**送信と結果受け取りが直列で詰まらない**

- 画面: 話者（先生／学生／講義）を**色とラベルで分ける**（`cr-transcript__line--teacher/student/lecture`）。
  途中の文（interim）も**音源ごとに 1 行**出し、音源ごとの案内（送信失敗・欠落区間）を別々に出す。
- 検証: `classroom-source-stream.spec.ts`（6 件: 音源ごとの URL・失敗したら同じ音を送り直す・
  貯めすぎたら欠落を記録・1 回の送信は上限まで・停止は「送り切る→/finish」・2 音源が独立）＋
  画面テスト（音源ごとの interim・送信失敗時の案内・停止と終了の收尾が二重に走らない）＋
  実機（`check-dual-source-e2e.mjs` が通し・`check-two-source-roles.mjs` が
  マイク＝学生／共有＝先生で保存されることを実 STT で確認）。

  まとめ作成中 → 完了。**％は出さない**（測れない進み具合を装わない）。失敗したら段階を
  「失敗」にして「もう一度【授業を終了】を押すと続きからやり直す」と出す（音声は保存済み・
  `/finish` は冪等なので、押し直しで安全に再開できる）。
- 画面の並び順（利用者の指示 3-4）: 転写は**実際の発言開始時刻**で並べ（`orderedSegments`）、
  遅れて届いた文も正しい位置へ入れる。同時刻は連番で安定させ、**同時発言の時間の重なりは消さない**。

  「先生」扱いになる。この制限と**イヤホン**の案内を録音中の画面にも出した

  二重に認識しない＝冪等）。応答に `processedFrames`（処理し終えた番号）を返すので、
  画面はそこから続きを送ればよい。番号を渡さない HTTP の分塊送信は到着順に採番する（互換）。
- **WebSocket エンドポイント**を追加した（後端）: `spring-boot-starter-websocket` を足し、
  `/api/user/classroom/{recordId}/stt/socket?source=mic|shared` を用意
  （`ClassroomSttSocketConfig` / `ClassroomSttSocketHandler`）。
  - 認証は**ハンドシェイクの HttpSession**（`SPRING_SECURITY_CONTEXT`。`AccountController` が
    ログイン時に入れている）から利用者を取り出す。**未ログインは接続させない**。許可元は HTTP の
    CORS と同じ設定（`study21.cors.allowed-origins`）を使う。API Key は画面へ出さない。
  - やり取り: 画面→サーバーは**バイナリ**（100ms ＝ 3200 バイトの 16kHz PCM）、
    サーバー→画面は `{"type":"result", interim, added, error, processedFrames}`。
    接続の最初に `{"type":"resume","from":N}` を送れば番号を数え直せる（断線復帰）。
    `{"type":"finish"}` で終了（最後の確定文を返して閉じる）。**音源ごとに別の接続**。
  - ソケットが切れても**認識セッションは閉じない**（張り直した接続で続きを送れるように）。
  - 依存の入手: オフラインのローカルリポジトリに `spring-boot-starter-websocket` /
    `spring-websocket` / `spring-messaging` を追加した（配備側の Docker ビルドはネットワークから取得する）。
- **画面側も WebSocket 送信に切り替えた**（`SourceStream`）: 音源ごとに 1 本の接続を開き、
  **100ms（3200 バイト）のフレーム**を番号付きで送る。接続の最初に `{"type":"resume","from":N}` を送り、
  未確認のフレームを送り直す（断線しても**同じ音を二重に認識しない**）。`{"type":"finish"}` のあとは
  `finished`（最後の確定文）を待ってから終わる。
  - **接続できないときは HTTP へ退避する**（書き起こしを止めない）。判定は 2 つ:
    接続が開かないまま **1500ms**（`socketConnectTimeoutMs`）経ったとき、および張り直しが
    5 回（`maxReconnects`）を超えたとき。どちらも画面に理由を出す（録音は続いている）。
  - 送れないまま溜まった音は **60 秒**を上限に保持し、溢れた区間だけを `MissingRange` として
    「欠けた区間」に記録する（**黙って捨てない**）。
- **仲介（プロキシ）の設定が要る**（実測で見つけた落とし穴）: 常時接続は**経路の途中で
  昇格（Upgrade）が通らないと成立しない**。画面は接続できないと HTTP へ静かに退避するので、
  設定漏れは「なんとなく遅い」という形でしか現れない（気づきにくい）。
  - `deploy/docker/nginx.conf`: `/api/user/` に `proxy_http_version 1.1` と
    `Upgrade` / `Connection`（`map $http_upgrade $connection_upgrade`）を追加した。
    これが無いと、配備した環境では常時接続にならない。
  - ローカル検証用の `tmp/e2e/vite.stt-e2e.config.ts` にも `ws: true` が要る。
  - 実測（本物の認識・実音声・30 秒）: **設定前**は接続が開いても音声フレームが 1 つも
    流れず（`wsFrames: 0`）HTTP 送信 22 回へ退避。**設定後**は
    `wsFrames: 406`（3200 バイト×406 = 1,296,944 バイト ≒ 40.5 秒ぶん＝音源 2 つ×20 秒）で
    HTTP 送信 1 回。遅延の比較（HTTP 対 WS）は**まだ測れていない**: 下の周期の不具合で
    送信量が実時間に足りず、条件が揃っていなかったため。
- **1 周期に送る量の不具合**（実測で見つけた・修正済み）: 常時接続では 100ms のフレームを
  **1 周期に 1 個**しか送っていなかった。周期は既定 250ms なので、**実時間の 4 割**しか届かない
  （実測: 20 秒の録音で 84 フレーム＝8.4 秒ぶん）。マイク側は「発話が後半にある仕込み」だったため
  音声が届かず、**書き起こしが 1 文字も出なかった**（共有側は前半に発話があるので出ていた）。
  周期ぶん（`ceil(周期数 × 周期長 ÷ フレーム長)`）を送るようにし、1 周期の上限だけ設けた
  （`MAX_FRAMES_PER_TICK`＝50）。修正後は 20 秒の録音で **20.4 秒ぶん（マイク）/ 20.3 秒ぶん（共有）**
  が届く（＝実時間どおり）。回帰テストはフレーム数を数える（旧挙動に戻すと 4 個で落ちる）。
- **「マイクの書き起こしが出ない」の原因（切り分けて解決）**: 画面が送った PCM をそのまま取り出し、
  **同じ音を直接認識にかけた**ところ「ありがとう、ありがとう…」（8.14〜14.34 秒で確定）と正しく
  認識された＝**捕まえた音は正しい**。原因は次の 3 つが重なっていた。
  1. **送信量**（上の周期の不具合）で、実時間の 4 割しか届いていなかった。
  2. **尾部の確定文**は停止のあとに届く（実測: マイクは約 14 秒後、共有は 60 秒近くかかることも）。
     画面は終了を待たずに詳細へ移っていたため、その文は詳細に間に合わなかった。
  3. 記録が消えたあとに届いた文の保存が**外部キー違反で例外になり、WebSocket が 1011 で閉じて
     そのあとの文も全部落ちていた**（検証では記録を先に消していたため、この 3 が重なって
     「マイクは 1 文字も残らない」になっていた）。
  対策: (a) 1 文の保存に失敗しても**セッションを殺さない**（警告ログ＋画面へ理由。音は録音に残る）、
  (b) 【終了】は**尾部の確定文を待ってから**記録を終える。ただし待ちすぎない（上限 15 秒。
  待ち切れなくても記録は消さないので、あとから届いた文はそのまま保存される）。
  実測（本物の認識・20 秒）: `source=mic speaker=学生 key=mic#1#1 start=8.140`（仕込みは 8.0 秒）、
  `mic#1#2 start=20.720`、`source=shared speaker=先生` も保存＝**音源別のロールと音声クロックの
  タイムラインが実音声で通った**。
- **実音声での前後比較（HTTP 対 WebSocket。同条件 20 秒・同じ仕込み・本物の認識・各 1 回）**:
  測った値は `tmp/e2e/stt-measure-report.md` に残す。**結論として言えることと言えないことを分ける**。
  - 言える: どちらも**音を実時間どおり送れている**（WS は 100ms フレームで マイク 17.5 秒／共有 17.0 秒。
    HTTP は分塊で 1 音源あたり約 16〜17 秒ぶん）。**欠けた区間 0・重複 0・保存失敗 0**。
    音源別ロールと音声クロックのタイムラインも両方式で一致（マイク 8.12 秒＝仕込み 8.0 秒、
    共有 0.56 秒＝仕込み 0.5 秒）。HTTP の要求回数 52 に対し WS は 5（常時接続なので往復が減る）。
  - **言えない: 「WS の方が遅延が小さい」**。各方式 3 回ずつ測った（計 6 回、`tmp/e2e/measure-repeat.log`）:
    最初の途中経過は HTTP 3.7 / 4.7 秒（1 回は測れず）、WS 3.8 / 10.7 秒（1 回は測れず）。
    最初の確定文も HTTP 8.8 / 10.6 秒、WS 5.5 / 17.0 秒。**範囲が重なっていて方式の差は確認できない**
    （1 回だけの測定では向きが逆に出ることもあった）。毎回そろって出たのは
    **停止→收尾完了が HTTP 約 16.4 秒・WS 約 17.6 秒**で、これは尾部の確定文を待つ上限と
    後端の尾部処理の時間であって、通信方式の速さではない。
  - **毎回そろって確認できたこと（6 回すべて）**: 欠けた区間 0・重複 0・保存失敗 0。
    マイクのタイムラインは 8.10〜8.12 秒（仕込み 8.0 秒）、共有は 0.56 秒（0.5 秒）。
    WS は 1 回あたり 340〜360 個の 100ms フレーム＝実時間どおり、HTTP は 17〜26 回の送信。
  - **残る限界（次の段で扱う）**: マイクの確定文は**尾部でしか出ない**ことが多く、
    6 回のうちマイクの文が残ったのは 4 回（WS 3/3、HTTP 1/3）。停止後 20 秒ほど遅れて届くため、
    詳細画面に出るまでに間がある。確実に残すには尾部の取りこぼし対策（補書き起こし）が要る。
- **フレームの識別を常時接続と HTTP で統一した**（画面は両経路で同じ欄を送る）: 常時接続は
  バイナリの前に**見出しのテキスト** `{"type":"frame","no":N,"startSample":S,"sampleRate":16000,
  "source":…}`、HTTP は `?source=…&frameNo=N&startSample=S`。後端は**到着順に採番しない**ので、
  張り直し・経路の切り替え・後端の再起動でも同じ音が同じ識別になり、二重に認識しない
  （見出しの無いフレームだけ到着順に採番＝古い画面の互換）。
  - `startSample` は**録音の先頭からの絶対位置**（16kHz のサンプル数）。文の時刻は
    「**その認識セッションの開始位置**（最初に流したフレームの `startSample`）＋阿里雲の
    `begin_time`」で決める（`begin_time` はセッションの音声の先頭からの位置なので、足すのは 1 回だけ）。
    したがって非 0 の位置から続けても時刻が 0 に戻らない・詰まらない。`resume` の換算は
    **位置を送らない古い画面のための互換**として残す。位置は前へしか進めない
    （すでに処理した位置より古いフレームは流し直さない）。
  - 受け取り確認（`processedFrames`）は**保存できたところまで**しか進めず、
    **認識そのものが失敗した回（`task-failed`）も進めない**（進めると画面がその音を捨て、
    書き起こしに残らない区間が確定する）。
- **次の段**: 実音声での通し確認（実 Alibaba・ローカル画面）と HTTP との遅延比較、
  補書き起こし（欠けた区間を録音から後追いで認識して重複を統合）、
  hotwords / 文の区切り / 心拍の調整、参照音声での前後比較の量測レポート。

## なぜ AI 生図を「作図方法 A〜D」と「作成する図の種類」に分けるか（2026-09-18 改修 第 1 段）

利用者の指示: 「AI 生成の責務を 4 つのバッチ（batC51-A 画像をもとに再現 / batC51-B 数式からグラフ /
batC51-C 文章の条件から作図 / batC51-D 文章と図を合わせて作図）に分ける。1 回の要求で実行するのは
利用者が選んだ 1 つだけ。モード（入力をどう読むか）と結果種別（何を作るか）は**別**に扱う」。

- **モードと結果種別を混ぜない**。A・C・D は「画像から」「文章から」「文章と図から」という
  **入力の読み方**であって、幾何だけに限定されない（関数・方程式のグラフも、混在も作れる）。
  「何を作るか」は `結果種別`（AUTO / GEOMETRY / GRAPH / MIXED）が決める。B（数式からグラフ）だけは
  画面で選ばせず **GRAPH に固定**（サーバーでも `AUTO` を `GRAPH` へ寄せる）。
- **連字符つきの接尾辞を使う**（`batC51-A`〜`D`）。`BAT_バッチコントロール情報` と
  `BAT_バッチ実行履歴情報` の バッチコード は `VARCHAR(20)` で、既に `batC15-1`〜`3` の前例がある。
  Spring のハンドラも `taskCode()` で引くだけなので、追加の対応表は要らない（`FigureBatchRegistrationTest`
  で 4 つが別々に登録されることを固定した）。
- **歴史的な batC51 は A として扱う**（モード欄が無い要求・実行履歴）。結果種別は当時の
  `利用者区分`（FIGURE → GEOMETRY / FUNCTION → GRAPH / MIXED → MIXED）から読み替える。
  ※ このうち **裸の `batC51`（バッチコード）は 2026-09-19 に削除した**（下の項）。
  残るのは「`作図モード` が NULL の要求を A として扱う」規則で、こちらは今も生きている。
- **出力 DTO はモードごとに独立**（`BatC51AResultDto`〜`D`）。共通項目は `FigureOutputDto` が持ち、
  作図の構造（点・線・円・関数・曲線・定義域・表示範囲）は `FigureParts` に集約する。
  プロンプトの「出力形式」も設定ページの Data TAB も**この DTO から生成**する（定義を書き写さない）。
- **AI の「判定」は実行・検証・保存の結果ではない**。`GENERATABLE` でもコマンドが方針に合わなければ
  検証で落ちるし、`NEEDS_INPUT` / `UNSUPPORTED` はコマンドが空で正常なので**再質問しない**
  （無駄な課金を避ける）。種類の食い違いは**黙って切り替えず**質問を返す（`NEEDS_INPUT`）。
- **実行はバックエンドの働き手（admin-api の `GeometryAiWorker`）が行う**。要求行そのものを待ち行列にし、
  `FOR UPDATE SKIP LOCKED` で 1 件ずつ確保する（画面の追加入力に依存しない＝画面を閉じても続く）。
  `GENERATED`（検証待ち）は**検証だけ**を回す（生成からやり直すと AI を二重に呼ぶ）。
  **FAILED は自動で拾わない**（利用者の【もう一度生成】だけが再開する＝黙って課金しない）。
- **1 枚の画像は全モードで使う**。B・C でも画像の中の式・問題文を読むため、切り抜きの案内だけを
  モードごとに変える（B は式と定義域、C は問題文、D は文字と図の両方、A は図形全体と軸・目盛）。
- **補充パラメータはモードと種類に当てはまる項目だけを保存・送信する**（画面で隠れている項目や、
  モードを切り替える前に書いた項目は送らない）。サーバー（`GeometryAiSupplements`）でも同じ規則で絞る。
- **追加入力待ち・失敗は同じ要求行を送り直す**（`POST /requests/{id}/resubmit`）。行を増やさないので
  一覧に古いタスクと新しいタスクが二重に並ばず、図形も 1 つしかできない。
- **第 1 段の範囲**: 正式な図形の保存は今までどおり**作図画面の applet**が XML とサムネイルを作って行う
  （`READY` → 作図画面で確認 → 保存）。**サーバー側の制限付き実行・検証・XML 直列化・サムネイル生成は
  第 2 段**で入れる。それまでは「AI がコマンドを返した」ことを「実行・検証・保存できた」とは扱わない。

## なぜ書き起こしの入口・受け取り確認・発話キー・収尾を作り直したか（2026-09-19 改修）

利用者の指示: 「(1) 常時接続でも**同じ所有者確認**を通し、記録の状態も見る。(2) **保存できていない文の
位置を「処理済み」と言わない**（黙って成功にしない・有界でやり直す）。(3) 発話キーを**張り直し・再起動で
変わらない**ものにする。(4) 収尾（finish）も**サーバー側で状態と結果を見る**」。

- **入口の確認は HTTP と常時接続で同じ 1 か所**（`ClassroomService.requireSttAudioAccountId` /
  `requireSttFinishAccountId`。実装は `ClassroomServiceImpl.requireSttAccountId` が
  既存の `requireOwner` を再利用する）。状態を見る場所を 2 つ作らない（片方だけ直して食い違うのを防ぐ）。
  - **音声は「録音中」だけ受け取る**。常時接続は**接続時にしか認証しない**ので、接続後に録音が終わった
    記録へ音が流れ続ける（HTTP は 409 で止まるのに常時接続だけ素通りする）のを防ぐため、
    **フレームごとに**（接続時＋1 フレームごと）確かめる。主キー参照 1 回なので軽い。
    断った接続は覚えておき、閉じたあとに届くフレームでは DB を引かない・閉じ直さない。
  - **収尾（finish）だけは停止直後の猶予（既存の `LATE_CHUNK_GRACE`＝10 分）も受け付ける**。
    尾部の確定文は停止のあとに届くので、ここで断ると**その音源の最後の文が丸ごと残らない**。
    完了（COMPLETED）・古い停止・取消は収尾も断る（`finished` に理由を載せて返してから閉じる＝
    画面は `finished` 待ちなので、黙って閉じると成功に見える）。
  - 未ログインは今までどおり接続させない（ハンドシェイク＋ハンドラの両方で確かめる）。
- **受け取り確認（`processedFrames`）は「保存できたところ」までしか進めない**。進めた番号までの音を
  画面は捨てるので、保存に失敗した文を含むフレームを「処理済み」と返すと**その音は二度と送られない**
  （＝書き起こしが消える）。したがって:
  - 保存は 1 文につき **3 回までやり直す**（50ms 待つ。一時的な接続断・デッドロック向け。無限には粘らない）。
  - それでも駄目なら**セッションは殺さず**（実測の 1011 で閉じる不具合を戻さない）、`error` に理由を返し、
    **`drained`（取り出し位置）とフレーム番号を進めない**。次の回に同じ文がもう一度取り出されて
    やり直され、画面が同じ番号を送り直しても**認識へは流し直さない**（音は 1 回だけ認識する）。
    同じ文は発話キーで UPDATE に寄るので**行は増えない**。
  - 1 つの悪い文でそのあとの良い文まで捨てない（保存は続ける。ただし「処理済み」にするのは
    途切れる前まで）。
- **発話キーは「音源#開始ミリ秒」（＝音声の位置）にした**。理由と代案の比較:
  - 旧: `音源#セッション番号#sentence_id`。**セッション番号はつなぎ直すたびに増える**ので、張り直し・
    再起動で同じ発話が別のキーになり、**同じ音が 2 行**になった（遅れて届いた重複が別の古い行を
    上書きすることもあった）。`sentence_id` もセッション内の通し番号なので単独では安定しない。
  - 代案の「記録×音源ごとの永続カウンタ」は**採らなかった**: 再送された文に新しい番号を振ってしまい、
    「同じ発話＝同じキー」を満たせない（重複が 2 行になる）。位置は
    「同じ音を送り直せば同じ位置」になるので、**重複の統合と一意性を同時に満たせる**。
  - 位置は「その音源へこれまでに送ったサンプル数 ＋ 阿里雲の `begin_time`」から決まる（画面の時計・
    到着順は使わない）。**後端を再起動したとき**は送ったサンプル数が 0 に戻るので、
    画面が断線復帰で送る `{"type":"resume","from":N}` の番号（100ms 固定＝3200 バイト）から
    位置を**前に進めるだけ**合わせる（`ClassroomSttStreamService.resume`）。これで再起動後も
    同じ発話には同じキーが出る。
  - 限界（正直に書く）: HTTP へ退避した送信（番号が無い）で後端を再起動した場合は、位置の基準を
    復元できないので古い位置から数え直す＝**重複した行ができる可能性が残る**。位置ベースなので
    既存の行を壊すことはない（キーが衝突するのは本当に同じ位置の同じ音源だけ）。
  - 一意性: 音源ごとに別の空間（`mic#` / `shared#`）で、文の開始位置は同じ音源の中で重ならない。
    秒の値（`開始オフセット秒`）と同じ計算からミリ秒を作るので、**キーと時刻が食い違わない**。
    同じ発話キーの INSERT が一意制約で弾かれたとき（HTTP の再送が重なった等）は、もう一度探して
    **UPDATE に寄せる**（行を増やさない・「保存できませんでした」にもしない）。
  - **スキーマ変更は不要**（`発話キー VARCHAR(160)` と `UK_CR_転写セグメント_発話キー` をそのまま使う）。
    既存行の旧形式キー（区切り 3 つ）は新形式（区切り 2 つ）と衝突しないので変換しない。
    DB のコメントだけ実態に合わせる移行を追加: `database/移行/MIG_CR_転写セグメント_発話キー音声位置_20260919.sql`
    （**未適用**。適用は利用者の判断）。
- **収尾（finish）はサーバー側で「成功と言ってよいか」を決める**（画面が待ったかどうかに頼らない）。
  `error` に理由を入れて返す（画面は `error` を案内として出す）:
  - 認識セッションが無い（＝2 回目の終了、または音を 1 つも送っていない）→ 理由を返す。**データは
    何も変えない＝冪等**（2 回呼んでも行は増えず、壊れない）。
  - 尾部を取り切れなかった（`DashScopeAsrClient.Stream.tailFinished()`＝`finish-task` のあと
    `task-finished` を時間内に受け取れなかった）→ 「遅れて確定した文は残らない可能性がある」と伝える。
    取れた文は保存する（捨てない）。
  - 保存できなかった文がある → 理由を返し、受け取り確認も進めない。
  - 状態の確認（録音中か・停止直後か）は**入口**（HTTP と常時接続の共通の確認）に置く。
    サービスは認識セッション側の状態（未保存の文・尾部の取り込み）を見る（サービスから
    `ClassroomService` を呼ぶと依存が輪になるため、判定の置き場を分けている）。

- 数据库表结构 / DDL / 索引 / 外键。
- 认证方案（登录方式、会话、Token）。

## 为什么 AI 生図のプロンプト変数をコード側に一本化し、共通＋モード別を連結するか（2026-09-19 改修）

**決めたこと**: プロンプトのテンプレート変数は **コードが唯一の定義**（`FigurePromptTemplate` /
`AiFigureSupplements` / `AiFigureSettingKeys`、いずれも common-core か admin-api の 1 か所）。
データベースの A〜D のテンプレートはその名前に合わせて移行する（逆はしない）。

**なぜ**:

- 画面に入っていた日本語のテンプレートは `{requested_output_type}` / `{user_note}` /
  `{allowed_commands}` / `{output_schema}` を使っていたが、**コードはこれらを知らない**。
  実行時に「知らない変数があります」で落ち、利用者から見ると「AI が動かない」にしか見えない。
  `{output_schema}` はさらに悪く、**サーバーが DTO から生成して末尾に足す Schema と二重**になる。
- 変数の説明（設定画面のヘルプ）・保存時の検証・実行時の展開が**別々の一覧**を持っていたので、
  どれか 1 つを直すと他が嘘になる。定義を 1 つにすれば、ヘルプ＝検証＝展開が必ず一致する。
- 補充項目（画面の任意項目）は**項目ごとに専用の変数**を持たせた（`{reproduceFocus}` `{domain}` …）。
  保存する JSON のキーは日本語の項目名で、その対応表も common-core に 1 つだけ置く
  （user-api が保存し、admin-api が展開するので、ずれると「選んだのに AI へ届かない」という
  静かな不具合になる）。

**System Prompt は連結する（モード別で上書きしない）**:

- 共通（`GEOMETRY_AI_SYSTEM_PROMPT`）＋モード別（`GEOMETRY_AI_<A〜D>_SYSTEM_PROMPT`）＋
  コードが持つ「モードの役割」「結果種別の守り方」＋DTO から生成した出力 Schema、の順に連結する。
- 上書きにすると、モード側が禁止事項・出力の約束を書き漏らしたときに**共通の規則が消える**。
  実際、共通の System Prompt はいつのまにか「コマンド列だけを出力」「1 行に 1 コマンド」
  「座標は -10..10」という、いまの JSON 出力と「利用者が座標の範囲を指定できる」という約束に
  **矛盾する文面**のまま残っていた（利用者の指定より古い指示が優先されかねない）。
- 共通の User Prompt（`GEOMETRY_AI_INSTRUCTION_TEMPLATE`）は**必須にしない**。
  モード別に書けばそれを使い、どちらも無ければ「テンプレート無し」で実行する
  （利用者の指定＝結果種別・補充・補足・名前の方針は、テンプレートの文面に関係なく必ず足す）。

**保存時に検証する**: 知らない変数を含むテンプレートは**保存させない**（`SettingValueValidator`）。
実行してから失敗するのではなく、保存した瞬間に理由と「使える変数の一覧」を返す。

## なぜ要求ごとに「有効な設定」を固定するか（2026-09-19 改修）

**決めたこと**: 要求の受付時（作成・送り直し・もう一度生成）に、共通 → モード別の継承を適用した
**有効な設定の本文**を `GEO_AI生図リクエスト情報.設定スナップショット` に固定し、働き手（worker）は
それをそのまま使う。スナップショットが無い（歴史的な）行だけ、いまの設定から解決して書き足す。

**なぜ**:

- 実行は画面からではなく**バックエンドの働き手**が後から行う。待ち行列に並んでいる間に設定を
  変えると、**利用者が見た条件と違う条件で AI が走る**（＝同じ操作なのに結果が変わる）。
  検証（許可コマンド・上限）も同じ版で行わないと、生成時と検証時で条件が食い違う。
- 旧版は**ハッシュだけ**を残していた（`systemPromptHash` など）。ハッシュでは
  「どの文面で作ったか」を読み返せず、復元もできない。**本文を残す**（秘密は入れない）。
  入れるのはプロンプト本文と、使うモデルのスロット・上限・出力形式・タイムアウト・再実行回数だけ。
  API Key と接続先 URL は `AI_MODEL` ページの設定で、要求行には**入れない**。
- 1 列（JSONB）に `config`（受付時に固定した本文）と `trace`（生成時に分かったこと＝使ったモデル・
  確定した結果種別・版のハッシュ）を入れる。`trace` を後から書いても `config` は上書きしない。

## なぜ検証（VALIDATING）を「確保した状態のまま」受け付けるか（2026-09-19 改修）

**決めたこと**: 待ち行列が確保に使う状態（`VALIDATING`）を、**検証工程の入口も受け付ける**。
`GENERATED`（検証待ち）／`VALIDATING`（確保した直後に落ちた残骸）／`FAILED(VALIDATE)` が対象。

**なぜ**: 旧版は確保のときに `VALIDATING` へ進めるのに、検証の入口は `GENERATED` しか
受け付けていなかった。そのため拾った行は**何もせずスキップ**され、次の周期でまた拾われ続け、
**後ろに並んだ要求がまったく進まなかった**（AI をもう一度呼ぶことはないが、時間だけ失う）。
「確保が使う状態」と「工程が受け付ける状態」は**同じ契約**でなければならない
（`AiFigureValidateStepTest` が両者を突き合わせて固定している）。

同じ理由で、**工程が想定外で止まったら要求行へ `FAILED` と理由を書く**（`AiFigurePipelineService`）。
設定の不足・プロンプトの変数展開の失敗・接続の解決の失敗は、工程の途中で例外になることがある。
処理中の状態（`PREPROCESSED` など）のまま残すと、働き手が**同じ行を拾い続けて後ろが進まない**。
「既に実行中」（`ConflictException`）だけは失敗にしない（走っている実行がその要求を進めるので、
あとから `FAILED` を書くと成功した結果を壊す）。

## なぜ「生成完了」と「保存完了」を分けるか（2026-09-19 改修）

**決めたこと**:

- `READY` の表示は**「生成済み・確認待ち」**（**まだ図形になっていない**）。
- `REGISTERED` が**「保存完了」**。一覧のカードの状態も `READY` と `SAVED` に分ける。
- `VALIDATING` は**「検証中」**（「検証・保存中」とは書かない）。検証はコマンドの規則
  （許可リスト・長さ・個数・文字種）を確かめるだけで、**保存はしない**。
- 検証が通ったときの文面も「コマンドの規則チェックに通りました。**数学的な条件の検証は
  行っていません**。作図画面で確認してください」にする。GeoGebra は作図画面のブラウザにしか
  無いので、サーバーは「図が数学的に正しいか」を確かめていない。
- ブラウザでコマンドを実行できなかったときは、理由をはっきり出して**【保存】させない**。
  失敗すると作図は元に戻るので、そのまま保存すると「AI の結果が入っていない作図」が
  **成功として登録**されてしまう（利用者から見ると成功に見える）。

## なぜ種別 C のバッチに【再実行】ボタンを出さないか（2026-09-19 改修）

**決めたこと**: バッチ一覧（`views/batch/BatchListView.vue`）で、**種別 C（呼出）の行には
【再実行】ボタンを出さない**（押せない灰色のボタンも残さない。操作の列は「—」）。
判定はバックエンドが行い、行の `canManualRerun`（＝`BatchTaskDefinition#canManualRerun()`）で返す。
`POST /api/admin/batch/tasks/{code}/rerun` も種別 C を拒否する。
行の `canRerun`（ボタンを押せるか＝業務処理のハンドラがあるか）とは**別のフラグ**にした。

**なぜ**:

- 種別 C は **他の処理が工程として呼ぶバッチ**（AI 生図の流水線の `batC51-A`〜`D` / `batC52`、
  授業ノートの `batC61` / `batC62` など）で、起動する側が要求（`要求内容` の `aiRequestId` /
  `assistId` / `noteId`）を用意する。画面の【再実行】で単体で走らせても、その要求が無いまま
  動くだけで、利用者が見ている処理（作図の生成など）は進まない。ハンドラが実装済みでも同じ。
- ハンドラがある C（`batC51-A`〜`D`・`batC52`・`batC61` / `batC62`）は**押せてしまう状態**だった。
  ハンドラが無い C は「2.1 では未実装です」の灰色ボタンだが、これも**未実装ではない**のに
  押せないと読めてしっくりこない。**種別で出し分ける**（どちらもボタンを出さない）。
- 画面側の出し分けだけに依存しない（2.1 の方針。有効／無効の切替も同じ）。API を直接叩かれても
  種別 C は走らない。他の処理からの呼出（`BatchService#rerunStep`）は種別に関係なく従来どおり。

## なぜモードが無い時代の裸の batC51 を削除したか（2026-09-19 改修）

**決めたこと**: AI 生図の AI 生成は**作図モードごとの 4 バッチ**（`batC51-A`〜`D`）だけにし、
モードが無い時代の**裸の `batC51` はバッチ定義・ハンドラごと削除**した（利用者の指示

- `AiFigurePipelineService#LEGACY_BATCH_CODE`（**未使用の定数**だった）

**なぜ**:

## なぜ設定の入口を「要求に固定した設定」に一本化するか（2026-09-19 改修 第 2 段）

**決めたこと**: AI 生図のバッチ（batC51-A〜D）は、実行の入口でも**その要求に固定した設定**
（設定スナップショット）を見る。**いまの設定（`COM_設定情報`）は、固定が無い歴史的な要求のときだけ**
読む。読み取りの入口は `AiFigureTaskConfigResolver` の 1 か所で、生成・プロンプトの組み立て・
パラメータの検証・コマンドの検証がすべてそこを通る。

**なぜ**（実測した不具合）:

- 受付時にスナップショットを固定し、生成の工程もそれを読むようにしていたが、
  `BatchServiceImpl.execute()` が**先に** `settingsService.requireSettings(batchCode, task.requiredSettings())`
  を呼んでいた。ここは**いまの設定**を検証するので、提出後に共用プロンプトを消す・不正な値にするだけで、
  固定した設定が完全でも**生成の工程に入る前に**失敗していた（＝並んでいるタスクが全部止まる）。
- 直し方は「実行の入口が先に現在の設定を見て、あとからスナップショットを読む」順番をやめること。
  入口の検証も**同じスナップショット**を使う。設定の入口を 2 つにしない
  （`FigureProcessorSettings.resolve(processor, snapshot)` は消し、`AiFigureTaskConfigResolver` だけにした）。
- **AI 生図以外のバッチの検証は今までどおり**（`BatchSettingsPreflight` を差し込んだバッチだけが変わる）。
  一覧の `settingsSource`（`CURRENT` / `TASK_SNAPSHOT`）で、どちらの規則かを画面からも分かるようにした。

**スナップショットの読み取りは「無い」と「壊れている」を分ける**（`AiFigureConfig.parseSnapshot`）:

| 状態 | 扱い |
| --- | --- |
| `ABSENT`（列が空・未設定） | いまの設定から作り、**AI を呼ぶ前に固定する**（`updatePinnedConfig`）。次回の再試行はその固定を使う |
| `VALID` | そのまま使う。**いまの設定は読まない** |
| `BROKEN`（JSON が壊れている・項目が足りない・版が違う・モードが食い違う） | **失敗**させ、要求行へ `FAILED(GENERATE, CONFIG_SNAPSHOT)` と理由を書く。**いまの設定へは切り替えない** |

版の互換の規則: 現在は版 1。同じ版 1 でも `model`（受付時のモデル名）と `revision`（実行版）が
無いものは**前の版が書いたもの**として読む（`model` は「固定できていない」＝実行の直前に読み直して
固定し、`revision` は 1 とみなす）。追跡用のハッシュだけの古い形は**本文が復元できない**ので `BROKEN`。

## なぜモデルの「スロット＋名前」を固定するか（2026-09-19 改修 第 2 段）

**決めたこと**: スナップショットに固定するのは `provider`（スロット。例 `qwen:4`）だけでなく、
**そのときのモデル名**（例 `qwen3-vl-plus`）も入れる。実行時は**固定した名前**で呼ぶ。

**なぜ**: モデル名はスロットごとの設定（`AI_QWEN_MODEL_4`）に入っているので、スロットだけを固定すると
**同じ ID の下でモデル名を書き換えるだけで、並んでいる要求が黙って別のモデルへ移る**。
実行の記録（`trace.configuredModel` / `trace.modelFromPinned`）と警告ログに残すので、あとから気づける。

- **スロットそのものが消えている**（設定が未設定・空）ときは**失敗**する。別のモデルへは切り替えない。
- **API Key と URL はスナップショットに入れない**（提供元ごとの秘密。実行のたびに `AI_MODEL` から読む）。
- 受付時にモデル名が読めない（`AI_MODEL` が未設定の）ときは空で固定し、**実行の直前に読めた名前で固定する**。

## なぜ「技術的な再試行」と「利用者の出し直し」を分けるか（2026-09-19 改修 第 2 段）

**決めたこと**: スナップショットに**実行版**（`revision`）を持たせる。

- 受付（作成）＝ 1。**利用者が入力を直して送り直す／【もう一度生成】＝ +1**（そのときの有効な設定で固定し直す）。
- **技術的な再試行では増やさない**: 働き手が拾い直したとき（`PREPROCESSED` / `GENERATING` の残骸）、
  検証だけをやり直したとき、AI 呼び出しの再質問（`REPAIR_PREFIX`）は、すべて**同じスナップショット**を使う。
  モデル名を後から固定した場合（受付時に `AI_MODEL` が未設定だった）も版は増やさない
  （利用者が入力を変えたわけではないため）。

これで「技術的な再試行が、いつのまにか最新の設定で作り直す」ことが起きない。

## なぜ録音の分塊を独立した表（CR_授業録音分塊情報）にするか（2026-09-19 改修）

**決めたこと**: 授業録音の分塊（`MediaRecorder` の 1 塊）を `CR_授業録音分塊情報` に
**1 塊 1 行 1 ファイル**（`chunk-{記録ID}-{連番}.webm`）で持ち、再生用の 1 本は
**再生のときに連番順へ組立てる**（`ClassroomRecordingAssembler`）。分塊の重複判定は
`(授業記録ID, 分塊連番)` と**中身の照合（バイト数 + SHA-256）**で行い、同じ連番で中身が
違えば上書きせず 409 にする。録音の最大時間は**画面が測った実際の経過秒**で見る。
画面は「次に送る分塊の連番」を `GET /classroom/{id}/chunks` の `nextSeq`（分塊表）から取る。

**なぜ**:

- 旧版は分塊の重複判定に**転写セグメントの最大連番**を流用していた。連番の意味が違うため、
  実害が 3 つ出ていた: (1) 転写が分塊より多く出た回（例 転写 8 文・分塊 3 個）は
  3 個目の分塊が「重複」と誤判定されて**音声が捨てられる**（音は後から作り直せない）、
  (2) 転写が 1 件も出ない回（無音の授業）は最大連番が 0 のままで、開き直して同じ分塊を送ると
  **二重に追記される**、(3) 画面が続きの番号を転写の連番から作れない（番号が飛ぶ・衝突する）。
- 旧版は再生用の 1 本へ**到着順に追記**していた。「ファイルの追記は成功したのに DB の
  トランザクションが失敗した」再送で、同じ音が**二重に入る**（音は消せない）。
  分塊を連番の名前で 1 ファイルずつ置けば、再送・同時再送・再起動のどれでも同じ場所に落ち着く。
  組立ては**ファイルを見て**行う（行の登録だけ失敗した分塊の音も残す）。
- 一時停止・画面の開き直しでは `MediaRecorder` を作り直すので、2 本目の分塊は**コンテナの
  ヘッダ（EBML）から始まる**。単純に連結するとファイルの途中にもう 1 つヘッダが入り、
  プレイヤーは**最初の回の音しか再生しない**。そこで 2 本目以降は最初の `Cluster` までを
  落として繋ぐ（`RecordingContainerCutter`）。落とし方が分からない形式（MP4 など）は
  **勝手に連結しない**（WARN を残し、分塊はそのまま残す）。Ogg は規格上連結できるのでそのまま繋ぐ。
- 分塊のファイル名に**記録 ID を入れる**のは、改修前から続いている録音の置き場
  （月ごとの共有ディレクトリ）でも他の記録の分塊と衝突しないようにするため。
  新しい録音は 1 記録 1 ディレクトリ（`…/{yyyyMM}/{uuid}/recording.webm` + `chunk-…`）。
- 保持期限切れの掃除（batR02）は、実体（再生用の 1 本と分塊）と分塊の行を一緒に消す。
  行だけ残すと「保存済み」に見え、遅れて届いた分塊の冪等判定が**実体の無い分塊**を
  「もう在る」と判断してしまう。
- 改修前の録音は分塊の行もファイルも持たない。**そのまま**（`録音ファイル保存先 /
  保存ファイル名` の 1 本を配信）にする。音声は作り直せないので移行しない。

## なぜ【作図方法を選択】をタブ＋3 節にするか（2026-09-19 画面の作り直し）

**決めたこと**: AI 生図のステップ 3 を、**A〜D のタブ**＋**3 つの節**（① 作成する図の種類／

## なぜ収尾（finish）を段階に分けて、失敗した状態を残すか（2026-09-19 改修 第 3 段）

**決めたこと**: 授業録音のストリーミング書き起こしの収尾は、1 回の呼び出しで
**「新しい音声の受け付けを止める → STT の最終結果を集める → 最終的な書き起こしを保存する →
資源を解放する」**の 4 段に分ける。**2 と 3 が済むまで完了にしない**。

**なぜ**（実測した不具合）: 旧版は `finish` の最後に無条件で `close(recordId, source)` を呼び、
認識セッションの状態を**消していた**。尾部（停止のあとに確定する文）を取り切れなかった回や、
保存に失敗した回でも同じなので、画面が【続きをやり直す】を押しても
「受け付けている認識セッションがありません」しか返らず、**やり直す手段が無かった**
（音は録音に残っているのに、尾部の文が永久に書き起こしへ入らない）。

**残すものと、その理由を状態で分ける**（`finish` の戻りと
`GET /classroom/{id}/stt/stream/status` が同じ形で返す）:

| 復帰の仕方 | いつ | やり直しで起きること |
| --- | --- | --- |
| `AWAIT_RESULTS` | 尾部（`task-finished`）を時間内に取り切れなかった | **接続は閉じずに残す**ので、同じ要求の尾部をもう一度待つ（**認識し直さない**） |
| `RESAVE_PENDING` | 取れた文を保存できなかった | 取れた文（発話キー確定済み）を**保存するだけ**（**認識し直さない**・行は増えない） |
| `RETRANSCRIBE` | `task-failed`・通信断で接続が復帰しない | 死んだ接続は持たず、**控えた音声**（最後の 2 分・有界）から新しいセッションで**認識し直す** |

- **閉じた接続を「保留の状態」にしない**。待てるあいだは `DashScopeAsrClient.Stream` を
  `requestFinish()` と `awaitTail()` に分けて**開いたまま持ち越し**、待てないと分かったら
  （`task-failed`、または待ち直しが上限に達した）控えた音声へ切り替える。
- **発話キーは認識した時点で確定**させ、保存に失敗した文はその形（`PendingSegment`）で残す。
  やり直しでも同じキーなので INSERT ではなく UPDATE に寄る（**行が増えない**）。
  位置が進むのは**保存できたときだけ**（受け取り確認も同じ規則）。
- **収尾の控え（保存待ち・控えた音声・完了の控え）は 1 時間で片付ける**
  （`RETENTION_MILLIS`、次の API 呼び出しのたびに期限切れを掃除する）。控えた音声は録音の
  ファイルにも残っているので、音そのものは失われない（在り処は `retainedAudioRef` に出す）。
- **`finish` は冪等**: 済んだあとの 2 回目は「セッションが無い」ではなく**保存済みの文を返す**
  （画面が応答を失ってやり直しても失敗に落ちない）。
- **収尾のあとに続きを録れる**（画面の【再開】）。画面は再開すると**フレーム番号を 1 から
  数え直す**ので、番号で「送り直し」と「続きの録音」を区別しない（区別すると続きの音を
  丸ごと捨てる）。送り直しは**位置**（すでに処理した位置より古い）で落ちるので、二重には認識しない。
- **終端を明示する**: 音声なし（`NO_AUDIO`）・発話なし（`NO_UTTERANCE`）は成功の終端。
  やり直しても直らない失敗（試行の上限）は `FAILED` + `retryable=false` にし、`error` ではなく
  **`notice`** に載せる。`error` のままだと画面が永久に再試行を出し続け、授業を終えられない。
- **`POST /classroom/{id}/end` はサーバー側で検証する**（画面のボタンを信じない）:
  まだやり直せる未完了の収尾があれば **409 で理由つきに断る**（記録も終わらせない＝終わらせると
  収尾を受け付けられなくなる）。書き起こしがあるのに分塊が 0 件なら音声が保存されていないので断る。
  直らない終端は通し、`notice` で知らせる。これで**最終まとめの範囲は、書き起こしを保存し切った
  あとに固定される**（尾部の文がまとめから落ちない）。

## なぜバッチの実行スケジュールを「メモリのスナップショット＋30 秒検査」にしたか（2026-09-19 改修）

**決めたこと**: 4 つのバッチ（`batR03` ネット利用終了 / `batR04` 開始 / `batL02` 動画取込 /
`batL03` スナップショット AI 分析）の実行時刻・実行間隔・ずらしを `COM_設定情報` で設定できる
ようにし、**実行の判断はプロセス常駐のメモリのスナップショットだけを見て 30 秒ごとに行う**。
仕組みの全体は `docs/BATCH_SCHEDULE.md`。

- 2.0 は batR03 = `0 30 23 * * *`、batR04 = `0 30 6 * * *` の cron で**時刻がコードと通知文に固定**、
  batL02 は専用の 5 分 cron（+ `BatL02ScheduleGuard` が「分 % 5 == 1」を強制）、batL03 は定義の
  `loopEveryMinutes=5`。実行間隔もずらしも変えられず、**画面には「毎時 05/15/…/55 分」という
  実際（01/06/…/56 分）と違う案内**が出ていた。
- **なぜ設定テーブルを毎回読まないか**: 30 秒ごとの検査で毎回 `COM_設定情報` と
  `BAT_バッチコントロール情報` を引くと、1 日 11,520 回の無駄な読み取りになる。設定は
  「起動時 / 保存のコミット後 / メモリに無いときの托底 / 管理者の再読み込み」でだけ読む。
- **なぜ不変スナップショット（`AtomicReference` で丸ごと差し替え）か**: 検査の途中で設定が
  入れ替わると、古い間隔と新しい時刻が 1 回の検査に混ざる。1 回の検査は必ず 1 枚だけを見る。
- **なぜ「要求の通し番号」で守るか**: 並行に保存されると、先に要求した（が遅く読み終わった）
  更新が新しい設定を上書きしうる。発行を直列化したうえで、自分より後に要求された更新が
  先に発行済みなら自分の結果を捨てる（リクエストの終了順だけで決めない）。
- **なぜトランザクションのコミット後に反映するか**: コミット前にキャッシュを触ると、
  ロールバックしたのに実行設定だけ変わっている、という食い違いが起きる。
  保存（`saveGlobalSettingFields`）と有効／無効（`updateActive`）は**どちらもコミット後**に
  `ScheduleConfigService#refresh` を呼ぶ。
- **なぜ失敗しても DB を巻き戻さず「反映待ち」を見せるか**: DB は保存済みなので消してはいけない。
  前の有効な設定で動かし続け、30→60→120→240→300 秒の退避で自動再試行し、画面には
  「保存済み・実行設定への反映待ち（理由）」と、いま効いている版・読み込み時刻・次の再試行を出す
  （嘘の「反映しました」も、無限の即時リトライもしない）。
- **なぜ計画実行点を DB に持つか**（`BAT_スケジュール状態情報`）: 「同じ計画実行点を 2 回実行しない」
  ことを JVM のメモリロックに任せると、再起動・多重起動・ポーリングのゆらぎで二重実行する。
  バッチごとに 1 行を持ち、**1 文の原子的な確保**（`INSERT ... ON CONFLICT DO UPDATE ... WHERE`）で
  勝った 1 つだけが実行記録を作る。メモリは DB を叩く回数を減らす早見にすぎない。
- **なぜ「最新の 1 点」だけを確保するか**: L で何点取りこぼしても補跑は 1 回に合并し、
  R は**最後に到来した 1 点**だけを実行する（23:30〜06:30 の停止明けに「前夜の終了を今さら実行して
  から開始」という順序を作らない）。計画（時刻・間隔）の変更や有効化でも過去の補償は起きない
  （無効の間は計画だけ進める）。
- **上書きしない規則**: 計画時刻より後に端末が更新されていれば、ネット制御は切り替えを見送り
  理由を履歴に残す（復帰後に利用者が手で選んだ状態を壊さない）。
- **単一インスタンス前提**を明記した（多重起動するときは、起動時の未完了実行の復旧条件・
  設定変更の通知・跨インスタンスの重複防止を見直す）。大きなスケジューラ製品は入れない。

### 追加の決め（2026-09-19 改修・スケジュールの 4 つの穴を塞ぐ）

- **なぜ要求ごとの通し番号を「読み込みと発行の両方」に持たせるか**: 発行時に
  `requestSequence.get()`（＝そのときの最新番号）を読むと、まだ読み込んでいない後続の要求まで
  「発行済み」になり、その要求が**破棄されて最新の設定が反映されない**。番号は要求した時点で取り、
  読み込みと発行に同じ番号を使う。**実際に DB を読まなかった要求は発行済みにしない**
  （読まずに捨てた要求が最新番号を握ると、本当の最新の読み込みが捨てられる）。
- **なぜ「設定の適用時刻」（`設定適用日時`）を持つか**: 22:00 に終了時刻を 23:30 → 21:00 に変えると、
  その日の 21:00 は既に過去なので「最後に到来した点」を実行してしまい、**変更した瞬間に
  ネットワークが止まる**。実行設定が実際に変わったときだけ適用時刻を記録し、
  **適用時刻より前の計画実行点は実行しない**（計画だけ進める）。適用時刻はタスクごとに DB へ残し、
  再起動しても引き継ぐ。「設定を変えたから実行しない」と「サービス停止中の取りこぼしの補執行」は
  別物で、後者は今までどおり補執行する。画面の「次回実行時刻」も同じ規則で出す
  （画面とスケジューラの判断を食い違わせない）。
- **なぜ R03 / R04 を 1 つのネット状態として扱うか**: 2 つは**同じ状態への逆向きの操作**なので、
  別々に補執行すると適用順によって「開始したのに止まっている」という誤った状態になりうる。
  復帰時は**いま以前で最後に到来した 1 点（＝現在有効なはずの状態）だけ**を実行し、古い点は
  実行せずに計画だけ進める。最新の点が無効・適用時刻より前なら古い点も実行せず、もう一方の
  切替が実行中ならその回は見送る（点を確保しない＝次の検査で再挑戦）。
- **なぜ手動操作の保護で「更新の出所」を見るか**: `更新元コード` が `batR03` / `batR04` の行は
  **このバッチ自身の更新**なので手動操作に数えない。数えると前回の実行時刻が計画時刻より後になり、
  **次の切替をいつまでも見送ってネット状態が切り替わらない**。出所が NULL の行は
  「利用者・不明」として手動に数える（上書きしない側に倒す）。
- **なぜメモリの早見を「コミット後だけ」進めるか**: 確保（`claim`）と実行記録は同じ
  トランザクションで行うが、コミット前にメモリへ「確保済み」と書くと、ロールバックしたときに
  その計画実行点が**二度と確保されず実行が抜ける**（漏執行）。トランザクションを明示的に切り
  （`TransactionTemplate`）、戻り値を得てから（＝コミット後に）だけメモリを進める。
- **なぜ待機中と実行中を分けて復旧するか**: 待機中（`QUEUED`）は**まだ業務が始まっていない**ので、
  失敗にせず同じ実行IDで実行し直す（＝「実行されないまま永久にスキップ」を作らない）。
  実行中（`RUNNING`）は結果が分からないので、まず失敗として閉じ、**その点がまだ「いまの計画」で
  タスクが有効なときだけ**、新しい実行記録（`起動種別=RETRY`）で 1 回だけやり直す
  （新しい点に追い越されていればやり直さない＝古い状態で新しい状態を上書きしない）。
  再実行してよい根拠は業務の冪等性（端末モードは設定、L02 は取込済みの重複除外、L03 は最新版フラグ）。
  1 件の復旧で例外が出ても、起動と残りの行の復旧は止めない。

### 追加の決め（2026-09-19 改修 第 2 段・復旧と設定保存の穴を塞ぐ）

- **なぜ「実行してよいか」の判定を 1 か所（`SchedulePlanGuard`）に集めるか**: 検査（30 秒）・
  再起動の復旧・実行直前で規則が違うと、片方だけ直して食い違う（＝復旧で古い逆向きの操作を
  実行する）。判定は `RUN` / `WAIT`（今は実行しないが**無効と決めつけない**）/ `SKIP`（理由つき）の
  3 つにし、見るものは**現在時刻・設定の版・適用時刻・有効／無効・タスクの実行状態**に固定する。
- **なぜ復旧で「計画実行点の新しい順」に処理するか**: R（batR03 / batR04）は 1 つのネット状態なので、
  未完了が両方あるときは**新しい方だけ**を実行し、古い方（逆向きの操作）はスキップとして閉じる。
  夜間の停止が翌朝まで残っていても、復旧で実行されるのは**朝の開始だけ**。
  L（batL02 / batL03）は最新の 1 点に合并し、古い点は実行しない（履歴を 1 件ずつ再生しない）。
- **なぜ復旧は「設定を読んでから」判定するか**: この復旧は起動処理（`ApplicationReadyEvent`）の
  最初に走る。何もしないとメモリの設定が空（未読込）で、**正しい実行まで「計画が無効」と誤判定して
  スキップ**してしまう（実機で実際に起きた）。托底（`ensureUsableConfig`）で 1 回読んでから判定し、
  それでも読めないときは `WAIT`＝**閉じずに保留**する（実行記録をスキップで埋めない）。
- **なぜ実行の直前にもう一度見るか**: 待ち行列（別スレッド・既定 1 本）で待っている間に
  利用者が設定を変える・タスクを無効にする・計画が古くなることがある。そのまま実行すると
  「もう効いていない設定」で業務が動く。実行直前に `SchedulePlanGuard` で見て、無効なら
  **理由を残してスキップ**する（待機中のまま残すと次の計画実行点が確保できない）。
  ただし L は**1 周期ぶん許す**（待ち行列で少し待っただけで実行できなくならないように）。
- **なぜ設定値と適用時刻を同じトランザクションで書くか**: 適用時刻を「設定のコミット後」に
  別で書くと、その間でサービスが落ちたときに**新しい設定＋古い適用時刻**が残り、再起動後に
  過去の計画実行点を実行してしまう。`ScheduleTimingRecorder` を設定保存トランザクションの
  中（`SettingSaveTransactionHook`）で呼び、`設定適用日時` と `設定版`（計画バージョン）を
  設定値と同じトランザクションで書く。**キャッシュの読み込みは何も書かない**（読みの途中で
  補って書くと、書けたかどうか分からないまま食い違いが残る）。
  入口は「設定ページの保存」と「有効／無効の切替」の 2 つで、**どちらも同じ記録を通る**。
- **なぜ計画バージョン（`設定版`）を持つか**: 「いま読んだ設定が保存時の版と同じか」を
  再起動後にも判定できる。DB を直接書き換えた場合（計画バージョンが進まない）は
  記録せず、**メモリだけで**「いまから新しい設定」として扱い、警告を残す（再起動で判断し直す）。
- **なぜ「DB が読めない」と「設定が無い」の退避を分けるか**: 読み込みに成功しても
  「設定が無いタスク」の回数を消してしまうと、退避が 30 秒に戻り、30 秒ごとに DB を引き続ける。
  回数は**そのタスクの設定が使えるようになったとき**だけ消す。托底は**足りないタスクぶんを
  まとめて 1 回**（1 回の読み込みで全タスクの状態が更新される）。設定がそろっていれば
  30 秒の検査はメモリだけを見る（周期的な DB 読み取りを増やさない）。利用者が保存したときは
  退避中でも即座に読み直す。
- **なぜ管理画面に退避の状態を出すか**: 「なぜ動かないのか」「次にいつ確認するのか」が
  分からないと、利用者は待つことも直すこともできない。タスクごとに
  `fallbackMessage`（理由・連続回数・次の確認時刻）と、上部に
  `configMissingMessage`（設定が無いバッチの案内）を出す。

### 追加の決め（2026-09-20 改修・復旧の続きと整合性）

- **なぜ復旧に段階（`PENDING_DISCOVERY` → `PENDING_REVIEW` → `COMPLETED`）を持たせるか**:
  起動時に設定や遺留リストを読めないことがある（DB がまだ上がっていない等）。そのとき実行を
  「無効」と決めつけて閉じるのは誤りだし、**閉じずに放置すると次の実行が永久に止まる**
  （未完了の実行は「前回が実行中」として次の実行を止める）。そこで
  「まだ読めていない」と「読めたが判定できない」を分けて持ち、30 秒の検査のたびに退避しながら
  続きを進める。**再起動は要らない**。すべて処理したら `COMPLETED` にして**以後は DB を引かない**。
  設定が読めるようになった直後（設定の保存・再読み込み）は退避を待たずにその場で判定し直す。
- **なぜ復旧の「境界」を固定するか**: 復旧は「このプロセスが始まる前に作られた実行」だけを扱う。
  起動時にそのときの最大の実行ID を読み、それを境界として遺留リストを確定する。境界を決めずに
  「いま未完了のもの」を毎回読み直すと、**このプロセスが作った実行中（RUNNING）のものを
  「落ちた実行」と誤解**して、同じ計画実行点を二重に走らせてしまう。境界とリストは最初に読めた
  値で固定するので、初回が失敗しても次の読み直しに自分の実行は混ざらない。
- **なぜ「閉じる」と「やり直しを作る」を同じトランザクションにするか**: 別々だと、
  閉じたのにやり直しが無い（＝その計画実行点が**永久に実行されない**）状態が残りうる。
  1 トランザクションにして、どちらか一方だけが残ることを防ぐ。二重の防止は
  **条件つき UPDATE**（未完了のときだけ閉じる）と**元実行ID の部分一意索引**
  （やり直しは 1 つだけ）で行い、メモリのロックには依存しない。実行器への投入は**コミット後**。
- **なぜ待ち行列があふれても記録を閉じないか**: その場で失敗にすると「確保した計画実行点が
  実行されないまま消える」＝漏執行になる。次の検査で入り直しを試し、上限まで入らなければ
  失敗として閉じる。入り直しを待っている間に落ちても、記録は `QUEUED` のまま残るので
  次の起動の復旧が拾える。
- **なぜ設定の読み込みを 1 トランザクション（`REPEATABLE READ`）にするか**: 設定値・有効／無効・
  適用時刻は別の表にあり、読み込みの途中で設定の保存がコミットされると、既定の
  `READ COMMITTED` は**文ごと**にスナップショットを取るため「設定値は新しい・適用時刻は古い」という
  混ざった版を読みうる。PostgreSQL の `REPEATABLE READ` はトランザクションで 1 つの
  スナップショットなので 3 クエリでも混ざらない。単一 SQL（UNION）にしない理由は、
  種類の違う行を Java で振り分ける形になり、既存の Mapper と SQL ログの形を崩すため。
- **なぜ `SchedulePlanGuard` が設定を自分で取りに行かないか**: 判定の途中でメモリの
  スナップショットが入れ替わると、前半は古い設定・後半は新しい設定で判断してしまう
  （R の「いま有効なはずの状態」が 2 つの版で食い違う）。呼び出し側が「その回に使う 1 枚」を
  決めて渡す（検査＝その回の 1 枚、復旧＝そのパスの 1 枚、実行直前＝そのとき最新の 1 枚）。
  実行状態（もう一方のネット切替が実行中か）だけは DB を見る、という境界にした。

### 追加の決め（2026-09-20 改修・復旧の境界と移行の完全化）

- **なぜ復旧の境界を「実行記録の帰属（起動識別子）」にするか**: 「起動時に読んだ最大の実行ID
  より古い行」を遺留とする方式には 2 つの穴があった。
  (1) 最初の読み込みが失敗し、その間に現在のプロセスが実行を作ると、再試行で読んだ最大ID が
  その実行を含み、**実行中の自分の実行を遺留と誤認する**（閉じる・二重に走らせる）。
  (2) 最大ID は読めたが遺留リストの読み込みが失敗すると、境界が固定されず再試行のたびに広がる。
  実行記録に「作ったプロセスの識別子」を刻み、復旧は**自分と違う行（NULL を含む）だけ**を
  遺留とすれば、読み直しを何度しても自分の実行は入らない（境界を固定する概念が要らない）。
  時刻（登録日時）での判定にしない理由: 時計のずれ・長いトランザクション・コミット順に依存する。
  ID の大小にしない理由: 「起動前のデータ」という仮定が、(1) で崩れる。
- **なぜ挿入を MyBatis のインターセプタで刻むか**: 実行記録の入口は 4 つ（自動スケジューラ・
  起動時バッチ・画面の手動実行・復旧のやり直し）あり、これからも増えうる。入口ごとに設定すると
  **足し忘れた入口**が生まれ、その入口で作った実行を復旧が誤認する。挿入の直前に一括で入れる
  方式にして、入口が増えても漏れないようにした（値をビジネスロジックに書かない）。
- **なぜ履歴の 起動識別子 が NULL の行を遺留として扱うか**: この列を入れる前の記録は
  「前のプロセスが作った行」としか言えない（現在のプロセスは必ず値を書く）。互換のため
  遺留として扱い、配備順序は「移行 → 新しいアプリ」とする（列が無いと挿入できないため、
  逆順は動かない）。
- **なぜ移行で重複を見つけたら中止するか**: `元実行ID` の一意索引は「やり直しは 1 つだけ」を
  DB で守る要（`INSERT ... ON CONFLICT`）。既存データに重複があると索引が作れないが、
  履歴を勝手に消したり書き換えたりしてはいけない（監査の記録）。件数を報告して中止し、
  利用者が内容を確認してから再実行する。
- **なぜ移行スクリプトをテストから実行するか**: `CREATE TABLE IF NOT EXISTS` は既にある表に
  列を足さないため、**既存環境の移行スクリプトが動くこと**を確かめないと「新規環境では動くが
  既存環境では動かない」事故になる。テストは**出荷するスクリプトをそのまま**（テスト用の作業表に
  向け直して）2 回流し、列・索引が増えて既存行が変わらないことを確かめる。
  スクリプトの読み出しは**シェル**に任せる（リポジトリの `database/` は日本語のパスで、
  ファイル名エンコーディングが UTF-8 でない JVM では Java から開けないため。
  スクリプト冒頭の ASCII の `MIGRATION-ID:` 行で選ぶ）。

### 追加の決め（2026-09-20 改修 第 2 段・復旧の競合と試験の隔離）

- **なぜ復旧を「整理」と「投入」の 2 段階にするか**: 判定しながら実行器へ渡すと、同じタスクの
  **古い記録が未完了のうちに新しい記録が走り出し**、業務側の「前回が終わっていないのでスキップ」
  （`runQueued`）に当たって**本来実行すべき記録が失われる**（実測: batL02 の古い A と最新の B で
  B がスキップされ、そのあと A が「計画が古い」で閉じられた）。第 1 段階で全遺留を判定して
  実行しない記録を**先に閉じ**、第 2 段階で有効な記録を投入する。実行側の防重チェックは
  **外さない**（最後の砦として残す）。
- **なぜ「同じタスクに未決が残る間は投入を持ち越す」か**: 未決（保留・閉じられなかった・
  復旧トランザクション失敗）の記録が残っていると、投入しても業務側の防重でスキップされ、
  **そのまま失われる**。持ち越して次で再判定すれば失われない。持ち越しはタスクごとに判断するので、
  1 つのタスクの失敗で全体を止めない（R03/R04 の業務順序は計画判定（新しい点だけ実行）で保つ）。
- **なぜ「実行中から作ったやり直し」を復旧が持ち続けるか**: そのやり直しは**このプロセスの記録**
  （起動識別子が自分）なので「前のプロセスの遺留」検索では二度と出てこない。誰かが持ち続けないと
  作ったまま投入されず漏れる。復旧の投入待ち（追跡）が唯一の持ち主として、実行器へ渡すまで
  責任を持つ。投入の直前には待機中かを確かめ、実行済みなら追跡から外す（二重実行しない）。
  待ち行列があふれたときの入り直しは実行器の既存の仕組みに任せる（投入経路を 2 つにしない）。
- **なぜ実 DB 統合試験を専用 DB に限るか**: それまでは「DB のパスワードがある」だけで日常の開発 DB に
  繋がり、実行記録や設定を書き換えていた（後始末も「最近の N 件」で、他人の記録を触りうる）。
  専用の使い捨て PostgreSQL（`tmp/tools/study21-batchtestdb.sh`）を URL で渡したときだけ動かし、
  無ければスキップする。試験が作った記録は**自分が作った実行IDだけ**を閉じる
  （`BatchTestExecutionCleanup`。元実行ID でつながるやり直しも自分のものとして扱う）。
- **なぜ実業務を代役にするか**: 動画取込・AI・プロキシ起動は外部に副作用を持つ。
  `BatchServiceImpl` はハンドラを**生成時**にタスクコードで引くため、Bean を差し替えるのではなく
  **代役だけを持つサービスを試験が組み立てる**（実ハンドラが混ざらない）。MyBatis・
  起動識別子のインターセプタ・トランザクションの経路は本物のまま通す。

### 追加の決め（2026-09-20 改修 第 3 段・復旧の追跡不変条件と試験の自動運転スイッチ）

- **なぜ「復旧トランザクション成功 → 追跡へ登録 → 元の実行IDを外す」の順にするか**:
  逆順（先に元を外し、あとで局所リストへ入れる）だと、その間の照会が失敗したときに
  **新しく作ったやり直しが誰の追跡にも入らない**。その記録はこのプロセスのもの
  （起動識別子が自分）なので遺留検索では二度と出ず、**待機中のまま永久に実行されない**。
  登録を先にすれば、途中で失敗しても次のパスが同じ実行IDを投入できる（やり直しは作り直さない）。
- **なぜ照会の失敗を「無い」「終わった」と解釈しないか**: 投入してよいかの判断は 3 状態
  （待機中／終了済み／照会できず）にし、**照会できなかったら追跡に残して次のパスでやり直す**。
  「行が無い」「終了済み」と同一視すると、一時的な DB 障害で**有効な実行を捨てる**ことになる。
  1 つの記録の照会失敗で他の記録の投入を止めない（例外は記録ごとに握る）。
- **なぜ自動運転のスイッチを設定にするか**: テストで本物の起動時バッチ・自動復旧・定期実行を
  止めたいが、「間隔を 1 日に伸ばす」ような回避は**止めたことにならない**（起動イベントは止まらない）。
  `study21.batch.auto-run.*` の 3 つで**自動の入口だけ**を無効にする（既定は有効＝正常環境の挙動は
  変えない）。入口は薄い適配層にして、業務の入口（`runOnStartup`・`recoverInterruptedExecutions`）は
  そのまま呼べる＝テストは「入口を差し替える」のではなく**明示的に呼ぶ**。
  profile 名で分岐するコードは書かない（設定で切り替える）。
- **なぜスイッチ自体をテストするか**: 入口を mock して「無効だから動かない」と言っても、
  スイッチの効き方は確かめられない。ユニットテストで（無効：協力者と一切やり取りしない／有効：
  実行する）、実 DB の統合テストで（**本物の `ApplicationReadyEvent` を流しても起動時バッチ・
  自動復旧が動かず、明示的に呼べば動く**）を確かめる。

## なぜ録音と回放の時間軸を 1 つにしたか（2026-09-19 改修）

**決めたこと**: 授業録音の時刻は **`RecordingTimeline`（`frontend/pc-web/src/features/classroom/timeline.ts`）
の累計サンプル位置（16kHz）**だけで決める。`Date.now()` も画面のタイマーも使わない。
**一時停止のあいだは時間軸を進めない**。マイクと共有の音は**同じ `AudioContext`** に載せ、
その 1 つのサンプル時計から位置を出す（`contextSample`。`AudioWorklet` の `currentFrame`）。

- **なぜ累計サンプル位置か**: 端末の時計（`Date.now()`）は停止のあいだも進み、端末の時刻合わせで
  飛ぶ。音そのものとずれた時刻で書き起こしを並べると、**回放を聞いたときに文の位置が合わない**
  （実測: 停止 → 続きの録音で、続きの文が録音の先頭へ飛んだ）。
- **なぜ一時停止を数えないか**: 録れていない時間は録音の音にも入っていない。進めてしまうと
  「録音の 3 分目」と「回放の 3 分目」が別の音を指す。停止 → 続きの録音では、画面が
  **保存済みの位置**（`GET /classroom/{id}/chunks` の `recordedSeconds` と `localStorage` の
  先のほう）へ `restore` してから `resume`（＝再開した時点の時計を基準）する。
  保存した**混ぜた音**も同じ規則になる: `MediaRecorder` は停止のたびに作り直し、
  停止のあいだは音源を繋いでいないので、**停止のあいだの無音は 1 本に入らない**
  （回放は分塊を連番で連結したもの。`ClassroomRecordingAssembler`）。
- **なぜ 1 つの `AudioContext` か**: 別々のコンテキストは**別の時計**なので、片方が遅れて繋がると
  その音源の 0 が録音の別の時刻になる（同じ瞬間の発言が別の行として 2 つ出る）。同じ
  コンテキストなら時計が 1 つで、**後から繋がった音源もその時点の位置**から始まる。
  混ぜているときは**混ぜるのと同じコンテキスト**を使う（別のコンテキストの節点へは `connect`
  できず、二音源のときだけ黙って PCM が取れなくなる）。
- **なぜ時計の差を位置にするか**: 時計と音は同じ速さで進む。報告の時計が「このチャンクの長さ」
  より先へ進んでいたら、その差は**録れていない区間**（マイクを抜いた・端末が止まった・共有が切れた）。
  **詰めずにその長さぶん先へずらす**（欠落として記録する）。時刻を圧縮して隠すと、
  あとから補書き起こしするときにどの音か分からなくなる。
- **なぜ `resume` を送らないか**: 後端は `{"type":"resume","from":N}` から
  「その音源へ送ったサンプル数 = N × 100ms」を計算して**時間軸の下端**にする。こちらは
  フレーム番号も位置も**録音全体で通し**なので、続きの録音（番号 600 番台から）で送ると
  下端が実際の音より遥かに先へ飛び、**続きの音が全部「すでに処理した位置より古い」として
  捨てられる**。位置はフレームの見出し（`startSample`）で毎回送るので、後端は番号から
  計算しなくてよい（この改修で `resume` の送信をやめた。後端はそのまま＝互換）。
- **なぜ 3 つの位置を分けるか**（採った・送った・確認できた）: 送っただけの位置を「録れている音」と
  して使うと、まだ送れていない音の時刻で送ってしまう。位置は**前へだけ**進め、送り直し・
  張り直し・後端の再起動で戻らない（戻すと確定済みの文と同じ発話キーを作り直して行が増える）。
- **HTTP 送信の 1 回の長さ**は「前の送信から待った長さ」まで（上限 `maxSendSeconds`）。
  いつも上限まで送ると、送信の周期ごとにまとめて投げて**送る位置が受信した音を追い越す**。
- **画面に出す確認**: 位置は画面に残す（`study21.classroom.timeline.{recordId}`）。後端の分塊の
  状態（`GET /chunks`）だけに頼らない（分塊は「送れた音声」の位置しか持たない）。

**同じ改修で消したもの**: 録音中の画面の**【共有を選び直す】**（`data-cr-reshare`）と
`ClassroomAudioGraph.replaceRemote`。前の実装は**混ぜる遠隔音だけを入れ替え、共有の音の
書き起こしは入れ替えていなかった**（＝混ぜた音と書き起こしの食い違いの元）。入口も案内文も
残さない（同じ役割のボタンを別の名前で足さない）。共有の音が止まったときは、
**先生の音源が中断したことを明確に知らせ、その音源だけを収尾**（`/stt/stream/finish?source=shared`）
し、**マイクは録り続ける**（学生の声は残す）。役割のラベル（共有＝先生／マイク＝学生）は
録音の設定で決まるので、片方が止まっても変わらない。

## なぜ Text の位置の言葉を外して通すか（2026-09-19 不具合修正）

**症状**（利用者の報告・要求 AIG202609192003227909778）: AI 生図は `READY` になったのに、
作図画面を開くとエラーが出て保存できない。

**原因**: AI が `Text("A", A, "left")` のように **`Text` の 3 番目へ位置の言葉**を渡していた。
この版の GeoGebra の `Text` は `Text(文章, 点)` / `Text(文章, 点, true|false)` だけで、
位置の言葉は**引数に存在しない**（実機で必ず `false`）。
実測: その要求の 14 コマンドのうち **8 件しか実行できない**（6 件が `Text`）。
第 2 段の改修で「実行できなければ保存させない」ようにしたため、利用者には

## なぜ分塊を「固有の場所へ書き、DB が引用を決める」形にしたか（2026-09-19 改修・②）

**決めたこと**: 分塊（`MediaRecorder` の 1 塊）は **分塊ごとに固有のファイル**
（`chunk-{記録ID}-{連番}-{UUID}.webm`）へ書き、**どの実体がその分塊なのかは
`CR_授業録音分塊情報` の行（`ON CONFLICT DO NOTHING` に勝った 1 本）が決める**。

- **なぜ並べ替えたか**: 以前は「連番で決まる同じ名前」へ書いてから DB の一意制約で重複を
  判定していた。同じ連番が同時に 2 本来ると、**負けた側のファイルが勝った側の音を上書き**し、
  DB は勝った側の行を持っているのに実体は負けた側の中身、という食い違いが起きる
  （＝再生すると別の音が鳴る。音は後から作り直せない）。
- **順序**: ①置き場を用意する → ②**行を入れて引用を取る**（勝った 1 本だけが取れる）→
  ③引用を取れた側だけが実体を書く。負けた側は**実体を書かない**ので、壊すものが無い。
- **冪等と衝突**: 同じ連番・同じ中身（バイト数 + SHA-256）の再送は**保存済みの結果**を返す。
  違う中身は 409 で断り、**勝った側の実体には触れない**。
- **置き場の初期化**: 録音の置き場は**記録 ID から決める**（`classroom/{アカウント}/{yyyyMM}/rec{記録ID}`）。
  ランダムな名前だと、開始直後に分塊が同時に届いたとき**別々の置き場**ができて分塊が散らばる
  （DB が指す置き場と実体の場所が食い違い、欠落として扱われる）。`Files.createDirectories` は
  冪等なので、同時に呼ばれても同じ 1 つに落ち着く。
- **孤立ファイル**: 「実体は書けたがトランザクションが失敗した」分塊は、行から引用されないまま
  残る。**一定時間（1 時間）より古い孤立ファイルだけ**を掃除する（書いた直後の実体は、まだ
  確定していない同時実行中の要求が引用するかもしれない）。**引用されている実体は消さない**。
- **結合の正体は DB の行だけ**: 置き場のディレクトリを数えて結合すると、孤立ファイルまで音として
  混ざる。**行に無いファイルは音として使わない**。

## なぜ続録の結合で ffmpeg を使うか（2026-09-19 改修・②）

**決めたこと**: 画面は一時停止・画面の開き直しで `MediaRecorder` を作り直す。その回の分塊は
**別のコンテナで、タイムスタンプが 0 から始まる**。2 本目以降のコンテナヘッダを落として
繋ぐだけでは、**2 本目以降の時刻が最初のセッションへ重なる**（再生位置と書き起こしの時刻が
食い違う）。そこで `ClassroomRecordingSessionPlanner` で
「同じ `MediaRecorder` の続き（ヘッダ無し）」と「新しいセッション（ヘッダ有り）」に分け、
**セッションごとに時刻を積み直してから**、ffmpeg（`-itsoffset` + `concat` フィルタ＝再多重化、
再符号化なし）で 1 本にする。

- **1 セッションなら ffmpeg を使わない**（同じコンテナの続きなので、そのまま連結で正しい）。
- **欠落があるときは結合しない**（`INCOMPLETE`）。途中までを 1 本にすると、利用者には
  「録れている」ように見える（黙って音を失わない）。
- **ffmpeg が無い環境では結合しない**（`FAILED`）。**分塊は 1 つも消さず**、状態と理由を画面に
  出して再試行できるようにする。**壊れた 1 本を公開しない**ことを優先する。
- **出力は必ず新しいファイルへ**（`-y` を付けない・既にあるパスへ書かない）。結合に失敗しても
  **前の 1 本はそのまま**配信する（途中までの音。上書きで壊さない）。
- **分塊は絶対に消さない**（結合が成功しても残す。音の作り直しができる最後の砦）。
- **結合の道具はイメージに入れる**（`deploy/docker/user-api.Dockerfile` で `ffmpeg` を導入。
  設定は `study21.classroom.ffmpeg-command` / `study21.classroom.ffprobe-command`）。

## なぜ終了の前に「そろっているか」をサーバーで確かめるか（2026-09-19 改修・③）

**決めたこと**: 終了（`POST /classroom/{id}/end`）は、**分塊が 1 から連続して全部そろっているか**を
サーバー側で確かめる。以前は「分塊が 1 つ以上あるか」しか見ておらず、**途中が欠けていても・
最後の分塊が届いていなくても**終われてしまった（音は後から作り直せない）。

- **画面は停止のあと「送った分塊の一覧」を渡す**（`manifest` = 最後の連番・送った数・終わりの
  サンプル位置）。サーバーはこれで**最後の分塊の取りこぼし**を見つける（保存済みの行の最大連番
  だけでは、まだ届いていない最後の分塊が分からない）。一覧は `localStorage` にも残す
  （停止の直後にページを閉じても・開き直しても同じ判断ができる）。
- **欠けていれば 409 で欠けている連番を返す**。画面はその分塊だけ送り直す（`GET /chunks` の
  `finalizeCheck` でも同じ判断が取れる＝開き直してもサーバーから状態を復帰できる）。
- **明示の「不完全なまま終了」**（`force=true`）だけは通し、**何を失ったか**を `notice` に載せる。
  既定は断る（黙って音を失わない）。
- **書き換えの直前にもう一度見る**: 確認と書き換えのあいだに別の要求（未調整のアップロード）が
  分塊を足せるので、**同じ一覧であることを確かめてから**完了にする。変わっていれば終了せず、
  もう一度やり直させる（中途半端な完了状態を作らない）。
- **取り込み音声（mp3）・貼り付けだけは分塊を持たない作り**なので、分塊を理由に断らない
  （今までできていた操作をできなくしない）。

## なぜ録音中の画面を「状態 1 つ + 転写が主役」にしたか（2026-09-19 改修・④）

**決めたこと**: 主画面は**授業名・録音の長さ・音源・いまの状態・主な操作**だけ。技術情報
（分塊の番号・サンプル位置・ミリ秒の区間・STT の中の状態・API の説明）は**既定で畳んだ
【詳細情報】**の中だけに出し、**件数を上限で切る**（DOM を無限に増やさない。CSS で隠すだけに
しない）。旧い説明（MVP・`two_speaker`・話者を分けない案内）は出さない。

- **状態は 1 か所**（`cr-status`）: 「録音中」「音声を保存しています…」「文字起こしを仕上げています…」
  「授業を終了できます」「やり直せます」。**正常に動いているあいだは赤い警告を出さない**。
  やり直せるものだけ【再試行】を出す（利用者に「どのボタンを押せばよいか」を推測させない）。
- **「音声は保存されています」は、サーバーが「全部そろっている」と確認したときだけ**言う
  （送っただけで約束しない）。
- **停止したら、その場で**「止めた」と分かるようにし、**収尾が走っているあいだは終了の入口を
  押せなくする**（`finishing` は `await` より前に立てる）。待っている中身（段）を文章で出す。
- **転写が主役**: 話者は**ラベルと色の両方**で分かる（色だけに頼らない）。時刻は**1 文に 1 つだけ**
  （`[mm:ss]`。ミリ秒や区間は出さない。内部の精度はそのまま持つ）。読んでいる位置を飛ばさない
  （下を見ているときだけ追いかける・【最新へ】で戻れる）。AI 解析が無効でノートが無いときは
  **空の枠を出さない**。
- **離脱の確認**: 録音中・保存中・送り残しがあるあいだは `beforeunload` で止める
  （未アップロードの音を持ったまま消えない）。

## なぜタスクカードの【削除】を「取消にして一覧から外す」にするか（2026-09-19）

**決めたこと**: AI 生図のタスクカードに**削除のアイコン**（ゴミ箱）を足す。押すと**確認してから**、
サーバーは状態を**取消（CANCELLED）にして、タスク一覧から外す**（行は残す）。
あわせてカードの操作を**アイコンだけ**にした（意味は `title` と `aria-label` で伝える）。

**なぜ「行ごと消す」ではないか**:

- 要求行は `BAT_AI呼出履歴情報`（お金を使った記録）と `図形ID` から参照される**監査の記録**。
  行を消すと「いくら使ったか」「どの図形になったか」が辿れなくなる。図形も物理削除ではなく
  削除済みで残す作りなので、同じ考え方に揃える。
- 一覧は `状態コード <> 'REGISTERED'` で絞っているので、`CANCELLED` も外す（消したカードが戻らない）。
- 【取消】は「お金を使ったあとは取り消せない」という規則のままにする（生成中の課金を止める話）。
  カードの【削除】は**利用者が自分のカードを片付ける**入口なので、**どの状態でも消せる**。
  生成中に消したときは、走っている働き手の書き込みが版数で弾かれ、取消のままになる
  （`AiFigurePipelineService.ensureFailed` も `CANCELLED` には書かない）。
- 図形として保存済みのものは消せない（図形一覧から削除する。サーバーも断る）。

**なぜアイコンだけにするか**: カードが狭く、文字ボタンを並べると 1 行に収まらない。
図形カードの操作（編集・コピー・印刷・削除）が既に**アイコンのみ＋`title`/`aria-label`**なので、
同じ規則に揃える（読み上げでも意味が分かる）。**確認は出す**——生成済みの作図は消すと
作り直し（再課金）になり、AI 生図の履歴一覧はどの画面にも出していないため。

## なぜ最終分塊一覧の「録れた範囲」と「保存の事実」を分けるか（2026-09-19 改修・第 4 段 ①）

**決めたこと**: 終了（`POST /classroom/{id}/end`）に添える一覧の欄の意味を固定し、**保存の事実は
後端（DB の行と実体のファイル）を正**とする。

- `expectedLastSeq` / `expectedCount` … **実際に録れた**最後の連番とその件数（分塊を作った時点で
  決まる。**送れたかどうかとは別**）。
- `expectedEndSample` … 最後に録れた分塊が終わる**統一時間軸の位置**（16kHz のサンプル数）。
- `uploadedSeqs` … **送信の応答を受け取れた**連番。**補助情報**であって、保存の事実ではない。
- `unrecoverableSeqs` … 画面が「送り直しても直らない」と判断した連番（エラーコードで判断する）。

**なぜか**: 以前は「送れた範囲」をそのまま「そろっている範囲」として扱っていたため、**どちら向きにも**
壊れ得た。①最後の分塊の**応答だけ**失われた回（後端には保存できている）に「欠けている」と誤って断る
（実際には残っている音を利用者に諦めさせる）。②画面が「作った数」を送ると、届いていない最後の分塊を
見落とす。いまは後端が**保存済みの連番（`savedSeqs`）を返して照合**させ、欠落の判断には
`uploadedSeqs` を使わない。応答を失っただけの分塊は「欠けている」にならない。

- **断る理由は種類で返す**（`reasonCode`）: `MISSING`（送り直せば直る）/ `BROKEN`（行はあるが実体が
  無い）/ `EXTRA`（録れた範囲の外に在る）/ `MANIFEST_CONTRADICTION`（一覧そのものが矛盾・上限超え）/
  `END_SAMPLE_MISMATCH`（録音の終わりの位置が合わない）。**日本語の文面では判断させない**。
- **終わりの位置も使う**（受理して捨てない）: 単位は統一時間軸のサンプル数（16kHz。画面の
  `TIMELINE_SAMPLE_RATE` と同じ）。許容差は**端数の 2 秒**だけ（分塊 1 つ＝20 秒のずれは申告の誤り）。
- **上限を設ける**（`MAX_CHUNKS`）: 現実にあり得ない件数の一覧は、調べる前に断る。
- **旧い画面**（録れた範囲を送らない）は、保存済みの範囲で確かめる。この場合
  `expectedLastSeq=0` を返し、画面は「最後の分塊まで届いたことを**証明していない**」と読む
  （「保証された完了」と読み替えない）。取り込み音声（mp3）は今までどおり分塊で断らない。

## なぜ分塊の受け入れと収尾で**同じ行を押さえる**か（2026-09-19 改修・第 4 段 ④）

**決めたこと**: `uploadChunk` と `end` は、どちらも**同じ授業記録の行を排他で押さえて**
（`SELECT ... FOR UPDATE`）から状態を読み直す。長い処理（AI 解析・FFmpeg）は**押さえた
トランザクションの中で走らせない**（収尾の応答と接続を長時間占有しない）。

**なぜか**: 状態（`RECORDING` → `TRANSCRIBING`）を条件にした更新だけでは足りない。押さえる前に
読んだ状態を根拠にしたアップロードが、収尾の**あと**に分塊の行を足せてしまう（確定した一覧が動く）。
行を押さえれば、収尾の更新はアップロードのコミットを待ち、アップロードは収尾のコミット後に新しい
状態を読む（どちらか一方が必ず後になる）。**受け入れの判断は必ず押さえたあと**に行う。

**終わったあとのアップロード**: 収尾で確定した範囲（`録音分塊最終連番`）だけを受け入れる。
停止直後に届いた**一覧に載っている分塊**（取りこぼしの救済）は受け入れるが、**一覧に無い新しい連番**
は断る（確定した一覧を動かさない）。同じ連番・同じ中身の再送は今までどおり冪等。

## なぜ結合の状態を DB に残すか（2026-09-19 改修・第 4 段 ⑤）

**決めたこと**: 再生用の 1 本（分塊の結合）の状態を `CR_授業記録情報` に残す
（`NOT_STARTED` / `QUEUED` / `PROCESSING` / `READY` / `FAILED` / `INCOMPLETE`）。あわせて
**どの分塊から作ったか**（内容の要約 = ダイジェスト）と、長さ・理由・開始/終了時刻を持つ。

**なぜか**: 以前は状態を**メモリの Map だけ**で持っていた。user-api を再起動すると `READY` が消えて
`NONE` に戻り、画面は「作成中」を出し続ける（**永久に待つ**）。いまは起動直後に DB の状態を読み直し、

- `READY` でも**いまの分塊の要約と一致しない/出力ファイルが無い**なら READY とは言わない（やり直す）。
- `PROCESSING` が残っていて**このプロセスが始めたのではない**なら「サーバーが再起動しました」＝
  やり直せる失敗にする（このプロセスが始めたものだけを「作成中」と言う）。
- `NOT_STARTED` は**「作成中」と言わない**（誰も作っていないのに待たせない）。画面は【作り直す】を出す。

状態の書き込みは、開始前に `QUEUED`、終わったら `READY`／`FAILED`／`INCOMPLETE`。走らなかった
（既に新しい）ときは `READY` に戻す（「作成中」のまま残さない）。失敗しても**分塊は 1 つも消さない**。

## なぜ離脱は「収尾の結果」で決めるか（2026-09-19 改修・第 4 段 ②）

**決めたこと**: 収尾は**共有の 1 つの約束**（`finalizePromise`）にして、**結果を値で返す**
（`completed` / `incomplete` / `failed`）。「保存が終わるのを待って移動」はその結果を見て、
**失敗・未完了なら移動しない**。

**なぜか**: 以前は「走っている収尾が終わるのを待って**無条件に**移動を許可」していた。収尾が失敗しても
タイムアウトしても移動でき、保存できていない音を置き去りにできた（100ms ごとにブール値を見る形では
**成功・失敗・未完了を区別できない**）。いまは失敗なら画面に残り、【もう一度待つ】【この画面に残る】
【音声をあきらめて移動】の 3 つを出す。**タイムアウトは成功ではない**（失敗として扱う）。

**意図の格上げ**: 停止の最中に【授業を終了】を押したら、押した操作を捨てずに同じ約束の終了へ進める
（2 本目の収尾は走らせない）。停止・終了・離脱の 3 つが同じ約束を待つ。

## なぜ「不完全なまま終了」で確認した分塊を凍結するか（2026-09-19 改修・第 4 段 ③)

**決めたこと**: 普通の終了は**完全**であることを要求し、明示の不完全終了だけが「利用者が確認した
内容の完全性」を免除する（権限・状態・一覧の正当性・並行の保護は**免除しない**）。確認したあとは
その分塊を**凍結**（自動の送り直しを止め、`unrecoverableSeqs` として申告）し、送り残しがあっても
終了の要求を止めない。失った連番は後端が `録音欠落連番` として残し、**詳細画面が出し続ける**。

**なぜか**: 以前は送り残しがあると収尾の途中で止まるため、確認まで済ませた利用者が終了へ進めなかった
（`force` が届かない）。逆に、確認したあとに届いた分塊で確定する範囲が動くと、利用者が確認した内容と
実際に終わる内容が食い違う。凍結は両方を同時に防ぐ。**4xx を一律に「もう直らない」と決めない**のも
同じ理由（認証切れ・権限・競合・制限は待つか入り直せば直る。直るものを「失った音声」に数えない）。

## なぜ収尾の結果に `retryable` を足したか（2026-09-19 改修・第 5 段 ①）

**決めたこと**: 書き起こしの収尾（`finish`）の結果を「成功・失敗」の 2 つで表すのをやめ、
**`retryable`（まだやり直せるか）を明示の欄**として返す（HTTP の本文と常時接続の `finished` の両方）。
画面は `error` / `finalizeCompleted` / `retryable` / `finalizeStatus` / `notice` を
**1 か所（`stt-finalize.ts`）で同じ意味に揃えて**読み、次の 6 つに分ける:

- `PENDING`（まだ途中）/ `COMPLETE`（完全）/ `NO_AUDIO`（音声なし）/ `NO_UTTERANCE`（発話なし）/
  `RETRYABLE_FAILURE`（やり直せば直る）/ `INCOMPLETE_UNRECOVERABLE`（やり直しても直らない不完整な終わり）/
  `UNKNOWN`（**確認できない**）。

**なぜか**: 後端は「やり直しても直らない終端」を **`error=null` / `finalizeCompleted=false` /
`notice=理由`** で返す（画面が永久に再試行しないため）。画面が `error` だけを見ると、これを
**成功と誤読**して「録音と書き起こしを保存しました」と言い、**書き起こしが欠けたまま**終わる。
逆に「全部成功でなければ失敗」とすると、直らないものを永久に再試行させて授業を終えられない。

**「終わってよい」と「識別が完全」は別**: `INCOMPLETE_UNRECOVERABLE` は `canFinish=true` /
`complete=false`（終わってよいが完全ではない）。`UNKNOWN` は `canFinish=false`（確認できないものを
成功とも失敗とも決めない）。**欄が欠けている応答（旧い後端・応答の欠落）は「完全」と読まない**。

## なぜ識別の完備を DB に残すか（2026-09-19 改修・第 5 段 ①-5）

**決めたこと**: 収尾がけりついた時点で、記録に `認識収尾状態`（`COMPLETE`/`INCOMPLETE`/`RUNNING`/
`NO_AUDIO`/`UNKNOWN`）・`認識完備`・`認識音源状態`（音源ごとの JSON）・`認識収尾理由` を書く。
詳細画面はこれを読み、`complete=false` のときは「書き起こしの一部を完了できませんでした
（録音した音声は保存されています）」と出す。**音声の欠落（`lossSeqs`）とは別の欄**にする。

**なぜか**: 収尾の結果はその場の応答にしか無く、画面を開き直すと**不完全だったことが消える**。
また「音声が欠けている」と「識別が欠けている」は別の出来事で、混ぜると
「録音は保存できたのに『音声が欠けています』と言う」／「書き起こしが欠けたのに『保存しました』と
言う」という嘘になる。記録が無い（改修前・音声を送っていない回）ときは `UNKNOWN`＝
**完全とは見なさない**（「確認できない」と出す）。

## なぜ最終まとめの起動を「受理 + 背景」にしたか（2026-09-19 改修・第 5 段 ②）

**決めたこと**: `POST /api/admin/batch/classroom/notes/{noteId}/run` は **AI の完了を待たず**、
条件つき更新（`PENDING`/`FAILED` → `GENERATING` を 1 文で）で**受理**して背景で走らせる。
応答は `{noteId, accepted, status, message}`。`READY` なら**AI を呼ばずに**そのまま返す。
前回の開始から一定時間（30 分）たった `GENERATING` は「プロセスが落ちた回」とみなして
もう一度受理する。画面は**受理の応答を待ってから**「始めた」と印を付け、失敗は
**録音の保存を取り消さずに**画面と詳細の両方に残す（【最終まとめを再試行】）。

**なぜか**: 以前は画面が「起動を投げて、待たずに `noteStarted=true`」にしていた。応答が失敗しても
起動済みと見なし、そのまま詳細へ進む（利用者には**見えない失敗**）。また同期実行だったため、
画面は数百秒待たされ、待ち切れないと**受理できたかどうか**も分からなかった（重複起動の恐れ）。

- **受理の応答を失った回**（タイムアウト・通信断）は、記録に最終まとめの行があるかを問い合わせて
  から判断する（あった＝受理されている）。**二つ目のタスクを作らない**。
- **防重は DB の条件つき更新**（画面のボタンやメモリの真偽値に頼らない）。同時に何本来ても
  受理は 1 回だけ（実 DB の統合試験 `ClassroomNoteGenerationClaimIT` で固定）。
- **走っている・できているときは再試行の入口を出さない**（永久に「生成中」を出さない・
  完了済みに AI をもう一度呼ばない）。AI の**実行**失敗（`FAILED` の行）は【再試行】でやり直せる。

## なぜ「最終まとめの行がある」を受理の証拠にしないか（2026-09-19 改修・第 6 段）

**決めたこと**: 最終まとめの起動を確かめるのは「**同じ `noteId` の状態**」にする。
`GET /api/user/classroom/{recordId}/notes/{noteId}` を足し、状態の意味を固定する:

- `PENDING` … **user-api が行を作った**だけ。admin-api の実行が受理された証拠ではない
  （終了のときに先に作るので、起動が届かなくても行は在る）。画面は**作成の入口を出す**。
- `GENERATING` … 実行が**受理されている**（実行の仕組みが管理している）。
- `READY` … 完成（**AI をもう一度呼ばない**）。
- `FAILED` … 失敗。**やり直せる入口を出す**。
- 状態の問い合わせが失敗したら「**確認できない**」（成功とも失敗とも決めない）。

**なぜか**: どこにも接着していない**安定した答えが無い**ままページを表示していた。画面は
`notes.some(kind === 'FINAL')` で判定していたため、user-api が先に作った `PENDING` の行だけで
「起動できた」と誤判定し、admin-api に届いていなくても成功として扱っていた（利用者には
見えない失敗）。詳細画面は `FAILED` のときしか入口が無く、**未着手のまま永久に「作成中」**に
見えていた。

**起動の確認**: `POST .../notes/{noteId}/run` の応答が `GENERATING`/`READY` なら受理。応答が
`PENDING`・欄が無い・失ったときは、**同じノートの状態を問い合わせて**から決める
（`GENERATING`/`READY`＝受理済み／`PENDING`＝未受理／`FAILED`＝失敗／問い合わせも失敗＝確認できない）。
録音の終了（`/end`）と STT の収尾はこの経路では**呼ばない**（まとめの操作だけを行う）。

## なぜ受理したら必ず「けり」を付けるか（2026-09-19 改修・第 6 段 ③）

**決めたこと**: 起動を受理したら、どの失敗位置でも**記録にけりを付ける**（`GENERATING` のまま
放置しない）: バッチが忙しくて断られた（`NOTE_ENGINE_BUSY`）／設定不足・未実装・例外
（`NOTE_ENGINE_FAILED`）／実行はされたが失敗・スキップで終わった／実行器の起動そのものに失敗した。
**実行器の起動に失敗しても、長い AI をその場で走らせない**（受理の応答は既に返している）。

**なぜか**: 以前は `accept()` が `GENERATING` にしてから背景へ渡し、背景の例外を**ログに書くだけ**
だった。同じ `batchCode`（batC62）が別の授業で走っていると防重で断られ、その授業のまとめは
**誰も実行しないまま `GENERATING` のまま**残る（画面は永久に「作成中」）。

**試行の識別（`生成トークン`）**: 受理のたびに新しいトークンを書き、`markGenerating`／
`updateReady`／`updateFailed`／`markGenerationFailed` は**トークンが一致するときだけ**通す。
古い実行が遅れて返ってきても、新しい試行の状態や**既にできた READY** を上書きしない。

**失われた実行の回復**: 判定は**実行記録**で行う（経過時間だけで「死んだ」と決めない）:
そのバッチの `QUEUED`/`RUNNING` があれば**生きている**（触らない）。無いまま猶予
（30 分）を過ぎた `GENERATING` は失われたとみなし、`POST /api/admin/batch/classroom/notes/recover`
（または同じ判定を行う `recoverLostGenerations`）で**やり直せる失敗**に戻す。既存の
`GENERATING` のうち実行記録が生きているものは**触らない**（一括リセットしない）。

## なぜ「やり直せる結果」で収尾の約束を捨てるか（2026-09-19 改修・第 7 段 ①）

**決めたこと**: `SourceStream.finish()` は**走っているあいだだけ**約束を共有し、終わったら
**もう一度やる必要がある結果のときは約束を捨てる**（`needsFinalizeRetry`）。捨てる条件は
結果そのもの（`finalizeResult`）で決める:

| 結果 | 約束 | 理由 |
|---|---|---|
| `COMPLETE` / `NO_AUDIO` / `NO_UTTERANCE` | **残す**（再利用） | 同じ音を二度締めない・成功した音源をやり直さない |
| `INCOMPLETE_UNRECOVERABLE` | **残す** | やり直しても直らない。画面は「そのまま終える」を出す |
| `PENDING` / `RETRYABLE_FAILURE` / `UNKNOWN` / 結果なし・例外 | **捨てる** | やり直すと**本当に後端へ行く**必要がある |

**なぜか**: 以前は `finishError` があるときだけ捨てていた。`UNKNOWN`（確認できない）と
`PENDING`（まだ途中）は `finishError` を立てないので約束が残り、画面が【続きをやり直す】を
出しても **`finish()` が古い約束を返すだけ**で後端へ行かず、永久に終われなかった。

- **ページ側も同じ**: `sttFinishing` / `sttFinishOutcome` をやり直しの前に捨てる
  （捨てないと、`SourceStream` が正しくてもページで止まる）。
- **新しい回の前に一時状態を戻す**: `finished`（常時接続の「届いた」印）・`finishError`・
  `finalizeResult` を戻す。**音声のキュー・フレーム番号・時間軸・欠落の記録は触らない**
  （送り直しに必要）。既存の WebSocket→HTTP 退避の仕組みはそのまま使う（2 本目の経路を作らない）。

## なぜ実行の生存を「そのまとめの実行」で見るか（2026-09-19 改修・第 7 段 ②）

**決めたこと**: ノートに `生成実行ID`（**この試行を実行しているバッチ実行記録の ID**）を持たせ、
失联判定は `ClassroomNoteMapper.findGenerationExecution`（**そのノートの実行だけ**を引く 1 文）で行う。
`AI呼出履歴ID` は AI 呼び出しログの ID なので**混ぜない**（`markGenerating` は実行IDを専用列へ書く）。

判定は 4 つ:

- `RUNNING` … 実行記録が `QUEUED`/`RUNNING` で、**このプロセスの起動識別子**。長く走っていても触らない。
- `BINDING` … 受理直後で実行記録がまだ無い**短い窓**。回収しない。
- `LOST` … 実行記録が終わっている／消えている／**別プロセスの起動識別子**（＝そのプロセスはもう居ない）。
- `UNKNOWN` … 実行記録を**確かめられなかった**（DB エラー）。**死んだと決めない**。

**なぜか**: 以前は `findRunningByBatchCode("batC62")` で「どこかの batC62 が走っているか」を見ていた。
**別の授業の正常な生成**が、このまとめの遺留回収を止めてしまう（逆に、実行記録が残ったままだと
永久に `GENERATING`）。プロセスの起動識別子を見れば「その実行はもう居ない」と言える。

**回復の入口（実際に呼ばれる）**: 詳細画面の【状態を確認／復旧】→
`POST /api/admin/batch/classroom/notes/{noteId}/recover`（**1 件だけ**。普通の利用者が全庫回復を
叩けない）。判定は後端が行い、`LOST` のときだけ `FAILED`（`NOTE_ENGINE_BUSY`）へ戻す。
`RUNNING`/`BINDING`/`UNKNOWN` は**何もしない**。回復は**版を進める**ので、旧スレッドが遅れて
**成功を書いても楽観ロックで弾かれる**（トークンの照合と二重に守る）。
管理者向けの一括回復 `POST .../notes/recover` も残す（実行記録が生きているものは触らない）。

## なぜ授業まとめの起動・回復を user-api 経由にしたか（2026-09-19 改修・第 8 段）

**決めたこと**: 画面は admin-api の内部入口（`/api/admin/batch/classroom/notes/**`）を**直接叩かない**。
画面 → `POST /api/user/classroom/{recordId}/notes/run?noteId=` / `.../notes/{noteId}/recover`
（**user-api**）→ サービス間の合言葉つきで admin-api、という順にする。

**なぜか**: admin-api の内部入口は `noteId` しか見ておらず、`/api/admin/batch/**` は既存のバッチ管理
UI の都合で `permitAll` だった。そのため**noteId を差し替えるだけで他人のまとめを起動・回復**できた
（`noteId` は連番なので推測も容易）。「内網だから」「画面にボタンを出さないから」は守りにならない。

**確かめる順序（user-api）**: ①ログイン（Spring Security・`/api/user/classroom/**` は認証必須）
②**授業の所有権**（`requireOwner`。他人の記録は 404＝存在を漏らさない／見えるが操作できない記録は 403）
③**noteId がその recordId のものか**（別の記録・他人のノートは **404**）
④回復は**種別が `FINAL`** だけ（途中のフェーズ分析は 400）。前端から来た accountId・operator・
ロールは**認証の根拠にしない**（operator は監査用に user-api が `user:{accountId}` を作る）。

**admin-api 側**: `/api/admin/batch/classroom/**` に**具体的な規則を広い `permitAll` より前**に置き、
サービス間の合言葉（`X-Internal-Token`）を要求する（`InternalServiceAuthorizer`）。合言葉が
**未設定なら全て拒否**（匿名に落とさない）。値は環境変数 `STUDY21_INTERNAL_TOKEN` から読み、
リポジトリ・前端・URL・ログには置かない。定数時間で比較する。無関係な `/api/admin/batch/**`
（スケジュール設定など）は**そのまま**（閉めると別の機能が止まる）。

**失敗の見せ方**: 下流が拒否・不調なら「成功」を返さない（`ClassroomNoteAdminClient` は例外にする）。
画面は 401（入り直し）・403（権限）・404（見つからない）を**区別した文言**で出し、
**無限に再試行しない**。まとめの起動・回復は録音の終了や STT の収尾を呼び直さない。

## なぜ AI の 4xx に「プロバイダーが返した理由」を付けるか（2026-09-25 改修）

**決めたこと**: AI の呼び出しが 4xx のとき、画面・`BAT_バッチ実行履歴情報`・`BAT_AI呼出履歴情報`・
`JPN_AI生成履歴情報` に残る文言は、定型文（「AI がリクエストを受け付けませんでした（HTTP 400）。
API Key とモデル名を確認してください。」）**だけにしない**。プロバイダーが返した本文（理由）を
「詳細: ...」として後ろに付ける（`AiErrorMessages.clientError`。改行は空白へつぶし、500 文字で切る）。

**きっかけ（実際に起きた失敗）**: 日本語単語の AI 取得（`batC41`）が 10 語すべて HTTP 400 で失敗した。
画面と履歴には定型文しか無く、「API Key とモデル名」を疑って設定を見直すことになったが、
本当の原因は **DashScope（阿里雲 Model Studio）のアカウント残高不足**だった:

```
HTTP 400 {"error":{"message":"Access denied, please make sure your account is in good standing.
For details, see: https://help.aliyun.com/zh/model-studio/error-code#overdue-payment",
"type":"Arrearage","code":"Arrearage"}}
```

- モデル名（`qwen3.7-plus`）は有効（`GET /compatible-mode/v1/models` に出る）。API Key も有効
  （`/models` は 200 で通る）。**同じキーの Qwen 系は全部同じ 400**（`qwen3.7-flash` / `qwen3-vl-plus` /
  `qwen-plus` / `qwen3-max` で確認）なので、機能側の設定では直らない。
- 理由は `GeometryAiLangChain4jClient` の **WARN ログにしか**出ていなかった（`log.warn(... message={})`）。
  運用者が見る画面・履歴からは分からず、切り分けに時間がかかった。

**なぜこの形か**:

- 定型文は「設定を疑え」と言うが、4xx の原因は設定とは限らない（残高不足・利用停止・内容フィルタ・
  レート制限の変種）。**プロバイダーが言ったことをそのまま見せる**のが最短。
- 例外メッセージ（LangChain4j）／応答本文（自前 HTTP クライアント）に理由が入っているので、
  新しい通信は増やさない（**課金も増えない**）。長さは 500 文字に切って、トーストと履歴が読める範囲に保つ。
- 文言の組み立ては `com.study21.admin.ai.AiErrorMessages` の 1 か所（AI を呼ぶ 3 実装が共有。
  特定の機能パッケージへ依存させない）。

## なぜ一覧の「品詞」「中国語訳」を有効版の詳細から引くか（2026-09-25 改修）

**決めたこと**: 単語情報管理の一覧（`GET /api/user/japanese/words`）は、

- **品詞** = `COALESCE(NULLIF(BTRIM(単語情報.品詞), ''), 有効版の詳細.品詞)`
- **中国語訳** = 有効版の詳細の**最初の語義の中国語**（語義が無い版だけ `説明_中国語` へ戻す）

を返す。**`単語情報` に中国語訳の列は作らない**（`JpnWordMapper.xml` の d / sense の LATERAL）。

**なぜ**:

- 利用者の指摘: 「詳細情報取得（A・B）のあと、一覧の**品詞と中国語訳が出ない**」。

  品詞がある状態で一覧に出る・品詞で絞り込める・人が直した品詞が優先）。

## なぜ単語一覧の「分類（To）」を実装したか（2026-09-25 改修）

**決めたこと**: 単語情報管理の検索条件「分類：From ～ To」を**範囲**として実装する。
API は `categoryFrom` / `categoryTo` を受け取り（**片方だけでもよい**）、SQL は
**同じ収録の行**で `分類 >= From AND 分類 <= To` を見る。画面にあった

**なぜ**:

- それまでは From だけが `分類 ILIKE '%…%'`（部分一致）で効き、**To は選べるのに何も起きなかった**

- 教材の課次は `Unit001`〜 のように**順番を持つ**ので、絞りたいのは「この Unit からこの Unit まで」。
  テスト作成（種別 C〜E）は既に `分類 >= From` / `分類 <= To` で絞っており、**一覧だけが揃っていなかった**。
- 両端を**1 つの `EXISTS`** で見るのは、別々の `EXISTS` だと「別の Unit で From を満たし、さらに別の
  Unit で To を満たす語」まで拾ってしまうため（同じ収録の中で範囲に入っていることを条件にする）。
- 種別 **A・B の出題元**（`buildWordEntries`）も同じ範囲で絞るようにした。テストの条件（書籍・分類）は
  C〜E と同じなのに、A・B だけ範囲外の語を選択肢に混ぜていた。
- 確かめ方: `JpnWordMapperSqlTest`（範囲の SQL 契約）＋ 実 DB の
  `JapaneseRepositoryTest#filtersWordsByCategoryRange`（From だけ／To だけ／両方）＋
  `tests/japanese-word.spec.ts`（送るクエリと、注記が消えたこと）。

## なぜ AI 取得の待ち時間を 60 秒に揃えたか（2026-09-27 追記）

**決めたこと**: 日本語単語の AI 取得（`POST /api/admin/batch/japanese-word-ai/run`）の
**HTTP 待ち時間を 60 秒**にし、**nginx の `proxy_read_timeout` も同じ 60 秒を明示**する。
利用者の指示（「调用 AI 时前端不需要等待后端的结果，把这两个时间统一成 60 秒」）。

- フロント: `frontend/pc-web/src/api/japanese.ts` に `AI_RUN_TIMEOUT_MS = 60_000` を置き、
  `runJpnWordAi` が `timeoutMs` として渡す。共通クライアントの既定（`HttpClient.ts:5` の
  **10 秒**）は一覧・保存のような短い呼び出し向けで、**同期で走る長い AI 呼び出しには短すぎた**。
- nginx: `deploy/docker/nginx.conf` の `/api/admin/`（PC と Mobile の 2 か所）へ
  `proxy_read_timeout 60s;` を**明示**した。既定も 60 秒なので実効は変わらないが、
  「フロントと同じ値」であることを設定ファイルに書き残すのが目的（片方だけ変える事故を防ぐ）。
- **前提の訂正（重要）**: この API は**同期**で、AI が終わるまで応答が返らない。
  「呼び出しが非同期だから前端は待たなくてよい」わけではない。断連しても**サーバー側の処理は
  止まらない**（同期処理を中断する仕組みが無い）が、**画面は結果を受け取れない**ので、
  60 秒を超える取得は画面では失敗として見え、一覧も読み直されない（結果は DB に残る）。
  数を制限しているのは時間ではなく **`MAX_WORDS_PER_RUN`（50 語）**と設定値であり、
  時間の上限は「件数」には効かない（利用者の理解どおり）。
- 本物の非同期（受付だけして背景で走らせ、画面は進み具合を見る）は**未実装**
  （設計書 §11。授業ノートの `accept` ＋ポーリングが手本）。60 秒を超える取得を画面で
  待ちたい／結果を確実に反映したいなら、そちらへ寄せる。
- 確かめ方: `tests/japanese-word-ai-timeout.spec.ts`（10 秒では切らず、60 秒で切れる。
  `AI_RUN_TIMEOUT_MS` が 60,000 であることも固定）。実機は Chrome（`--virtual-time-budget`）で
  **30 秒かかる応答**を返すスタブを使い、`abort=false`・成功のトーストが 31.5 秒で 1 件だけ
  （＝10 秒のタイムアウトが起きない）を確認（`tmp/jpn-data-tab/ai-timeout-60s.png`）。
  nginx 側は 2 か所とも `proxy_read_timeout 60s;` があることと括弧の対応を確認。
- **デプロイ注意**: `nginx.conf` は `web` イメージに焼き込まれるので、反映には `web` の再ビルドが必要
  （`docs/DOCKER_DEPLOYMENT.md` §6.1）。

## なぜ日本語単語の AI 取得を非同期（受付＋働き手）にしたか（2026-09-27 追改修）

**決めたこと**: 画面からの AI 取得を**受付**と**実行**に分ける。利用者の指示「请改成异步处理」。

1. **受付**（`POST /api/admin/batch/japanese-word-ai/run`）: `JPN_AI生成履歴情報` に
   **`QUEUED` の行を積んで即返る**（AI は呼ばない）。応答は
   `{"accepted":N,"reused":M,...}`。1 回の受付は **50 語**まで（利用者の選択。
   設定値ではなく受付の上限。語数を分けて受付ける）。
2. **働き手**（`JapaneseWordAiWorker`）: 起動時に開始し、**5 秒ごと**に
   **設定 `THREADS` の 4 バッチ最小値**だけ確保して並列実行する。`RUNNING` のまま残った行は
   **5 分後**に拾い直す。失敗（`FAILED`）は拾わない（利用者のやり直しだけが再開する）。
3. **画面**: 受付のあと**一覧を 3 秒ごとに読み直し**、受付けた語の「取得中」が消えたら
   結果（成功・失敗の件数）を知らせる。30 分で打ち切り、そのときは【再読み込み】を促す。

**なぜ**:

- 同期だと**HTTP の待ち時間が実質の上限**になる。実際、画面側の既定 10 秒・nginx の 60 秒で
  切られ、AI が終わる前に「失敗」と表示されていた（§「なぜ AI 取得の待ち時間を 60 秒に揃えたか」）。
  時間の上限を緩めても、数十語を待たせる画面は使いにくい。
- **待ち行列は新しい表を作らない**。`JPN_AI生成履歴情報` が元から
  `QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELED` と部分索引 `idx_jpn_ai_gen_active`
  （`WHERE 状態コード IN ('QUEUED','RUNNING')`）を持っており、**1 語 × 1 内容種別 = 1 行**が
  そのまま仕事の単位になる。一覧の「取得状態」も既にこの表のビューなので、**進み具合の表示は
  既存のまま**（取得中＝黄）で足りる。
- AI 生図の働き手（`GeometryAiWorker`）と同じ型にする（起動時に開始・一定間隔・落ちた行の拾い直し・
  失敗で止まらない）。**新しい流儀を持ち込まない**。

**二重に走らせない規則は 2 つ**（どちらも既存の索引が効く）:

1. 受付: 同じ語 × 内容種別に**実行中の行**（`QUEUED` / `RUNNING`）があれば積まない
   （`findActiveGeneration`。`reused` として数える）。
2. 取り出し: `FOR UPDATE SKIP LOCKED` で 1 件選び、**状態を条件にした更新**
   （`markGenerationClaimed`）で確定する。他の働き手が先に取っていれば 0 行になり、実行しない。

**「すべて再取得」の意味を直した**: 受付は `findTargets`（**成功済みを除く** SQL）を使わず、
画面が選んだ語をそのまま積む。除くのは実行中の行だけ。これで「すべて再取得」は
**新しい版で取り直す**という意味になり、以前の「窓には『取り直します』と書いてあるのに
SQL が成功済みを除くので実際は何も起きない」という食い違いが消えた（利用者の選択 2026-09-27）。

**変わらないもの**:

- `AI_RUN_TIMEOUT_MS`（フロント 60 秒）と nginx の `proxy_read_timeout 60s` は**そのまま**
  （受付は数十ミリ秒で返るが、両者を揃えておく規則は維持。サーバーが混んでも理不尽に早く諦めない）。

## なぜ AI 取得の様子見で「静かな読み直し」を使うか（2026-09-27）

**症状（利用者の報告）**: AI 取得を受付けたあと、**画面がずっとちらつく**。

**原因**: 様子見（3 秒ごと）が一覧の再取得に**普通の読み直し**を使っていた。普通の読み直しは
`loading` を立てるので、一覧のカードが `v-else-if="loading"` で
**「読み込んでいます...」に差し替わり**、取得が返ると表が組み直される。つまり 3 秒ごとに
表が消えて出る＝ちらつき。ほかに、行のオブジェクトを作り直していたこと（表全体の描き直し）と、
受付の直後の読み直しも同じ問題を起こしていた。

**直したこと**:

1. `loadWords({ quiet: true })` を足した。静かな読み直しでは **`loading` を立てない**
   （＝表を差し替えない）、**行の同一性を保って取得状態だけ写す**（`mergeWordStates`）、
   選択肢の作り直しをしない、失敗しても黙って見送る（次の周期でまた試す）。
2. 様子見（`pollAcquired`）と**受付の直後**の読み直しを静かにした。利用者が自分で押した
   【検索】【再読み込み】は今までどおり（待っていることが分かるように「読み込んでいます...」を出す）。

**確かめ方（実測。Chrome + MutationObserver で数えた）**:

| 指標（様子見 3 周期） | 直す前 | 直した後 | 対照群（AI 取得を押さない） |
|---|---|---|---|
| 表が外された回数 | 4 | **0** | 0 |
| 表が入り直した回数 | 5 | **1**（初回表示のみ） | 1 |
| 「読み込んでいます」が出た回数 | 11 | **3**（初回表示のみ） | 3 |
| ボタンの disabled が変わった回数 | 17 | 6 | 2 |
| DOM 変化の合計 | 104 | 66 | 35 |

直した後の残り（表の初回表示と loading の 3 回）は**対照群と同じ**＝様子見によるものではない。
差分の DOM 変化（35 → 66）は**取得状態のタグの更新**（これは出したい変化）。

**回帰テスト**: `tests/japanese-word.spec.ts`「様子見のたびに一覧を組み直さない（画面がちらつかない）」。
様子見の周期に入った直後に「読み込んでいます…」が出ないこと・検索ボタンが無効にならないこと・
取得が返っても**同じ表の要素**のままであること・取得状態は新しくなることを固定する
（直す前は赤、直した後は緑を確認）。

## なぜ AI 取得の対象を「検索条件に一致する語」にしたか（2026-09-27 追改修）

**決めたこと**: 一覧の右上【AI 取得】の対象を、**当ページの語ではなく「いまの検索条件に一致する語」**

   「把这个限制去掉，只使用设定页面的「1回の最大単語数」来进行限制」）で、**コード側の上限定数も

   - 設定が読めない・数値でない・範囲外のときは**例外にして受付しない**
     （`SettingsService#requireGlobal`）。`SettingsService` の方針（プログラム既定値・
     フォールバックを持たない）と同じで、かつ**実行そのものも設定が無ければ始まらない**

**踏んだ落とし穴（実 DB テストで発見）**:

1. MyBatis の OGNL では **`'C'` は char** になり、`kind == 'C'` は String と比べようとして
   `NumberFormatException` になる（`'DETAIL'` は複数文字なので String として動くため、
   DETAIL だけ通って C で落ちた）。**1 文字の比較は `"C"`（二重引用符）**で書く。
2. **素の `AND` を `<where>` の外に書くと条件が効かない**。`<where>` は条件が 1 つも無いと
   `WHERE` を出さないので、外に書いた `AND (…) IS DISTINCT FROM 'SUCCEEDED'` は直前の
   `LEFT JOIN LATERAL (…) ai ON TRUE` の **ON に付いてしまう**。LEFT JOIN では ON が偽でも
   行は残る（ai の列が NULL になるだけ）ので、**絞り込みが空のときだけ「取得済みをスキップ」が
   無効**になり、成功済みの語にもう一版積む＝無駄な課金になる。
   対策として `WordWhere` から `<where>` を外し、**呼ぶ側**（count / search / countAiTargets /
   findAiTargets）が `<where>` で包む形にした。`findAiTargets` はその**中**にスキップの条件を足す。
   見つけたのは実 DB のテスト（`JapaneseRepositoryTest#skipsAcquiredEvenWithoutFilters`）で、
   絞り込み無しのときに「窓の数（候補）と実際に送る語数が食い違わない」ことを確かめている
   （文字列一致のテストはこの形を見逃した）。

**確かめ方**: `JpnWordMapperSqlTest`（一覧と同じ断片を使う・同じ並び・状態の条件・C のまとめ方）、
`JapaneseServiceImplTest`（件数と上限の丸め・区分の検証）、`JapaneseRepositoryTest`（**実 DB** で
SQL が動き、登録した語が対象になり、上限で切られ、C でも動く）、
`JapaneseWordAiBatchControllerTest`（受付上限は設定値／200 の兜底）、
画面は `tests/japanese-word.spec.ts`（対象はサーバーが選ぶ。窓の文言は「検索条件に一致する N 語」）。
