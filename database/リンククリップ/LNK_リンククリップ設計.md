# Study 2.1 リンククリップ DB設計

## 所有権

リンククリップは資料とは異なり、親子共有ではなく**アカウント個人所有**とする。
2.0でも `liu`（保護者）10件、`ljz`（生徒）3件が別々に保存されていたため、
2.1では `所有者アカウントID` をすべての検索・更新・削除条件に含める。

| 2.0ユーザー | 2.1ログインID | 種別 | 移行件数 |
|---|---|---|---:|
| `liu` | `bruss.ji.liu@gmail.com` | GUARDIAN | 10 |
| `ljz` | `ricky.jingze@gmail.com` | STUDENT | 3 |

## テーブル

### `LNK_リンククリップ情報`

リンク、概要、状態、閲覧統計をまとめて管理する集約ルート。

- 2.0の文字列 `ユーザーID` を `ACC_アカウント` への外部キーへ変更。
- 日本語の保存先値を安定したコード `INBOX / READ_LATER / LEARNING / REFERENCE / DONE` へ変更。
- フラグ文字列 `'0'/'1'` を PostgreSQL `BOOLEAN` へ変更。
- ローカルファイルを `ソースコード=LOCAL_FILE / クリップ種別=FILE` として明示。
- 複数端末更新用に `バージョン` を追加。更新SQLは所有者と変更前バージョンを同時に照合する。
- URL正規化は重複候補検索に使うが、2.0の動作を変えないため一意制約にはしない。

### `LNK_リンククリップタグ情報`

タグはリンククリップ集約内の子情報とし、親への外部キーを追加する。
親削除時は `ON DELETE CASCADE`。1クリップ内では大文字小文字だけが異なる重複タグを禁止する。

## 2.0から削除した列

| 列 | 調査結果と判断 |
|---|---|
| クライアントリンクID | 全13件がNULL。オフライン同期処理も実利用されていないため削除 |
| 縮略ファイルSEQ | 全13件がNULL。外部サムネイルURLだけを維持 |
| 表示順（主表） | 全13件が0で、一覧SQLも使用していないため削除 |

タグ側の表示順は実際のタグ表示に必要なため維持する。

## ローカルファイルリンクの扱い（2.1 実装方針）

2.0 は `openLocalFile` でサーバ経由でファイルを配信していたが、2.1 のサーバは NAS 上にあり、
クライアント PC のローカルパスを開けない。そのため 2.1 では次のように扱う。

- `ソースコード=LOCAL_FILE / クリップ種別=FILE` として保存し、一覧ではローカルファイルとして表示する。
- 「開く」操作は行わず、**パスを表示してコピーできる**ようにする（ブラウザから `file://` は開けないため）。
- URL は 2.0 の値をそのまま維持する（`file:///D:/...` 形式）。

## 移行前調査

- 主表13件、タグ5件、孤児タグ0件。
- URL、URL正規化、ページタイトルの欠損0件。
- URL正規化の同一ユーザー内重複0件。
- 概要8件、AI概要1件、外部縮略画像URL 8件。
- お気に入り0件、既読5件、アーカイブ1件、総閲覧回数23回。
- ローカルファイルリンク1件。リンク文字列は移行するが、NAS上のWebアプリからクライアントPCの
  ローカルパスを直接開けるとは限らないため、機能実装時に専用の扱いが必要。

## 移行の安全性

`MIG_LNK_リンククリップ_20260911.sql` は次を満たす。

1. 旧ユーザーと2.1アカウントの対応を種別込みで検査。
2. 未対応ユーザー、必須値欠損、不明コード、孤児タグ、重複タグがあれば全体を中止。
3. 2.0のリンククリップIDを維持し、タグの参照先も同じIDへ変換。
4. 再実行時に同一IDの異なるデータを検出した場合は上書きせず中止。
5. 移行後に主表・タグ件数を照合し、採番シーケンスを最大IDへ同期。
