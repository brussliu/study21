#### `詳細JSON` の構造

```jsonc
{
  // 2.0 の STY_日本語単語詳細情報（本体）の列
  "jlptLevel": "N3", "partOfSpeech": "名詞", "conjugation": null, "transitivity": "NONE",
  "importance": 4, "chineseMeaning": "爱；爱情；喜爱",
  "descriptionJa": "人や物、ことなどをとても大切だと思い…", "descriptionZh": "…",
  "structuredSchemaVersion": "jp-schema-v1", "manuallyCorrected": false,
  "structured": { /* 2.0 の 構造化JSON（AI の生の結果）をそのまま */ },
  // 2.0 の 6 子テーブル（配列は 2.0 の 表示順 の昇順）
  "senses":         [{ "number": 1, "japanese": "…", "chinese": "…", "context": "…", "style": "NEUTRAL", "noteJapanese": null, "noteChinese": null }],
  "examples":       [{ "japanese": "…", "reading": "…", "chinese": "…", "contextJapanese": "…", "contextChinese": "…", "source": null, "senseNumber": null }],
  "pronunciations": [{ "reading": "あい", "accentNotation": "1", "accentType": 1, "moraCount": 2, "audioUrl": null, "audioProvider": null }],
  "collocations":   [{ "expression": "愛を込める", "reading": "あいをこめる", "chinese": "…", "exampleJapanese": "…", "exampleChinese": "…" }],
  "relatedWords":   [{ "relatedWordId": null, "relationType": "CONFUSABLE", "heading": "恋", "reading": "こい", "chinese": "…", "differenceJapanese": "…", "differenceChinese": "…", "eCandidate": false }],
  "cautions":       [{ "noteType": "USAGE", "japanese": "…", "chinese": "…", "wrongExample": "…", "correctExample": "…" }]
}
```

各要素のキーは **2.0 の列名を camelCase にしたもの**（`意味_日本語` → `japanese`、`アクセント表記` → `accentNotation`）。
これは 2.0 の AI 構造化JSON（`STY_日本語単語詳細情報.構造化JSON` のルート直下）とほぼ同じ形で、
実際に `構造化JSON` の要素キーは `{number?, japanese, chinese, context, style, noteJapanese, noteChinese}` /
`{expression, reading, chinese, exampleJapanese, exampleChinese}` / `{noteType, japanese, chinese, wrongExample, correctExample}`
と一致している。**`cautions` だけは AI 側が `usageNotes` という名前だった**が、
2.1 のキー名は `cautions` に統一した。

#### 詳細を JSONB に集約した理由

1. **検索対象ではない。** この詳細は「AI が生成した読み取り専用の参考情報」で、
   画面は 1 語ぶんをまとめて表示するだけ。子テーブルに分けても JOIN と並び替えが増えるだけで、
   正規化の利点（部分更新・部分検索・部分集計）を一切使わない。
2. **1 語 1 詳細で増えない。** `uq_jpn_detail_word` により詳細の行数は語数と同じ 383 行。
   子テーブルに分けると 6 テーブル・4,135 行になるが、得られるものが無い。
3. **中身を引きたいときは GIN 索引がある。** `idx_jpn_detail_json` でキー・値を横断で引けるので、
   「例文に特定の語が出る詳細を探す」ような用途には後から対応できる。
4. **AI の再取得で形が変わりうる。** プロバイダ・モデル・スキーマ版が変わるたびに
   6 テーブルの列を移行するより、JSONB 1 列のほうが素直（`content_version` で版を残す）。

本体の列（`品詞`・`代表中国語意味`・`日本語説明`・`中国語説明` など）も **捨てずに同じ `詳細JSON` の
トップレベルに入れている**。2.1 の詳細テーブルに列として置くと、AI の取得項目が増えるたびに
`ALTER TABLE` が要るため、詳細は「1 つの読み取り専用の塊」として JSONB に持つ。
`structured` に 2.0 の生の `構造化JSON` をそのまま残しているので、正規化前の情報も失われない。

- 索引: `idx_jpn_question_word`（`単語ID`, `問題種別`）／`idx_jpn_question_type`（`問題種別`, `状態コード`）／
  `uq_jpn_question_old_id`。
- **`問題種別` に CHECK を付けない。** 種別は今後増えうる（B 用の問題を作る等）ので、
  値を増やすたびに `ALTER TABLE` が要る形にしない。値はこの文書とコメントで列挙する。
- **`状態コード` の CHECK は 2.0 のコードをそのまま用意した**（`GENERATED` / `ACTIVE` / `REJECTED` / `ARCHIVED`）。
  実データに `ARCHIVED` が 175 件あるので、`ACTIVE`/`INACTIVE` だけにすると移行できない。

### 課題テーブルと回答履歴を 2.1 では持たない理由

2.0 は **テスト → 出題（1 語）→ 課題（A_STUDY / B1_ORTHOGRAPHY / B2_READING / C1_READING / C2_KANJI /
D_CONTEXT_MEANING / E_KANJI_USAGE の段階別。1,326 件）→ 回答履歴（1 試行ごと。1,113 件）** の 4 階層だった。
2.1 は **テスト → 出題** の 2 階層にし、**テスト結果は `JPN_テスト出題情報` の
`出題状態`・`最終判定`・`回答回数`・`誤答回数` で表す**。

1. **課題テーブルの役目は中断再開だった。** 2.0 は「B1 は終わったが B2 が途中」を正確に持つために
   課題を別テーブルにしていた。2.1 のテストは 1 語ぶんを続けて出題する（B なら B1 → B2）ので、
   **`出題状態` が `PENDING` の先頭から再開すれば足りる**（2.0 の `V_日本語単語テスト再開位置` と同じ結果が
   `出題情報` だけで求まる）。
2. **回答履歴は集計にしか使っていなかった。** 2.0 の画面に出していたのは 回答回数・誤答回数・正誤 だけで、
   1 試行ごとの選んだ選択肢は表示していなかった。同じ情報は `回答回数`・`誤答回数`・`最終判定` で足りる。
3. **行数が効く。** 回答履歴は 1 問 1 行で、教材 9,847 語を全問解くと数百万行になる。
   2.1 は SQL ログを含めて DB を軽く保つ方針（`docs/LOGGING.md`）なので、持たない。
4. そのため 2.0 の `課題数` / `完了課題数` / `正解課題数` / `不正解課題数` は
   `出題数` / `完了出題数` / `正解数` / `不正解数` に集約した。
   **B は 1 語 2 課題なので `正解数 + 不正解数 > 出題数` になりうる**（実データで 170 + 10 > 90）。

### 代表 JLPT レベルが実データ全件 NULL である件

2.0 の `STY_日本語単語母表.代表JLPTレベル` は **9,847 件すべて NULL**。
一方 `STY_日本語単語詳細情報.JLPTレベル`（383 件）には N1〜N5 が入っており、
`STY_日本語単語収録情報.レベル` は **全件 `'N1-N5'`** で、教材は
`書籍='01.N1~N5日本語単語'` の 1 冊しかない。

つまり 2.0 の日本語教材は **N1〜N5 を 1 冊にまとめた構成**で、語ごとの JLPT レベルは
母表には入っていない（AI 詳細を取った 383 語にだけ入っている）。

2.1 の扱い:

- `JPN_単語情報.JLPTレベル` は **2.0 の `代表JLPTレベル` をそのまま移行する（＝全件 NULL）**。
  勝手に AI 詳細の `JLPTレベル` を母表へコピーしない。2.0 の意味（代表値）と食い違ううえ、
  383 語だけ値が入った「半分埋まった代表値」になるため。
- **語のレベルを出したい画面は `JPN_単語収録情報.レベル` を使う**（`N1-N5`）。
  語ごとの JLPT が必要になったら、AI 詳細（`詳細JSON.jlptLevel`）を語の属性として
  昇格させるかを相談する（§5）。
- `JPN_単語情報.JLPTレベル` には 2.0 と同じ `N1`〜`N5` の CHECK を残してある
  （誰かが後から埋めるときに表記ゆれを防ぐため）。
- 単語情報管理画面の「JLPT レベル」絞り込みは、**値が 1 件も無い**ので
  実質「収録のレベル（N1-N5）」で絞ることになる。UI 側の表示は要相談（§5）。

  `jlptLevel`・`partOfSpeech`・`stateCode`・`book`・`category`・`learnState`・`favorite`・`learned`。
- **詳細ダイアログ**は「収録（教材のどこに載っているか）」「語義・例文など（`詳細JSON`）」
  「詳細／C〜E 問題（`JPN_単語問題情報` の種別ごとの有無）」をタブで見せる。
  `詳細JSON` は読み取り専用（AI が生成した参考情報）。
- 登録・修正ダイアログは 見出し語・読み・JLPT レベル・品詞・状態コード・備考（＋ `バージョン` で楽観的ロック）。
  2.0 の「詳細情報取得（A・B）」「C 読み問題取得」「D 文脈問題取得」「E 漢字問題取得」ボタンは
  **2.1 では AI 取得の API が無いので置かない**（§5）。
- 削除は確認ダイアログ。`ON DELETE CASCADE` にしてある子（**収録・詳細・学習状況・技能習得**）は
  語と一緒に消える。一方 **`問題`・`テスト出題` は `ON DELETE CASCADE` にしていない**ので、
  それらを持つ語を消そうとすると FK で止まる（実測で確認）。サービス側で
  「問題・出題を先に消してから語を消す」順に処理する。AI が生成した問題は捨てたくない資産で、
  テストの出題も履歴なので、語の削除で黙って消えないほうが安全という判断（§5 の確認事項）。

```

  │ JPT20260831-…-e3b22b │ ― │ 01.N1~N5日本語単語 │ Unit001〜Unit005 │ 完了 │ ALL │ A │ 8/31〜8/31 │ 90/90 │ ― │ 69分 │ [実施][誤答一覧][削除] │
  └────────────────────────────────────────────────────────────────────────────┘
  集計: テスト数 / 完了 / 学習中 / 平均正答率 / 総学習時間
```

- **新しい単語テスト**: 種別（A〜E）・レベル・書籍・分類 From/To・難易度・出題方式（ALL/RANDOM）・出題数を入れて作成する。
  作成すると `JPN_テスト情報` に 1 行（`状態コード='CREATED'`）と、
  条件に合う単語ぶんの `JPN_テスト出題情報`（`出題順` 1〜、`出題状態='PENDING'`）を作る。
- **実施**: テストを開くと `出題順` の `PENDING` の先頭から 1 語ずつ出す。
  A は詳細を見て覚える（`A確認回数`）、B〜E は選択肢を選んで回答する。
  回答すると `回答回数`・`誤答回数`・`最終判定`・`回答完了日時`・`有効学習時間ms` を更新し、
  同じトランザクションで `JPN_学習状況情報` と `JPN_技能習得情報`（種別に応じた技能区分）を更新する。
  すべて `ANSWERED` になったら `POST /tests/{testId}/complete` で `状態コード='COMPLETED'` にし、
  `JPN_学習日次情報` の `完了テスト数` を加算する。
- **誤答一覧**: そのテストの `最終判定 IN ('INCORRECT','MIXED')` の出題を出す。
- B は 1 語に 2 課題あるので、`正解数`（＝正解した課題数）は出題数を超える。
  画面の「正答率」は **課題ぶんの正解数 ÷ (正解数 + 不正解数)** で出す（`scorePercent`）。
- 2.0 の `japanese_test_a.jsp`〜`e.jsp` にあたる 5 画面は作らず、1 つの実施画面で種別を切り替える。

## 4. 移行（`MIG_JPN_日本語勉強_20260913.sql`）

- **dblink で `study3` に接続**（`dblink('dbname=study3', ...)`）。`BEGIN;` … `COMMIT;` の 1 トランザクション。
- 移行元の値を一度 TEMP テーブルに読み込み、事前チェック（NOT NULL・CHECK・桁数・一意性）を
  通してから INSERT する（`MIG_NET_Web閲覧履歴_20260912.sql` と同じ書き方）。
- 冪等: 2.0 の ID を `旧*ID`（一意索引）に保持し、`ON CONFLICT ("旧*ID") DO NOTHING`。
  子テーブルは親の `旧ID` → 新ID を引いて入れ、引けない行は入れない。
  **再実行しても件数は増えない**（2 回実行で全テーブル `INSERT 0 0`）。
- `ユーザーID` → `利用者アカウントID` の対応は `'liu'` → 1（保護者 `bruss.ji.liu@gmail.com`）、
  `'ljz'` → 2（生徒 `ricky.jingze@gmail.com`）。**実データは全件 `'liu'` なので SKIP 0 件**
  （引けない行は `利用者アカウントID` が NOT NULL のため移行せず、件数を `NOTICE` に出す）。
- 空文字は NULL に寄せる（テストの `レベル`、選択肢の `誤答区分`）。
  `出題状態` の `WAITING` は `PENDING` に読み替える。
- 監査列は人が実行した記録ではないので `登録者/更新者アカウントID = NULL`、
  `登録元コード`/`更新元コード = 'MIGRATION'`。
- 移行後に **DO ブロックで件数を検証**し、期待値と違えば `RAISE EXCEPTION` する

### 値の対応で迷った点と、そう決めた理由

| 項目 | 決めたこと | 理由 |

| 詳細の JSONB 集約 | 6 子テーブル ＋ **本体の列もトップレベル**に入れる | 本体の `代表中国語意味`・`日本語説明`・`中国語説明` は 383 件すべてに入っており、A 画面の基本情報。2.1 の詳細テーブルに列を作ると AI の取得項目が増えるたびに `ALTER TABLE` が要るので、詳細は JSONB 1 列に閉じる |
