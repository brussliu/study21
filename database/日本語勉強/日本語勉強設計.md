2.0 の実データで分かっていること（移行の前提）:

- **`代表JLPTレベル` は全件 NULL。** 2.0 は AI 詳細取得時に
  `STY_日本語単語詳細情報.JLPTレベル` へ N1〜N5 を入れたが、母表の代表値は一度も埋めていない。
  実際のレベルは **`収録情報.レベル`（全件 `'N1-N5'`）** 側にある（§2）。
- `代表品詞` は `[名]` / `[名・他サ]` / `[他五]` のような**日本語の記号つき文字列**（英語の品詞コードではない）。
  最頻値は `[名]` 4,634。
- `(見出し語キー, 読みキー)` は 9,847 件で重複 0（2.0 の UNIQUE 制約がそのまま成立している）。
  ただし `見出し語キー` だけでは 9,714 種類（同じ見出し語で読みが違う語が 133 組ある）。
- 教材は **`書籍='01.N1~N5日本語単語'` 1 冊・`分類='Unit001'〜'Unit590'` 588 種類**。
  2026-09-22 に `JPN_書籍情報` へ起こした結果も **1 冊**（`書籍コード='01'` / `書籍名='N1~N5日本語単語'` /
  `レベル範囲='N1-N5'` / `分類数=588` / `収録語数=9,886`）。収録 9,886 行すべてに `書籍ID` が入っている。
- テストの `ユーザーID` は **全件 `'liu'`**（保護者）。学習データも全件 `'liu'`。
- テストの `レベル` は **全件 空文字**（未設定）。対象範囲は `書籍` と `分類開始`/`分類終了` で決まる。
- 詳細の `音声URL` は全件 NULL、`関連語.関連先日本語単語ID` も全件 NULL
  （`音声テキスト` は問題側に 1,319 件ある）。
- `選択肢.品質状態` は全件 `'APPROVED'`、`詳細.状態` は全件 `'AI_GENERATED'`、
  `学習状況.習得済フラグ`・`お気に入りフラグ` は全件 false。

## 2. テーブル設計

24 テーブル（業務 13 ＋ 詳細の版の子テーブル 11）。監査列（`登録者アカウントID`・`更新者アカウントID`・`登録元コード`・`更新元コード`・
`登録日時`・`更新日時`）と楽観的ロック（`バージョン`）は 2.1 の規約どおり。
`登録元コード` は `APP`=画面から / `MIGRATION`=2.0 からの移行（書籍だけ `SEED` も許す）。
**詳細の 11 子テーブルでは `登録元コード` の意味が少し違い、`BATCH`=AI が作った内容 / `APP`=人が作った内容**（§2.4）。

> **詳細の版モデル・11 子テーブル・選択肢プールは中国版に詳しく書いてある**
> （`日本語勉強設計_中文.md` の 5.4〜5.4.12・第 7 章・第 8 章）。ここには実装の記録として要点を置く。

### `JPN_書籍情報`（教材のマスタ。1 冊 = 1 行。2.1 で新設）

**2.0 は書籍マスタを持たず、`STY_日本語単語収録情報.書籍` の文字列だけ**だった
（実データは `01.N1~N5日本語単語` の 1 冊）。新規登録画面は「先に書籍を作り、その書籍に語を入れる」
流れなので、書籍そのものに ID・コード・名前・並び・状態を持たせる。

| 列 | 型 | 意味 |
|---|---|---|
| `書籍ID` | BIGSERIAL PK | |
| `旧書籍コード` | VARCHAR(100) UNIQUE NULL | 2.0 の `書籍` の生値（`01.N1~N5日本語単語`）。移行の冪等性の根拠 |
| `書籍コード` | VARCHAR(100) NOT NULL UNIQUE | 教材の識別コード（`01`）。名前に埋め込まずに別の列で持つ |
| `書籍名` | VARCHAR(300) NOT NULL | 画面に出す名前（`N1~N5日本語単語`）。収録の `書籍` と同じ値 |
| `シリーズ名` | VARCHAR(300) NULL | 同シリーズの別巻をまとめる用（今は未使用） |
| `レベル範囲` | VARCHAR(20) NULL | `N1-N5` など。**分からない本は NULL**（CHECK は `^N[1-5](-N[1-5])?$`） |
| `分類数` / `収録語数` | INTEGER NOT NULL DEFAULT 0 | 統計。登録時に数え直す |
| `表示順` | INTEGER NOT NULL DEFAULT 0 | 画面の並べ替え |
| `状態コード` | VARCHAR(20) NOT NULL DEFAULT `'ACTIVE'` | `ACTIVE` / `INACTIVE`（消さずに一覧から外す） |
| `バージョン` | INTEGER NOT NULL DEFAULT 1 | 楽観的ロック |

- 索引: `uq_jpn_book_code`（`書籍コード`）UNIQUE／`uq_jpn_book_old_code`／
  `idx_jpn_book_order`（`表示順`, `書籍名`）／`idx_jpn_book_state`（`状態コード`）。
- **語と書籍は多対多**。1 語が複数の本に載ることがあるので、間に `JPN_単語収録情報` を置く。
  同じ語を別の本にも入れるときは、`JPN_単語情報` を増やさず収録の行を足す
  （`uq_jpn_word_key`（見出し語キー, 読みキー）で語は一意なので二重登録にならない）。
- **収録の `書籍`（文字列）は消さない。** 移行データと突き合わせるため残し、`書籍ID` を併せて持つ（§2.3）。
- 実データからの起こし方は `UPD_JPN_書籍情報_20260922.sql`。先頭の `.` より前をコード、後ろを名前にする
  （`.` が無ければ `LEGACY` ＋ 全体を名前）。**推測でレベルを埋めない**ので、名前から `N1~N5` が
  読めるときだけ `レベル範囲` を入れる。

### `JPN_AI生成履歴情報`（A〜E の内容を AI から取った記録。1 語 × 1 内容種別 = 1 行）

| 列 | 型 | 意味 |
|---|---|---|
| `生成ID` | BIGSERIAL PK | |
| `単語ID` | BIGINT NOT NULL FK | `JPN_単語情報` へ `ON DELETE CASCADE` |
| `内容種別コード` | VARCHAR(30) NOT NULL | `A_DETAIL` / `C1_READING` / `C2_KANJI` / `D_CONTEXT_MEANING` / `E_KANJI_USAGE`（CHECK） |
| `状態コード` | VARCHAR(20) NOT NULL DEFAULT `'QUEUED'` | `QUEUED` / `RUNNING` / `SUCCEEDED` / `FAILED` / `CANCELED` |
| `AI区分` / `モデル名` | VARCHAR NULL | `BAT_AI呼出履歴情報` と同じ語彙 |
| `内容版数` | INTEGER NOT NULL DEFAULT 1 | 取り直すたびに増える。詳細・問題の `内容版数` と対応 |
| `呼出履歴ID` | BIGINT NULL | `BAT_AI呼出履歴情報.呼出履歴ID`。**FK は付けない**（呼出履歴は保持期間で消えうる） |
| `生成件数` / `失敗件数` | INTEGER NOT NULL DEFAULT 0 | 詳細は語義・例文の内訳、問題は選択肢込みの問題数 |
| `エラーコード` / `エラーメッセージ` | VARCHAR/TEXT NULL | 失敗の理由を画面に出す |
| `処理時間ms` / `入力トークン数` / `出力トークン数` | INTEGER NULL | 呼出履歴が消えてもコストを見られるように写しを持つ |
| `開始日時` / `終了日時` | TIMESTAMP NULL | |
| `登録元コード` | VARCHAR(20) NOT NULL DEFAULT `'APP'` | `APP`=画面から / `BATCH`=定時・バッチから |

- 索引: `idx_jpn_ai_gen_word`（`単語ID`, `内容種別コード`, `登録日時 DESC`）／
  `idx_jpn_ai_gen_active`（部分索引。`QUEUED`/`RUNNING` だけ）／`idx_jpn_ai_gen_failed`（部分索引）／
  `idx_jpn_ai_gen_call`（`呼出履歴ID`）。
- **役割を分ける。** この表は「何を生成したか」、`BAT_AI呼出履歴情報` は「AI をどう呼んだか」
  （プロンプト・応答・トークン・HTTP ステータス）。同じ内容を二重に持たない範囲で写しを置く。
- **A と B は同じ行（`A_DETAIL`）で数える。** 詳細 1 つ（有効版を組み立てたもの）から A（勉強）と B（意味→日本語）の
  両方を作れるので、取得は 1 回・記録も 1 行にする（§2.4）。
- `SUCCEEDED` なのに `生成件数 = 0` は CHECK で弾く（取れたつもりで 0 件、に気づけるように）。
- 2.0 の実データは移行しない（既に `JPN_単語詳細情報`・`JPN_単語問題情報` へ移行済みで、
  この表はこれから実行する取得の記録）。

### `JPN_音声キャッシュ情報`（読み上げ音声のキャッシュ。1 文 × 1 声 × 1 速さ = 1 行）

**学習画面は音声を外部 TTS で作るので、同じ文を二度作るとそのぶん課金を食う。**
最初の 1 回だけ外部を呼び、できた音声をサーバに置いて、2 回目以降はここから返す。

| 列 | 型 | 意味 |
|---|---|---|
| `音声ID` | BIGSERIAL PK | |
| `音声キー` | CHAR(64) NOT NULL UNIQUE | **テキスト＋話者＋速度の SHA-256**（小文字 64 桁）。キャッシュの引き当てはこれ 1 本 |
| `テキスト` | TEXT NOT NULL | 生成に使った文（そのまま） |
| `テキスト種別コード` | VARCHAR(20) NULL | `WORD` / `READING` / `EXAMPLE` / `DIALOG` など（増えてもよいので CHECK は付けない） |
| `話者` / `速度` | VARCHAR(100) / NUMERIC(3,2) NULL | 声と速さ。**鍵に含める**ので、変えると別の音声になる |

  `idx_jpn_audio_failed`（部分索引。`FAILED` の再試行判断）／
  `idx_jpn_audio_unused`（部分索引。久しく使っていない `READY` の掃除）／
  `idx_jpn_audio_target`（`対象種別コード`, `対象ID`。画面の表示用）。
- **語ではなく文でキャッシュする。** 例文の使い回しや同じ読みの語があるので、鍵は「文＋声＋速さ」。
  `対象種別コード`・`対象ID` は「どの語から最初に作られたか」の記録にすぎない。
- **`READY` なのに置き場が無い**（`CK_JPN_音声_実体`）と、**`FAILED` なのに理由が無い**
  （`CK_JPN_音声_失敗`）は入れられない。「使えるはずなのに鳴らない」を作らないため。
- **失敗も記録する**（`FAILED` ＋ `エラーコード`）。毎回呼び直すと、つながらない相手に
  課金と待ち時間を払い続けることになる。`retry-after-minutes` の間は再試行しない。
- **実体を消しても行は残す**（`EXPIRED`）。同じ文をもう一度求められたときに、
  「前は作れた／作れなかった」が分かる（`音声ソースコード`・`TTS提供元`・`声の名前` で再生成できる）。
- 置き場は `study21.speech.storage-root`（既定 `${user.dir}/data/speech`）。
  既存の読み物・一時ファイルと同じ約束で、**DB には相対パスだけ**を入れ、
  配信は API（`GET /speech`）を通す（静的公開ディレクトリには置かない）。

#### 版の考え方（実装の事実）

1. **すべての取得・編集が 1 版を作る。** 内容は「そのときの有効版を複製し、変わった部分だけ入れ替える」。
   新しい版は自動で `ACTIVE`、前の版は `ARCHIVED`（**先に ARCHIVED、後に INSERT**。部分 UNIQUE 索引の順番）。
2. **人の編集も 1 版作る**（`登録元コード='APP'`・`生成ID`=NULL・`手修正フラグ`=true）。誤編集は前に戻せる。
3. **人の行は AI に消されない。** AI の取り直しでは、人の行（`手修正フラグ` または `登録元コード='APP'`）を
   **新しい版へ複製**する。人が書いた内容に戻したいときは、人の版へ有効版を切り替える。
4. **有効版の指定は `ACTIVE` を移すだけ**（版は作らない）。未指定なら最後に作った版が有効。
5. 履歴は**無限に残す**（掃除の規則は未定。§5）。

#### 1 問ごとの対錯と、テストの進行位置（`回答履歴JSON`）

| 何を知りたいか | どこを見るか |
|---|---|
| **どの問題に正解／不正解したか** | `JPN_テスト出題情報.最終判定`（`CORRECT` / `INCORRECT` / `CONFIRMED` / `MIXED` / `SKIPPED`） |

  出題表の行数が増えない。1 語のテストの様子は出題 1 行で読める（JOIN が要らない）。
  1 試行ずつを横断で集計したくなったら、`idx_jpn_test_question_history`（GIN）で引くか、
  そのときだけ子テーブルへ移す（§5 の申し送り）。

### 課題テーブルと回答履歴を 2.1 では持たない理由

2.0 は **テスト → 出題（1 語）→ 課題（A_STUDY / B1_ORTHOGRAPHY / B2_READING / C1_READING / C2_KANJI /
D_CONTEXT_MEANING / E_KANJI_USAGE の段階別。1,326 件）→ 回答履歴（1 試行ごと。1,113 件）** の 4 階層だった。
2.1 は **テスト → 出題** の 2 階層にし、**テスト結果は `JPN_テスト出題情報` の
`出題状態`・`最終判定`・`回答回数`・`誤答回数` で表す**。

1. **課題テーブルの役目は中断再開だった。** 2.0 は「B1 は終わったが B2 が途中」を正確に持つために
   課題を別テーブルにしていた。2.1 のテストは 1 語ぶんを続けて出題する（B なら B1 → B2）ので、
   **`出題状態` が `PENDING` の先頭から再開すれば足りる**（2.0 の `V_日本語単語テスト再開位置` と同じ結果が
   `出題情報` だけで求まる）。
2. **回答履歴は集計にしか使っていなかった。** 2.0 の画面に出していたのは 回答回数・誤答回数・正誤 だけで、
   1 試行ごとの選んだ選択肢は表示していなかった。同じ情報は `回答回数`・`誤答回数`・`最終判定` で足りる。
3. **行数が効く。** 回答履歴は 1 問 1 行で、教材 9,847 語を全問解くと数百万行になる。
   2.1 は SQL ログを含めて DB を軽く保つ方針（`docs/LOGGING.md`）なので、持たない。
4. そのため 2.0 の `課題数` / `完了課題数` / `正解課題数` / `不正解課題数` は
   `出題数` / `完了出題数` / `正解数` / `不正解数` に集約した。
   **B は 1 語 2 課題なので `正解数 + 不正解数 > 出題数` になりうる**（実データで 170 + 10 > 90）。

### 代表 JLPT レベルが実データ全件 NULL である件

2.0 の `STY_日本語単語母表.代表JLPTレベル` は **9,847 件すべて NULL**。
一方 `STY_日本語単語詳細情報.JLPTレベル`（383 件）には N1〜N5 が入っており、
`STY_日本語単語収録情報.レベル` は **全件 `'N1-N5'`** で、教材は
`書籍='01.N1~N5日本語単語'` の 1 冊しかない。

つまり 2.0 の日本語教材は **N1〜N5 を 1 冊にまとめた構成**で、語ごとの JLPT レベルは
母表には入っていない（AI 詳細を取った 383 語にだけ入っている）。

2.1 の扱い:

- `JPN_単語情報.JLPTレベル` は **2.0 の `代表JLPTレベル` をそのまま移行する（＝全件 NULL）**。
  勝手に AI 詳細の `JLPTレベル` を母表へコピーしない。2.0 の意味（代表値）と食い違ううえ、
  383 語だけ値が入った「半分埋まった代表値」になるため。
- **語のレベルを出したい画面は `JPN_単語収録情報.レベル` を使う**（`N1-N5`）。
  語ごとの JLPT が必要になったら、AI 詳細の `jlptLevel`（詳細の版の列）を語の属性として
  昇格させるかを相談する（§5）。
- `JPN_単語情報.JLPTレベル` には 2.0 と同じ `N1`〜`N5` の CHECK を残してある
  （誰かが後から埋めるときに表記ゆれを防ぐため）。
- 単語情報管理画面の「JLPT レベル」絞り込みは、**値が 1 件も無い**ので
  実質「収録のレベル（N1-N5）」で絞ることになる。UI 側の表示は要相談（§5）。

## 2.4 詳細の版（1 語 N 版）と、取得・編集の流れ

**すべての取得・編集が 1 版を作る**（表の列は §2 の `JPN_単語詳細情報`）。

| トリガ | 新しい版の中身 | `登録元コード` | `手修正フラグ` | `生成ID` | `元詳細ID` |
|---|---|---|---|---|---|
| batC41（A・B の全量取得）成功 | AI の結果で**全段落**を置き換え ＋ **人の行を複製** | `BATCH` | 人の行があれば true | 今回の生成 | 現在の有効版 |
| 将来の段落単位のバッチ（例文だけ等） | 有効版を複製し、**対象の段落だけ置き換え** | `BATCH` | 同上 | 今回の生成 | 現在の有効版 |
| 画面の編集保存（`PUT /words/{wordId}/editor`） | 有効版を複製し、**画面から来た段落で置き換え** | `APP` | true | NULL | 現在の有効版 |
| 有効版の切り替え | 版を作らない（`ACTIVE` を移すだけ） | — | — | — | — |

**実装の順番（入れ替えられない）**: 現在の有効版を読む → 人の行の最大 `表示順` を数える
（`countKeptDetailRows`）→ **現在の有効版を `ARCHIVED`** → 新しい版のヘッダを `ACTIVE` で INSERT →
**人の行を新しい版へ複製**（会話 → 会話行 の順。会話行は新しい `会話ID` へ付け替え）→ AI の新しい行を INSERT。
全体が 1 トランザクション（途中で失敗したら何も残らない）。

**画面の編集で「行の出所」をどう決めるか**（`JpnWordDetailEditorComposer`）:
要求の段落の行を元の版の行と**内容で**突き合わせる（`表示順` では見ない。画面は並べ替えられるため）。

| 要求の行 | 新しい版での出所 |
|---|---|
| 元の版と**まったく同じ** | 元の出所をそのまま引き継ぐ（`BATCH` は `BATCH`、`APP` は `APP`） |
| **変わった行・新しく足した行** | `APP` ・ `手修正フラグ`=true（以後 AI に上書きされない） |
| 元の版にあって要求に無い行 | 消す（画面で削除した行は消えたまま） |

**版の切り替え（API）**: `GET /words/{wordId}/detail-versions`（新しい順。段落の行数も返す）／
`PUT /words/{wordId}/detail-versions/{detailId}/active`（`version` で楽観的ロック。合わなければ 409）。
指定しなければ最後に作った版が有効（新しい版は必ず `ACTIVE` で生まれるため）。

**問題（C/D/E）の版の切り替え（API。2026-09-26 追加）**: `GET /words/{wordId}/question-versions`
（AI の取得 1 回 = 1 行。`問題種別` / `内容版数` / `問題数` / 使用中か / 生成の状態 / モデル /
取得日時 / 失敗の理由）／`PUT /words/{wordId}/question-versions/{questionType}/active`
（本文 `{"contentVersion":N}`。その種別の中で指定した版だけ `ACTIVE`、ほかは `ARCHIVED`。
問題は消さないのでテストの出題は壊れない。失敗した版＝問題 0 件は 400）。
問題の `内容版数` は AI の取得 1 回ぶんの番号（`JPN_AI生成履歴情報.内容版数` と同じ値。
`JapaneseWordAiStep` が `nextGenerationVersion` で数える）。

> **修正済み（2026-09-22）**: 版一覧と詳細の API が対象の版の `バージョン` を返すようになり、画面はそれを送る
> （中国版の設計レビュー A7）。

## 2.5 選択肢プールと、テスト作成時の抽選

- **プール**（`JPN_単語問題選択肢情報`）: AI には 1 問につき **正解 1 件 ＋ 誤答 4〜6 件（合計 5〜7 件）**、
  値は一意、正解はちょうど 1 件を出させる。**満たさない応答は 1 行も書かない**（失敗は `JPN_AI生成履歴情報` に残す）。
- **テスト作成時**（`JapaneseServiceImpl.createTest`）: C/D/E は問題のプールを読み、
  **正解 1 ＋ 誤答からランダム 3** を選び、**提示順もシャッフル**して `JPN_テスト出題情報.出題選択肢JSON` に固定する。
  プールが足りない問題（正解が 1 件でない・誤答が 3 件未満）が 1 つでもあれば、整回の作成を中止する。
- **A・B** はプールを持たない。別の語（同条件）から誤答を作り、**同じ形の 4 件**を `出題選択肢JSON` に書く
  （`choiceId` は null。判定の経路を 1 本にするため）。
- **画面と判定は `出題選択肢JSON` だけを見る**（`GET /tests/{testId}` は固めた 4 件だけを返し、プール全体は返さない。
  回答の判定もこの列の `correct` と `正解値` を二重に確かめる）。これで:
  - 同じテストを開き直しても選択肢が変わらない
  - プールを AI で取り直しても、受験済みの記録が壊れない
  - 表示と判定が必ず一致する
- `出題選択肢JSON` を持たない古い出題（移行データ）だけ、今までどおりプール／`単語スナップショットJSON` で判定する。
- **A（勉強）の回答は技能の行を書かない**: `JPN_技能習得情報` の CHECK は B〜E の技能区分だけを許すため
  （`updateLearning` の `tracksSkill`。A の確認は `JPN_学習状況情報.A確認回数` で数える）。

  - C・D・E … `JPN_AI生成履歴情報` の取得 1 回（`GET /words/{id}/question-versions`／
    `PUT …/{questionType}/active`）。C は C1 と C2 の 2 つを分けて出す
  - 切り替えは**同じ種別の中で**指定した版だけ `ACTIVE`、ほかを `ARCHIVED`（問題は消さない＝
    テストの出題が参照している）。失敗した版（問題 0 件）は選べない
  - **問題にも版番号を入れる**（`JPN_単語問題情報.内容版数`。AI の取得 1 回ぶんの番号で、
    `JPN_AI生成履歴情報.内容版数` と同じ値。`JapaneseWordAiStep` が
    `nextGenerationVersion` で数える）
- 絞り込みは `keyword`（見出し語・読み。`見出し語キー`/`読みキー` を使う）・`reading`・
  `jlpt`・`part`・`stateCode`・`book`・**分類の範囲（`categoryFrom` ～ `categoryTo`。片方だけでもよい）**・
  `learnState`。
  分類は**同じ収録の行**で両端を見る（`EXISTS (... AND 分類 >= From AND 分類 <= To)`）。
  別々の `EXISTS` にすると「別の Unit で From を満たし、さらに別の Unit で To を満たす語」まで拾ってしまう。
  テスト作成（種別 A・B の出題元）も同じ範囲で絞る（範囲外の語を選択肢に混ぜない）。
- **詳細ダイアログ**は「収録（教材のどこに載っているか）」「語義・例文など（有効版を組み立てた詳細）」
  「詳細／C〜E 問題（`JPN_単語問題情報` の種別ごとの有無）」をタブで見せる。
  詳細は読み取り専用（AI が生成した参考情報）。**版の履歴パネル**から過去の版に切り替えられる（§2.4）。
- **学習画面（A. 勉強）は別ウィンドウ**（`/{area}/japanese-word/study?wordId=…`）で開く（2026-09-25）。
  【詳細】（目のアイコン）が `window.open` で開き、**開いた時点で最大化**する
  （`screen.availWidth`/`availHeight` ＋ 左上 0,0。ブラウザには `window.maximize()` が無い）。
  データはその窓が `GET /words/{id}` で取り直す。**窓の中身は学習画面だけ**で、上部の帯
  （見出し・【修正】・【閉じる】）は置かない（利用者の指示。2.0 の学習画面も中身だけだった）。
  窓はブラウザの × で閉じ、修正は一覧の【修正】（鉛筆）から行う。
  アプリ内ダイアログ版（`JapaneseWordStudyDialog.vue`）は同じ見た目が 2 つになるので消した
  （編集ダイアログの「プレビュー」は今までどおりダイアログの中で `DemoWordStudyView` を使う）。
- 登録・修正ダイアログは 見出し語・読み・JLPT レベル・品詞・状態コード・備考（＋ `バージョン` で楽観的ロック）。
- 一覧の右上に **AI 取得のボタンを 1 つ**置き、押すと**窓**を出す。窓の中で 2 つを選んでから実行する
  （左の縦罫は置かない。区切りは余白だけ。2026-09-26 利用者の指示）
  （2026-09-26。参照は 2.0 の英語学習の単語情報管理 `word.jsp` の窓）:
  1. **どの情報を取るか** … 詳細情報（A・B）／読み問題（C）／文脈問題（D）／漢字問題（E）
  2. **取得済みをどうするか** … 取得済みをスキップ／すべて再取得
  4 つボタンを並べると場所を取るので 1 つにまとめた（利用者の指示）。対象は**いま出ている
  1 ページぶん**（上限 50 語）で、「取得済み」の判断は一覧の取得状態（`aiState`）
  ＝**取得状態の列と同じ情報**を使う（§5）。
- 削除は確認ダイアログ。`ON DELETE CASCADE` にしてある子（**収録・詳細・学習状況・技能習得**）は
  語と一緒に消える。一方 **`問題`・`テスト出題` は `ON DELETE CASCADE` にしていない**ので、
  それらを持つ語を消そうとすると FK で止まる（実測で確認）。サービス側で
  「問題・出題を先に消してから語を消す」順に処理する。AI が生成した問題は捨てたくない資産で、
  テストの出題も履歴なので、語の削除で黙って消えないほうが安全という判断（§5 の確認事項）。

  ┌────────────────────────────────────────────────────────────────────────────┐

- **新しい単語テスト**: 種別（A〜E）・レベル・書籍・分類 From/To・難易度・出題方式（ALL/RANDOM）・出題数を入れて作成する。
  作成すると `JPN_テスト情報` に 1 行（`状態コード='CREATED'`）と、
  条件に合う単語ぶんの `JPN_テスト出題情報`（`出題順` 1〜、`出題状態='PENDING'`）を作る。
- **実施**: テストを開くと `出題順` の `PENDING` の先頭から 1 語ずつ出す
  （**これが「テストがどこまで進んだか」の持ち方**。専用の列は持たない）。
  A は詳細を見て覚える（`A確認回数`）、B〜E は選択肢を選んで回答する。
  回答すると `回答回数`・`誤答回数`・`最終判定`・`回答完了日時`・`有効学習時間ms` と
  **`回答履歴JSON`（1 試行ごとの記録）** を更新し、
  同じトランザクションで `JPN_学習状況情報` と `JPN_技能習得情報`（種別に応じた技能区分）を更新する。
  すべて `ANSWERED` になったら `POST /tests/{testId}/complete` で `状態コード='COMPLETED'` にし、
  `JPN_学習日次情報` の `完了テスト数` を加算する。
- **1 問ごとの対錯**は `JPN_テスト出題情報` の `最終判定`（正誤）・`回答回数`／`誤答回数`（回数）・
  `回答履歴JSON`（1 回ごとに何を答えたか）で持つ。1 回答 = 1 行の子テーブルは作らない（§2）。
- **A〜E の 5 種別のテスト**は、種別ごとに必要な内容が揃っている語だけを対象にする。
  揃っていない語を混ぜると空の問題が出るので、作成時に
  「A/B は `JPN_単語詳細情報` がある」「C〜E は `JPN_単語問題情報` の該当種別が
  `状態コード='ACTIVE'` である」を条件へ足す（§3「内容の生成（AI 取得。A〜E）」）。
- **誤答一覧**: そのテストの `最終判定 IN ('INCORRECT','MIXED')` の出題を出す。
- B は 1 語に 2 課題あるので、`正解数`（＝正解した課題数）は出題数を超える。
  画面の「正答率」は **課題ぶんの正解数 ÷ (正解数 + 不正解数)** で出す（`scorePercent`）。
- 2.0 の `japanese_test_a.jsp`〜`e.jsp` にあたる 5 画面は作らず、1 つの実施画面で種別を切り替える。

### 内容の生成（AI 取得。A〜E）

「A〜E の内容を AI で取得し、その 5 種別のテストを作れる」ようにするための、
**内容の持ち場所と生成の単位**をここにまとめる。新しいテーブルは増やさず、既存の
`JPN_単語詳細情報`・`JPN_単語問題情報`・`JPN_AI生成履歴情報` の 3 つで受ける。

#### 種別ごとの内容と置き場所

| テスト種別 | 内容 | AI 取得の単位（`内容種別コード`） | 置き場所 |
|---|---|---|---|
| **A** 勉強 | 語の意味・読み・発音・文型・例文・注意（読んで覚える） | `A_DETAIL` | `JPN_単語詳細情報` の有効版 ＋ 11 子テーブル（`senses` / `examples` / `patterns` / `dialogs` / `synonyms` / `cautions` / `collocations` / `relatedWords` / `usageNotes` / `practices` / 発音・活用形・自他対応） |
| **B** 意味→日本語 | 中国語の意味から日本語（表記・読み）を思い出す。**1 語 2 課題**（表記／読み） | `A_DETAIL`（A と同じ 1 回の取得で作れる） | 同上（`senses.chinese`・`pronunciations.reading` を答えに使う） |
| **C** 漢字→読み | C1: 漢字 → 読み、C2: 読み → 漢字 | `C1_READING` / `C2_KANJI` | `JPN_単語問題情報`（`問題種別` ごと）＋ `JPN_単語問題選択肢情報` |
| **D** 文脈詞義判断 | 例文の下線部の語の意味を選ぶ | `D_CONTEXT_MEANING` | 同上 |
| **E** 漢字選択 | 文脈に合う漢字表記を選ぶ | `E_KANJI_USAGE` | 同上 |

- **A・B は問題テーブルに入れない。** 読んで覚える内容なので、出題は「詳細（有効版）を見せる」だけで足りる。
  2.0 も同じ作りだった（問題テーブルは C1/C2/D/E の 1,700 件のみ。A/B の問題は無い）。
- B の 2 課題（B1 表記 / B2 読み）は **同じ語の同じ詳細から出し分ける**ので、DB には課題を持たない。
  2.0 の `技能習得情報.技能区分`（`B_ORTHOGRAPHY` / `B_READING_RECALL`）で習得を分けて数える。
- C は 1 語につき C1・C2 の 2 種別を持つ（2.0 の実データも 381 件ずつ）。

#### 生成の流れと記録

```
① 対象の語を選ぶ（書籍・分類の範囲。JPN_単語収録情報 で絞る）
② 種別ごとに AI を呼ぶ
     A_DETAIL / C1_READING / C2_KANJI / D_CONTEXT_MEANING / E_KANJI_USAGE
③ JPN_AI生成履歴情報 に 1 行（QUEUED → RUNNING → SUCCEEDED / FAILED）
     AI の生の呼出は BAT_AI呼出履歴情報 に記録し、呼出履歴ID で結ぶ
     （呼出履歴ID は AI クライアントが採番後の値を返し、SUCCEEDED の更新で書き込む）
④ 取れた内容を **詳細の新しい版** / 問題情報 ＋ 選択肢情報（プール）へ書く
     ・詳細は「新しい版を作る」＝ 有効版を ARCHIVED → 新版を ACTIVE（§2.4）。
       内容版数はその語の最大 + 1。**人の行は新しい版へ複製する**ので AI に消されない
     ・問題は 問題ID を採番して作り直す（古い問題は状態コード='ARCHIVED' にする。
       選択肢は**プール（正解 1 ＋ 誤答 4〜6 ＝ 5〜7 件）**として作る。規則を満たさない応答は 1 行も書かない。
       ON DELETE で消さないのは、テストの出題が問題ID を参照しているため）
⑤ 失敗した語は 状態コード='FAILED' で残るので、その一覧から再実行する
```

- **二重起動を防ぐ**: `idx_jpn_ai_gen_active`（`QUEUED`/`RUNNING` の部分索引）で
  「同じ語・同じ種別が実行中でないか」を引いてから投入する。
- **取れなかった語を残す**: 1 語ずつ行があるので、成功・失敗が語単位で分かる
  （2.0 の `_AI取得結果情報` と同じ粒度）。
- 詳細は `内容版数` を上げて上書きし、**前の版は残さない**（2.0 も上書きだった）。
  版ごとの履歴が要るなら `JPN_AI生成履歴情報` に版が残っているので、そこから辿れる。
- 5 種別のテストを作る手順は §3【単語テスト】を参照。

#### 読み上げ音声のキャッシュ（外部呼び出しを 1 回で止める）

学習画面（A 勉強）は「見出し語・読み・例文」を音声で再生する。音声は外部 TTS で作るので、
**同じ文を二度作るとそのぶん課金を食う**。`JPN_音声キャッシュ情報` でそれを防ぐ。

```
① 画面が GET /speech?text=...&speaker=...&speed=... を呼ぶ
② 音声キー（テキスト＋話者＋速度の SHA-256）で JPN_音声キャッシュ情報 を引く
     ├ 状態コード='READY' かつ 実体がある
     │    → ファイルを返すだけ（**外部を呼ばない**）。再生回数 と 最終利用日時 を更新
     ├ 状態コード='FAILED' かつ retry-after-minutes 以内
     │    → 外部を呼ばずに失敗を返す（待たせない・課金しない）
     └ 行が無い／EXPIRED／再試行してよい FAILED
          → 外部 TTS を **1 回だけ** 呼ぶ
③ 取れた音声を storage-root 配下に置き（ファイル名は UUID）、行を UPSERT
     READY: 音声保存先パス・内容ハッシュ・ファイルサイズ・長さms・外部呼出回数=1
     FAILED: エラーコード・エラーメッセージ・失敗回数を +1（パスは NULL のまま）
④ 同じ文を別の語が使っても、②の鍵は同じなので**再生成しない**（対象ID は最初の語のまま）
```

- **アプリ側の実装で守ること**:
  1. 問い合わせは `音声キー` の UNIQUE 索引 1 本で行う（`テキスト` での LIKE 検索はしない）
  2. 同じ文の同時再生で二重に外部を呼ばない（キーで UPSERT し、負けた側は既存の行を読む）
  3. ファイルを先に書き、DB は後で更新する（`READY` なのに実体が無い状態を作らない）
  4. 配信は API 経由（セッション確認後）。**静的公開ディレクトリには置かない**
- 掃除（任意）: `idx_jpn_audio_unused` で久しく使っていない `READY` を見つけ、
  実体を消して `EXPIRED` にする（行は残す）。**消す前に「また作れる」ことを確認する**
  （`音声ソースコード='TTS'` なら作れる。`UPLOAD` は人が置いた音声なので消さない）。
