## 1. 详细信息的版本化模型

### 1.1 心智模型

```
JPN_単語情報 (1)
   └─ JPN_単語詳細情報 (N)  ← 版本头。1 行 = 该词的 1 个「版」
        ├─ 状态 ACTIVE 的 1 行 = 当前生效版（部分唯一索引保证唯一）
        └─ 11 张子表 (N)   ← 行内容，跟随版本（版本被归档时整版一起变历史）
```

- **每次「取得」或「编辑保存」都新建一版**：内容＝以「当时生效版」为基础，替换掉这次变动的部分，其余段落原样复制。
- 新建版立刻 `ACTIVE`，原来的生效版自动变 `ARCHIVED`（一条事务）。
- 「指定哪一版生效」＝把 `ACTIVE` 移到指定版；未指定则最新版（＝最后新建的那版）生效。
- 因此：AI 生成的历史、人工编辑的历史**都留下**，任何一版都能完整重现，也能一键回退。

### 1.2 版本头 `JPN_単語詳細情報`（改造）

| 列 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `詳細ID` | bigint | NOT NULL | sequence | 主键（沿用现列名） |
| `単語ID` | bigint | NOT NULL | — | FK → `JPN_単語情報`（CASCADE） |
| `内容版数` | integer | NOT NULL | 1 | 该词内的版本序号（1 起，递增） |
| `状態コード` | varchar(20) | NOT NULL | `'ACTIVE'` | `ACTIVE` 生效／`ARCHIVED` 历史 |
| `元詳細ID` | bigint | NULL | — | 基于哪一版产生（初版为 NULL）。**不设 FK**（自表引用，注释说明） |
| `生成ID` | bigint | NULL | — | `JPN_AI生成履歴情報.生成ID`。人工编辑版为 NULL。**不设 FK**（与既有「引用不设 FK」一致） |
| `AIプロバイダ` / `AIモデル` | varchar(40) / varchar(120) | NULL | — | 产生这一版的 AI |
| `取得日時` | timestamp | NULL | — | 产生这一版的时间 |
| `手修正フラグ` | boolean | NOT NULL | false | 这一版是否含人工编辑 |
| `備考` | text | NULL | — | 切换生效版时的理由等 |
| `元レスポンスJSON` | jsonb | NOT NULL | `'{}'` | AI 原始响应（人工版复制来源版的值） |
| `バージョン` | integer | NOT NULL | 1 | 乐观锁 |
| ＋审计列（6 列） | | | | |

**词级标量（留在版本头）**：`核心意味`(text)・`説明_日本語`(text)・`説明_中国語`(text)・`品詞`(varchar 100)・`JLPTレベル`(varchar 10)・`活用型`(varchar 100)・`自他`(varchar 20)・`重要度`(smallint)・`記憶ヒント`(text)・`記憶ヒント根拠`(text)。

**小结构（留在版本头，JSONB）**：`発音JSON`（`pronunciation` 单对象：reading/accentType/accentNotation/hint/hasAudioSample）・`活用形JSON`（`conjugations` 数组）・`自他対応JSON`（`transitivityPair` 对象）。

**约束与索引**
- `UNIQUE (単語ID, 内容版数)`
- **部分唯一** `UNIQUE (単語ID) WHERE 状態コード = 'ACTIVE'`（每词恰好一版生效）
- CHECK：`状態コード IN ('ACTIVE','ARCHIVED')`；`内容版数 >= 1`；`重要度 IS NULL OR 重要度 BETWEEN 1 AND 5`；`元レスポンスJSON` 为 object；`バージョン >= 1`
- 索引：`(単語ID, 状態コード)`；部分 `(単語ID) WHERE 状態コード='ACTIVE'`

### 1.4 版本的生命周期（4 条写入路径）

| 触发 | 新建版的内容 | `登録元コード` | `手修正フラグ` | `生成ID` | `元詳細ID` |
|---|---|---|---|---|---|
| batC41（A・B 全量取得）成功 | 本次 AI 结果覆盖**全部段落** | `BATCH` | false | 本次生成 | 当前生效版 |
| 将来的段落级批处理（如只取例句） | 复制当前生效版，**只替换目标段落** | `BATCH` | false | 本次生成 | 当前生效版 |
| 画面编辑保存（按段落） | 复制当前生效版，**只替换被编辑的段落** | `APP` | **true** | NULL | 当前生效版 |
| 切换生效版 | 不新建版，只把 `ACTIVE` 移动过去 | — | — | — | — |

**「AI 不许覆盖人工行」的实现**：AI 建新版时，人工行会被**复制进新版**（内容与 `手修正フラグ` 一起），所以不会丢；若用户想丢掉人工改动，切回 AI 那一版即可。这样不需要「行级归档」的状态列。

**AI 的写入顺序**（一个词一个内容种别，事务内）：
`insertGeneration(RUNNING)` → 调用 AI → 校验 → **建新版本（版本头 ＋ 全部子表行）** → `markGenerationSucceeded`（写入 `呼出履歴ID`／`生成ID`）

### 1.5 读取路径

- **详情 API**（`GET /words/{wordId}`）：服务端从**生效版**（`状態コード='ACTIVE'`）读版本头 ＋ 11 张子表，组装成**与现在完全相同的 detail 对象**（`coreMeaning` … `practices`，含 `pronunciations` 数组与 `structured` 等兼容键）。前端学习画面与 `wordMapper.ts` 不需要改结构。
- **AI 输入**（`findTargets` 取 `詳細JSON` 给提示词）：改为取**生效版组装后的 JSON**。
- **一览的「取得状态」**：仍用视图 `v_jpn_word_ai_state`（与版本无关）。
- **测试出题快照**：`単語スナップショットJSON` 存「出题时生效版组装后的 JSON」（现状不变）。

### 1.6 顺手修掉一个真实的读取缺陷（本次范围内）

事实（我读过代码）：前端 `wordMapper.ts` 的 `toDetail()` 只映射了 senses / examples / collocations / relatedWords / cautions / pronunciation，并且用的键名是 **2.0 的子表列名**，与后端产出不一致：

| 后端产出 | 前端读取 | 结果 |
|---|---|---|
| `cautions[].kind` | `noteType` | 区分永远落到 `UNNATURAL` |
| `cautions[].title` | `japanese` | ''
| `cautions[].wrong` / `correct` / `reason` | `wrongExample` / `correctExample` / `chinese` | 全为 ''
| `relatedWords[].relation` | `relationType` | 永远显示 `類義語` |
| `examples[].level` | 忽略（硬编码 `BASIC`） | 等级丢失 |
| `patterns` / `dialogs` / `synonyms` / `conjugations` / `memoryHint` / `practices` / `transitivityPair` | **完全没有映射** | 画面永远空白 |
| `usageNotes` | 由 `senses.context/style` 合成 | AI 产出的 `usageNotes` 被丢弃 |

**决定**：本次一并修正 —— 以**后端产出的键名为唯一规范**（AI 的 DTO 决定键名，AI 提示词与 JSON Schema 都基于它），改 `api/japanese.ts` 的类型与 `wordMapper.ts` 的映射，让 10 个段落都能显示。`usageNotes` 改为读后端产出的段落（不再用 senses 合成）。

## 2. 选项池

### 2.1 生成侧（AI・校验・提示词）

- `JapaneseWordAiDtoMapper`：`REQUIRED_CHOICES = 4` → **`MIN_CHOICES = 5` / `MAX_CHOICES = 7`**（合计），并要求**正解恰好 1 件、误答 4〜6 件、值互不重复**。不满足则整条响应不合格（**一行都不写**，失败记在 `JPN_AI生成履歴情報`）。
- 提示词（`COM_設定情報` 的 **3 行**：`BAT_C42_SYSTEM_PROMPT`（C1・C2 共用）・`BAT_C43_SYSTEM_PROMPT`・`BAT_C44_SYSTEM_PROMPT`）：
  把「options は必ず 4 件」改成「options は**正解 1 件 ＋ 誤答 4〜6 件（合計 5〜7 件）**。誤答は学習者が実際に迷うもの」。
  已建库用 `database/設定/UPD_COM_設定情報_JAPANESE_WORD_AI_選択肢.sql`（UPDATE ＋ 自检 SELECT）；新库由
  `database/設定/TBL_COM_設定情報_init.sql` 以同值初始化。
- `JPN_単語問題選択肢情報` 的结构**不用改**（本来就是多行）：`(問題ID, 表示順)` 唯一、正解 1 行、`誤答区分` 只在误答行。
- 附带：批处理**重取**时旧题仍按现在的规则 `ARCHIVED`（不删），新题插入。

### 2.2 出题侧（作成测试时抽选并固定）

- 新增列：`JPN_テスト出題情報.出題選択肢JSON` jsonb NOT NULL DEFAULT `'[]'`（＋CHECK 为 array）。
  内容：`[{"choiceId":…, "value":…, "reading":…, "correct":true|false}]`（**已打乱的提示顺序**）。
- `createTest`（C/D/E）：挑中题后，读该题的选项池 → 取正解 1 个 ＋ 从误答里**随机取 3 个** → 打乱顺序 → 写入 `出題選択肢JSON`；同时保留 `問題ID`、`単語スナップショットJSON`。
- `createTest`（A/B）：同样写 `出題選択肢JSON`（把现在放在 `単語スナップショットJSON.choices` 的那组选项改写成统一形状），让作答路径只有一条。
- `testDetail`（打开测试）：返回 `出題選択肢JSON`（**不再返回整个池**）。
- `answer`：用 `出題選択肢JSON` 判定（选中项的 `correct`，并与 `正解値` 双确认），兼容「没有该列值的历史数据」时回退到选项池。
- 这样：同一个测试每次打开选项相同；池被重新生成过也不影响已考过的记录。

### 2.3 已知的连带影响（实现时一并处理）

- `pickQuestions` 不按词去重，C 类同一词的 C1/C2 会同时入选（现状，属有意）。抽选固定后，同一题出现两次会各拿一套误答，效果更好。
- 选项池越大，`listChoices` 的读取量越大；因为**提示只用 4 个**，画面与作答改为读 `出題選択肢JSON` 之后，池大小不影响渲染性能。

### 与规格的差异（实施中偏离的地方，共 3 处）

① **段落级编辑 API 暂缓，改成「整份保存 ＋ 按内容判定出处」**（规格 §1.4 的「画面编辑保存（按段落）」与 §3 的「新增按段落的编辑 API」）

- 规格写的是一份新版「只替换被编辑的段落」；实际是 **一次请求送整份详细**，服务端用
  `JpnWordDetailEditorComposer` 把「内容没变的行」判定为「没被碰过」，沿用它原来的出处（`BATCH`/`APP`）。
- **结果与规格等价**：人工行不会被 AI 覆盖（出处是 `APP` 的行会在 AI 建版时被复制），只是判断依据从
  「哪个 API 调的」改成「内容有没有变」。
- **代价**：请求体是整份详细；同一段落里两条完全相同的行无法区分谁被改过（取第一条）；
  **无法只对某一段落重新调用 AI**（所以「段落级 AI 批处理 `A_EXAMPLES` 等」仍留在待办）。
- 将来要做段落级 API 时 DB 侧不用改：`compose` 已经是按段落分别处理的，只要给请求加「替换哪个段落」即可。

② **`出題選択肢JSON` 只写在 UPD 脚本里，没有并进 `TBL_JPN_テスト出題情報.sql`**

- 实际：列与 CHECK 在 `database/日本語勉強/UPD_JPN_テスト出題情報_出題選択肢.sql`（幂等：列 `IF NOT EXISTS`、
  约束 `DROP IF EXISTS` → `ADD`）。
- **这是本仓库的惯例**：`TBL_*.sql` 是建表时的形状，之后的结构变更一律追加 `UPD_*.sql`，
  部署按 **TBL → UPD** 的顺序流。之前的 `回答履歴JSON`（`UPD_JPN_テスト出題情報_回答履歴.sql`）与
  `単語収録情報.書籍ID` 也是同样处理。
- 所以**新库部署时两个文件都要跑**，只跑 `TBL_` 会缺这一列。

③ **A 类作答会违反 `CK_JPN_技能習得_種別と技能`**（规格漏掉的真实缺陷，已修）

- 发现：`JPN_技能習得情報` 的 CHECK 只允许 B〜E 的技能区分，但作答处理是共用的，A（勉強）也会去插一行技能 → CHECK 违反。
- 修复：`JapaneseServiceImpl.updateLearning` 用 `tracksSkill(testType)`（`!"A".equals(testType)`）判断，
  A **不写技能行**；`SKILL_CODES` 里也不放 A。词级 `学習状況情報` 与 `学習日次情報` 照常更新，
  A 的确认次数在 `学習状況情報.A確認回数`（`refreshStatusFromSkills` 收到「A 就 +1」的标记）。
- 规格 §1.4／§2 没有提到这一点，是实施中读 CHECK 约束才发现的。

### 收工前的两轴审查又发现并修掉的 4 件事（2026-09-22）

审查（Standards 轴 / Spec 轴）发现的问题都已修好，配了会变红的测试：

1. **「切换生效版」的乐观锁字段不对**：规格 V7 说用版本头的 `バージョン`，但版一览 DTO 不返回它、前端送的是
   当前详细版的 `内容版数` → 真库上切回旧版会误报 409。已修：一览与详情都返回该版 `バージョン`，前端送它。
2. **`Integer` 用 `!=` 比较**（`activateDetailVersion`）：版本号 > 127 时必然 409。已改成 `Objects.equals`。
3. **并发编辑保存会 500**：第二个事务撞唯一索引抛 `DataIntegrityViolationException`。已转成 409（`ConflictException`）。
4. **batC42 每个内容种别把 C1・C2 两题都写一遍**（第二次把第一次归档掉再插）→ AI 花费与履历翻倍。
   已按「只写本次内容种别的题」过滤，生成件数也改成实际写入数。

另外顺手清理：死代码（`toJson`／空的 `resolveConflictAsMine` 契约）、冲突判定统一按 409、`maxKeptDetailOrderNo` 改名、
注释与实现对齐、新版含人工行时 `手修正フラグ=true`、验收 #9 的测试对 10 个段落逐个断言、真库测试改用 `TestSqlMapper`
