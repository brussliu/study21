# Study 2.1 バッチ管理 DB設計

2.0（`/vol5/1000/DATA0/work/study2`）のバッチ管理（`BAT_タスク実行情報` と
`COM_設定情報` の有効設定）を 2.1 向けに再設計した記録。
対象は **batS01（プロキシサービス。2.0 の batL01）を含む全バッチ**である。

| テーブル | DDL |
|---|---|
| `BAT_バッチ実行履歴情報`（改名前: `BAT_タスク実行情報`） | `database/バッチ/TBL_BAT_バッチ実行履歴情報.sql` |
| `BAT_バッチコントロール情報`（新設） | `database/バッチ/TBL_BAT_バッチコントロール情報.sql` |
| 移行（表の再編） | `database/移行/MIG_BAT_バッチ管理_20260911.sql` |
| 移行（2.0 の実行履歴 4,139 件と有効／無効） | `database/移行/MIG_BAT_実行履歴_20260912.sql` |

## 0. 2.1 の実行モデル（2.0 からの変更）

| | 2.0 | 2.1 |
|---|---|---|
| プロキシ起動バッチのコード | `batL01` | **`batS01`**（種別 S = システム起動時） |
| 実行のきっかけ | 起動時 1 回 ＋ **6 時間ごと（0/6/12/18 時）** ＋ 手動 | **起動時 1 回 ＋ 画面の【再実行】だけ** |
| 種別 | C / L / R | C / L / R / **S** |
| 有効なバッチ | 複数（`BATCH_TASK_ENABLED_*`） | **batS01 だけ**（他は無効から開始） |

- 2.0 の `BatchTaskDefinition("batL01", L, …, 360, 0, …)`（360 分＝6 時間）と
  `BatchSchedulerService` の L 種別の定期実行は 2.1 では作らない。
- 2.0 も `BatchStartupInitializer` が起動時に `batL01` を `triggerReason=application-startup` で
  実行していた。2.1 はその起動時の 1 回だけを残し、`BatchStartupRunner`（admin-api）が
  `起動種別='S'`・`依頼元コード='STARTUP'` で履歴に記録する。
- プロキシが落ちた場合は、画面の【再実行】か admin-api の再起動で復旧する。

### 有効／無効: `COM_設定情報`

`BatchTaskActivationService` が **`BATCH_TASK_ENABLED_<バッチコード>`** というキーで
`'1'`／`'0'` を保存していた（実データは `BATCH_TASK_ENABLED_batL02` と `..._batL03` の 2 件）。

- 切り替えられるのは **batL / batR のみ**（それ以外は「有効設定を変更できるのは batL / batR のみです。」）
- キーが無いバッチは**定義側の既定値**で動く
- 備考は「バッチ管理画面の有効設定（OFF時は定時実行しない）」
- 既定の利用者は `batch.jsp`（画面名）で、人が特定できる形では残っていなかった

## 2. 2.1 の設計方針

1. **有効／無効は専用テーブルへ**（`BAT_バッチコントロール情報`）。
   設定テーブル（`COM_設定情報`）は画面の入力値・AI プロンプトと同居しており、
   運転状態の一覧・最終実行日時・監査（誰がいつ切り替えたか）を持たせるのに向かない。
2. **状態・種別はコード化**し、表示文言はフロント側でローカライズする
   （実行履歴の日本語状態 → `SUCCESS` / `FAILED` / `SKIPPED` など）。
3. **監査はアカウント参照へ**。実行履歴の `依頼者`（自由文字列）は
   `依頼者アカウントID`（`ACC_アカウント` への FK）＋ `依頼元コード` に分ける。
   2.0 の実データは `scheduler` `word.jsp` `liu` のように人が特定できない値が大半のため、
   両方を残す（バッチ・スケジューラによる更新ではアカウントID は NULL）。
4. **実行の記録を実装に合わせる**。`処理時間ms` を終了時に記録し、
   `バッチ種別` / `起動種別` を定義どおりに入れる（2.1 は 'C' 固定だった）。
5. 2.1 の共通規約（`登録日時` / `更新日時`、`COMMENT ON`、楽観的ロック用 `バージョン`）に合わせる。

### 2.0 から変えた点（意図的な差）

| 2.0 / 旧 2.1 | 2.1 | 理由 |
|---|---|---|
| テーブル `BAT_タスク実行情報` | `BAT_バッチ実行履歴情報` | 用語を「バッチ」に統一（列も タスクコード → バッチコード、タスク種別 → バッチ種別） |
| 状態が日本語（正常終了 等） | コード（`SUCCESS` 等） | 表示文言はフロント側で持つ（他の 2.1 テーブルと同じ方針） |
| `依頼者` の自由文字列のみ | `依頼者アカウントID` ＋ `依頼元コード` | 人が起動した場合と機械が起動した場合を区別できるようにする |
| `処理時間ms` を記録していない | 終了時に自動計算して記録 | 実行時間の把握（2.0 の列の意図を実装で満たす） |
| 有効設定が `COM_設定情報` | `BAT_バッチコントロール情報` | 運転状態・最終実行日時・監査を 1 か所にまとめる |
| 有効設定の既定利用者 `batch.jsp` | 実行者（アカウント）＋ 登録元/更新元コード | 監査を残す |
| — | `最終実行日時` | 一覧に最終実行を出すため（バッチ完了時に更新） |

## 3. 値の対応（移行用）

| 2.0 | 2.1 |
|---|---|
| `タスクコード` | `バッチコード`（**`batL01` は `batS01` に読み替える**） |
| `タスク種別` | `バッチ種別`（値は同じ C / L / R。2.1 で S を追加） |
| `状態` `正常終了` / `異常終了` / `スキップ` / `待機中` / `実行中` | `SUCCESS` / `FAILED` / `SKIPPED` / `QUEUED` / `RUNNING`（**`実行中` は `FAILED` に寄せる**。移行時に中断していたもので、そのまま残すと二重起動の判定を塞ぐため。理由は `エラー詳細` に残す） |
| `依頼者` | ログインID と一致すれば `依頼者アカウントID`、一致しなければ `依頼元コード`（自由文字列。20 文字以内） |
| `COM_設定情報` `BATCH_TASK_ENABLED_<コード>` | 引き継がない。**`batS01` のみ `状態='1'`、他は `'0'`** で作る（運用の作り直し） |
| `開始時刻` が NULL のまま 正常終了/異常終了 | `終了時刻` → `予定時刻` → `登録日時` の順で補完（2.0 に 3 件あった） |

## 4. 実装するときの注意

- **有効／無効の正は `BAT_バッチコントロール情報`**。アプリは
  - 一覧を返す前に、定義（`BatchTaskRegistry`）にある **S / L / R の行を用意**（既存行は触らない）
  - 一覧の `active` はコントロール表の値を優先（行が無ければ定義の既定値。定義の既定値は
    **batS01 だけ有効**で、他は無効にしてある）
  - 切り替えは S / L / R のみ（`POST /api/admin/batch/tasks/{batchCode}/active`）
  - 楽観的ロック（`バージョン`）で同時更新を検出
- 画面はメニュー「バッチ管理」の下に 3 つに分ける:
  **バッチ一覧**（`views/batch/BatchListView.vue`）/ **バッチ実行履歴**（`BatchHistoryView.vue`）/
  **AI呼出履歴**（`AiCallHistoryView.vue`。2.0 の `BAT_AI呼出履歴情報` を全件移行済み。§5.5）。
  2.0 はバッチ管理（batch.jsp）と履歴管理（history.jsp）に分かれていたが、2.1 は
  バッチに関する画面をこの親メニューにまとめる。
- 一覧の画面はタブ（グルーピング）を 2.0 から引き継ぐ（英語単語 / 英単語問題生成 / 英熟語 / 日本語単語 /
  英作文 / 英語埋め / 英語長文精読 / AI共通・OCR / 学習モニター / システム ＋「すべて」）。
  所属は**タスクコード**で決める（同じ設定ページでも別のタブに入るタスクがあるため）。
  実装は `frontend/pc-web/src/features/batch/batchGroups.ts`、確認は `tests/batch-groups.spec.ts`。
- 実行の入口は 2 つだけ。**定時・循環のスケジューラは 2.1 では作らない**。
  1. admin-api の起動時: `BatchStartupRunner`（`ApplicationReadyEvent`）が
     `BatchService#startupTargets()`（種別 S かつ有効）を 1 回ずつ実行する
     （履歴は `起動種別='S'`・`依頼元コード='STARTUP'`）
  2. 画面の【再実行】: `POST /api/admin/batch/tasks/{batchCode}/rerun`（履歴は `起動種別='C'`・
     実行者を `依頼元コード` に記録）。**有効／無効に関係なく実行できる**
     （無効は「定時実行しない」の意味）。業務処理のハンドラが無いバッチは拒否する。
     **種別 C（呼出）も拒否する**（C は AI 生図の流水線・授業ノートなど他の処理が工程として
     呼ぶバッチで、要求（`要求内容`）を用意するのは呼ぶ側。一覧にも【再実行】ボタンを出さない＝
     `canManualReRun()` / 行の `canManualRerun`。他の処理からの呼出は `rerunStep` で、これは従来どおり）
- 実行履歴は `バッチコード` で引き、**未完了（QUEUED / RUNNING）を部分索引で探す**
  （二重起動の防止）。終了時に `処理時間ms` を記録する。
- `最終実行日時` はバッチ完了時に更新する（`BatchControlMapper.touchLastRunAt`）。失敗時も更新する。
- スケジューラが「有効なバッチ」を引く用途には `idx_bat_control_enabled`（部分索引）を使う。

### 5.5 AI呼出履歴（`BAT_AI呼出履歴情報`）

2.0 の `BAT_AI呼出履歴情報`（66,800 件・約 394MB）を **プロンプト・レスポンスの本文も含めて
全件** 移行した（ユーザーの指定）。DDL は `database/AI呼出履歴/TBL_BAT_AI呼出履歴情報.sql`、

  （ja / ja-zh / en / 中国語 / 日本語 / ocr / image、qwen / deepseek / bigmodel / chatgpt / doubao / gemini）。

- `バッチコード` は枝番つき（batC04-1 / batC04-2 / batC04-3 / batC15-1〜3 など 31 種）があるため

- API は admin-api の `/api/admin/batch/ai-calls`（一覧）・`/ai-calls/{id}`（詳細）・

## 7. 2026-09-19 の変更（種別 C の【再実行】・有効の見せ方と、裸の batC51 の削除）

- **種別 C（呼出）の行に【再実行】ボタンを出さない**（押せない灰色のボタンも残さず、操作の列は「—」）。
  判定は `BatchTaskDefinition#canManualRerun()`（種別 C は false）で、行の `canManualRerun` として返す。
  `POST /api/admin/batch/tasks/{code}/rerun` も種別 C を拒否する（他の処理からの呼出 `rerunStep` は通る）。
  経緯は `docs/DECISIONS.md`「なぜ種別 C のバッチに【再実行】ボタンを出さないか」。
- **種別 C の「有効」は「いま使っているか」の目印**にした（利用者の指示）。C は切り替えられず
  （`canToggleActive()` は false。スイッチは置灰）、実行の可否にも影響しない（`rerunStep` は見ない）。
  使っている C（`batC51-A`〜`D`・`batC52`・`batC61` / `batC62`）は**定義の既定値を有効**にしたので、
  `BAT_バッチコントロール情報` に行が無い環境（新規環境・C は行を作らない）でも一覧で有効に見える。
  未実装の C は無効のまま（例: `batC01`）。経緯は `docs/DECISIONS.md`「なぜ種別 C の有効を目印にしたか」。
- **モードが無い時代の裸の `batC51` を削除**した（定義行・ハンドラ・モードを指定しない入口・未使用定数・
  DTO 表の互換 1 行・`FigureMode` の別名）。AI 生成は `batC51-A`〜`D` の 4 バッチだけになった。
  **`作図モード` が NULL の要求を A として扱う規則はそのまま**（過去の実行履歴 59 行もそのまま残す）。
  経緯は `docs/DECISIONS.md`「なぜモードが無い時代の裸の batC51 を削除したか」。

## 8. 実行スケジュール（2026-09-19 追加）

2.0 は batR03 / batR04 の実行時刻がコードと通知文に固定で、batL02 は専用の 5 分スケジューラ
（`BatL02FiveMinuteScheduler` + `BatL02ScheduleGuard`）、batL03 は定義の `loopEveryMinutes=5` だった。
2.1 は **1 つの統一スケジューラ（30 秒ごと）** で 4 タスクを動かし、時刻・間隔・ずらしを
`COM_設定項目` / `COM_設定情報` で変えられるようにした。

- **実行の入口は 3 つ**: ①起動時（種別 S）②画面の【再実行】③**30 秒スケジューラ**（種別 R / L）。
- **新しい表**: `BAT_スケジュール状態情報`（バッチごとに「最後に確保した計画実行点」=
  二重実行を防ぐ永続的な確保）。DDL は `TBL_BAT_スケジュール状態情報.sql`、
  設定の初期値は `database/移行/MIG_BAT_スケジュール設定_20260919.sql`。
- **設定キー**: ネット利用の `NET_CONTROL_START_TIME` / `NET_CONTROL_END_TIME`、
  学習モニターの実行設定 `STUDY_MONITOR_L02_INTERVAL_MINUTES` / `_OFFSET_MINUTES` /
  `STUDY_MONITOR_L03_INTERVAL_MINUTES` / `_OFFSET_MINUTES`。
- **有効／無効は `BAT_バッチコントロール情報` が唯一の正**（設定画面にスイッチを置かない）。
- **次回実行時刻**は API（`GET /api/admin/batch/schedule`）がメモリの設定から計算して返す
  （列としては持たない）。
- 実行記録には `予定時刻`（計画実行点）と `起動種別`（`R` / `L`）が入る。
- 仕組みの詳細（メモリの設定キャッシュ・托底と退避・保存後の反映・取りこぼしと復帰の規則・
  単一インスタンスの前提）は **`docs/BATCH_SCHEDULE.md`** を参照。
