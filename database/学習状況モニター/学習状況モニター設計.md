# Study 2.1 学習状況モニター DB 設計

2.0 の学習状況モニター（`study_monitor.jsp` ＋ batL02 / batL03）の 4 テーブルを
2.1 の規約で再設計した記録。DDL は
`database/学習状況モニター/TBL_MON_学習状況モニター.sql`、移行は
`database/移行/MIG_学習状況モニター_20260913.sql`。

- 機能の説明: `docs/STUDY_MONITOR.md`
- 対象DB: `study21`（移行元は同一インスタンスの `study2`。dblink で接続）

2.0 の動き（そのまま引き継ぐ）:

1. **batL02** がカメラのフォルダー（`study-monitor.source-directory` ＝
   `/vol5/1000/摄像头监控/XiaomiCamera_00_B88880D0F03E`）から動画を取り込み、
   1 分間隔で画像を切り出す
2. **batL03** が画像を AI で判定する（一次判定 → 信頼度が閾値未満なら二次判定）
3. 画面で結果を確認し、必要なら手動で修正する（修正理由つき）

## 2. 2.0 からの主な変更

| # | 2.0 | 2.1 | 理由 |
|---|---|---|---|
| 1 | `ユーザーID`（'1000' など 2.0 独自） | `アカウントID`（`ACC_アカウント` への FK）＋ `旧ユーザーID` | 2.1 の持ち主はアカウント。突き合わせが取れない場合は NULL で旧 ID を残す（学習日報と同じ） |
| 2 | 判定結果が**日本語の自由文字列**（CHECK に日本語を並べていた） | **コード＋CHECK**（`STUDY_NO_PC` / `STUDY_PC` / `AWAY` / `PC_NON_STUDY` / `OTHER` / `UNKNOWN`） | 2.1 の規約（コード値＋CHECK）。表示名はアプリ側で持つ。2.0 の JS も同じ slug を使っていた |
| 3 | `状態` は `'A'` / `'X'` | `'1'`（有効）/ `'0'`（無効） | 2.1 共通（端末コントロールと同じ） |
| 4 | `登録ID` / `更新ID` は 'batL02' などの自由文字列 | `登録者/更新者アカウントID`（FK・NULL 可）＋ `登録元/更新元コード` | 2.1 の監査規約。取り込み・分析はバッチなので `登録元コード = BAT_L02 / BAT_L03`、人が直したときは アカウントID を入れる |
| 5 | 楽観的ロックなし | `バージョン` を追加 | 画面からの手動修正で使う |
| 6 | 保存パスは**絶対パス**（`/usr/local/tomcat/webapps/file/snapshots/...`） | **保存ルートからの相対パス**（`20260726/snapshot_000045.jpg`） | 2.1 の他の機能（資料・臨時ファイル）と同じ。移行先の環境で場所が変えられる |
| 7 | 索引は検索条件そのまま | 2.1 の参照パターン（撮影日時の降順・分析状態×結果・日付ごとの一覧）で貼り直し | 画面とホームの時間軸が同じ形で引ける |

そのほか、2.0 が持っていた列（一次/二次判定の各列・`検出タグJSON`・`AIコメント`・
`最新版フラグ`・`手動修正*`）はそのまま残している（バッチと画面の作りを変えないため）。

### コード値

| 列 | 値 |
|---|---|
| `分析状態コード` / `一次分析状態コード` | `WAITING` / `RUNNING` / `COMPLETED` / `ERROR` |
| `二次分析状態コード` | 上記 ＋ `NOT_REQUIRED` |
| `最終分析結果コード`（一次・二次・手動も同じ） | `STUDY_NO_PC`=学習中（PC不使用・読書または筆記）/ `STUDY_PC`=学習中（PC使用）/ `AWAY`=離席中 / `PC_NON_STUDY`=PC使用中（非学習）/ `OTHER`=その他 / `UNKNOWN`=判断不可 |
| `最終採用段階コード` | `FLASH`=一次判定を採用 / `PLUS`=二次判定を採用 / `MANUAL`=手動修正を採用 |
| `取込状態コード`（動画） | `WAITING` / `IMPORTED` / `ERROR` |
| `切出状態コード`（スナップショット） | `WAITING` / `CREATED` / `ERROR` |

## 3. 移行（`MIG_学習状況モニター_20260913.sql`）

- 判定結果の日本語 → コード、`'A'/'X'` → `'1'/'0'`、保存パスの絶対 → 相対。
- 手動修正の実行者は 2.0 の `手動修正ID`（`liu` / `ljz`）を 2.1 のアカウント
  （1 = bruss.ji.liu@gmail.com / 2 = ricky.jingze@gmail.com）へ対応付ける。
- カメラの `ユーザーID = '1000'` は 2.0 独自の番号で対応が取れないため、
  録画している生徒（`ljz` → アカウント 2）へ寄せた（**要確認**）。

- 冪等（`ON CONFLICT DO NOTHING`）。再実行しても二重にならない。

## 4. 画像（実ファイル）の移行

**SQL では移せない**（2.0 の画像は 2.0 サーバーのファイルシステムにある）。
2.0 サーバーで次を実行し、2.1 の保存ルートへ置く（詳細は移行 SQL の末尾にも記載）。

2.0 の画像は NAS の `/vol5/1000/DATA0/tomcat/tomcat11_study2/file/snapshots` にある
（中は日付フォルダー: `20260726/snapshot_000045.jpg`）。**このフォルダーの中身
（日付フォルダー）を、配備先の `files/snapshots` へそのまま置く**。

```bash
# 配備先（docker-compose.yml と同じ場所）で
mkdir -p files/snapshots
cp -r /vol5/1000/DATA0/tomcat/tomcat11_study2/file/snapshots/. files/snapshots/

# 確認: 日付フォルダーが直下に来ていること（snapshots/ が二重になっていない）
ls files/snapshots | head        # → 20260726 20260727 …
ls files/snapshots/20260726 | head   # → snapshot_000045.jpg …
```

- コンテナ側は `docker-compose.yml` の
  `STUDY21_STUDY_MONITOR_SNAPSHOT_ROOT=/app/data/snapshots` と
  ボリューム `${STUDY21_STUDY_MONITOR_SNAPSHOT_HOST_PATH:-../files/snapshots}:/app/data/snapshots:ro`
  で読み取り専用で参照する（`setting/deploy.env` で場所を変えられる）。
- **`snapshots/` をもう 1 段作らないこと。** DB の `保存パス` は
  `20260726/snapshot_000045.jpg`（保存ルートからの相対）なので、1 段深いと 404 になる。

- 2.1 は `保存パス`（`20260726/snapshot_000045.jpg`）を**保存ルートからの相対**として読む。
- **動画（録画ファイル）はコピーしない**。容量が大きいため、2.1 は動画ルート
  （既定 `/vol5/1000/摄像头监控/XiaomiCamera_00_B88880D0F03E`）から直接読む。
- コピー用の補助スクリプト: `tmp/tools/copy-study-monitor-snapshots.sh`（2.0 側で実行）。
