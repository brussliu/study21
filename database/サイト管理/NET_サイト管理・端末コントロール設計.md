# Study 2.1 サイト管理・端末コントロール DB設計

2.0（`/vol5/1000/DATA0/work/study2`）の `NET_サイト情報` / `NET_端末コントロール情報` を
2.1 の規約で再設計した記録。DDL は次の 2 ファイル。

| 機能 | テーブル | DDL |
|---|---|---|
| サイト管理 | `NET_サイト情報` | `database/サイト管理/TBL_NET_サイト情報.sql` |
| 端末コントロール | `NET_端末コントロール情報` | `database/端末コントロール/TBL_NET_端末コントロール情報.sql` |

この 2 つは対で動く（プロキシが端末 IP でモードを引き、モードごとに許可サイトを判定する）ため、
設計は 1 つの文書にまとめる。

## 1. 2.0 の実装（調査結果）

### 判定の流れ（`com.study2.proxy`）

1. リクエストのクライアント IP で `NET_端末コントロール情報` を引き、端末モードを得る。
2. モード別に許可判定を行う。

| 端末モード | 表示 | サイト判定 |
|---|---|---|
| `S` | 停止 | **すべて拒否** |
| `J` | 自由 | **すべて許可**（判定しない） |
| `G` | ゲーム | **すべて許可**（判定しない） |
| `T` | 通常 | 許可リストが必要。区分 `STUDY` と `NORMAL` を許可 |
| `K` | 休憩 | 許可リストが必要。区分 `STUDY` / `NORMAL` / `BREAK` を許可 |
| `B` | 勉強 | 許可リストが必要。区分 `STUDY` **のみ**許可 |

3. 許可リストは `NET_サイト情報` のうち **承認ステータス='承認済' かつ ステータス≠'無効'** の行。
   各行の URL を `判定方法`（先頭一致 / 末尾一致 / 含める / 完全一致）でリクエストホストと照合し、
   一致した行の区分がそのモードで許可されていれば通す（＝どれか一致すれば許可）。

- `承認ステータス` が NULL の行は「未承認」扱い（SQL が `COALESCE(...,'未承認')`）。
- サイトを編集すると `承認ステータス` は未承認へ戻る（＝再承認が必要）。
- サイト名はホスト判定の候補にも使われていた（`extractCandidateHosts(siteName, siteUrl)`）。

## 2. 2.1 の設計方針

1. **値はコード化**し、表示文言はフロント側でローカライズする
   （`database/リンククリップ/LNK_リンククリップ設計.md` と同じ方針）。
2. **監査はアカウント参照へ**。2.0 の `登録ID`/`更新ID` は画面名・バッチ名で実行者が分からない。
   人が操作した場合は `登録者/更新者アカウントID`（`ACC_アカウント` への FK）、
   エージェント・バッチ・移行は `登録元コード`/`更新元コード` に残す。
   端末はエージェントが自動登録する場合があるため、アカウントID は NULL 可とする。
3. **有効／無効（`状態` '1'/'0'）を追加**し、行を消さずに退役させる。
   端末は「有効な行の間で IP 一意」とし、退役後の IP 再利用を可能にする。
4. **承認の追跡**（`承認者アカウントID` / `承認日時`）を追加。
   `APPROVED` のときは承認日時必須（承認者が特定できない移行データは NULL 可）。
5. **判定用の正規化列**（`ホスト名`）を持ち、重複確認と索引に使う。
   判定は 2.0 と同様に「URL 文字列への一致」で行う（SQL では表現しにくいため、
   アプリ側で承認済み＋有効の行を読み込んで照合する。その読み込みを部分索引で支える）。
6. 2.1 の共通規約（`登録日時`/`更新日時`、`バージョン` による楽観的ロック、
   `COMMENT ON` による仕様の埋め込み）に合わせる。

### 2.0 から変えた点（意図的な差）

| 2.0 | 2.1 | 理由 |
|---|---|---|
| `端末ステータス`（T/K/G/B/S/J） | `端末モード`（同じ値） | 実体は運用モード。停止・自由はサイト判定を通さないため「ステータス」より正確 |
| サイト名もホスト判定の候補 | `サイトURL` と `ホスト名` のみ判定 | 表示名の書き換えで許可範囲が変わる事故を防ぐ |
| 端末 `IPアドレス` は全体で一意 | **有効な行だけ**一意 | 退役させた端末と同じ IP を再利用できない問題を解消 |
| `分類` は自由文字列 1 列 | `分類コード` + `分類名称` | UI 外の値（英会話・ニュース）を情報を落とさず保持 |
| 端末の削除のみ | `状態='0'` で無効化 | 履歴・設定を残したまま運用から外す |

## 3. 値の対応（移行用）

| 2.0 の値 | 2.1 の値 |
|---|---|
| 区分 `0.勉強` / `1.通常` / `2.休憩` / `3.ゲーム` | `STUDY` / `NORMAL` / `BREAK` / `GAME` |
| 判定方法 `先頭一致` / `末尾一致` / `含める` / `完全一致` | `PREFIX` / `SUFFIX` / `CONTAINS` / `EXACT` |
| 分類 `学習` / `娯楽` / `ショッピング` / `SNS` / `その他` | `LEARNING` / `ENTERTAINMENT` / `SHOPPING` / `SNS` / `OTHER` |
| 分類 `英会話` / `ニュース` など上記以外 | `OTHER` + `分類名称` に元の文字列 |
| 承認ステータス `未承認` / `承認済` | `PENDING` / `APPROVED`（`APPROVED` は `承認日時` を移行日時で埋める） |
| ステータス `有効` / `無効` | `状態` `'1'` / `'0'` |
| 端末ステータス `T`/`K`/`G`/`B`/`S`/`J` | `端末モード` 同じ値 |
| 登録ID / 更新ID `site.jsp` / `history.jsp` | 破棄（実行者情報として無意味）。`batR03` などは `更新元コード` に移してよい |
| 端末 `登録ID='AGENT'` | `登録元コード='AGENT'`、`登録者アカウントID` は NULL |

## 4. 実装するときの注意

- **プロキシの判定はアプリ側で行う**（`判定方法` の 4 種は SQL で表現しにくい）。
  読み込み対象は `承認ステータス='APPROVED' AND 状態='1'` で、`idx_net_site_approved_active`
  が効く。サイト数は 2.0 実績で 175 件程度なので全件読み込みで十分。
- **承認フロー**: 新規登録と編集後は `PENDING`。管理者が承認すると `APPROVED` +
  承認者・承認日時を記録する。`REJECTED` は「却下」で、判定には使わない。
- **端末モードの変更**は監査対象。人が操作した場合は `更新者アカウントID`、
  エージェント／バッチは `更新元コード` を必ず埋める。
- **`最終接続日時`** はプロキシが更新する想定。プロキシ実装までは NULL のままとする。
- **権限**: 管理者専用の想定（`docs/ROLE_FUNCTION_MATRIX.md` では未決定）。
  生徒・保護者に開放する場合は、テーブル単位ではなく API の権限で制御する。

## 5. この設計の検証（実施済み）

一時データベース（`study21_ddlcheck`、検証後に削除）で次を確認した。実 DB の study21 は未変更。

1. **DDL の適用**: 2 ファイルともエラーなく適用でき、索引 8 本が作成される。
2. **制約の反例 9 件**（不正な区分・判定方法・状態、承認日時なしの APPROVED、
   空白のみの名称、存在しないアカウント（FK）、不正な端末モード、空白付き IP、
   有効端末の IP 重複）が**すべて拒否**される。
3. **正例**: 退役（`状態='0'`）にした端末と同じ IP を再登録できる
   （＝2.0 で問題だった「IP が埋まって再利用できない」を解消）。
4. **2.0 実データの移行リハーサル**: study2 から出力した実データ
   （サイト 175 件・端末 5 件）を §3 の対応表どおりに変換して全件投入できた。

| 確認項目 | 結果 |
|---|---|
| サイト件数 | 175 件（欠落なし） |
| 承認ステータス | 全件 `APPROVED`（`承認日時` は移行日時で補完） |
| 区分の分布 | `BREAK` 100 / `STUDY` 31 / `NORMAL` 22 / `GAME` 22（2.0 と一致） |
| 判定方法の分布 | `SUFFIX` 173 / `PREFIX` 1 / `EXACT` 1（2.0 と一致） |
| 分類 | `OTHER` 164 / `LEARNING` 6 / `ENTERTAINMENT` 2 / `SNS` 1 ＋ `OTHER`+`分類名称`（英会話・ニュース）2 件 |
| ホスト数 | 149（2.0 の正規化結果と一致） |
| 端末 | 5 件・IP 5 種類（一意制約に抵触しない） |

検証スクリプト（エージェントの一時ファイル）:
`tmp/ddl/verify-net-ddl.sql`（制約の正例・反例）、`tmp/ddl/verify-migration.sql`（移行リハーサル）。
